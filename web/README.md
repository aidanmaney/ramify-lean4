# web — the renderer

React + Vite + d3-dag. This half knows nothing about Lean: it is handed a
`Proof` and draws it. See [../README.md](../README.md) for the project, and
[../OVERVIEW.md](../OVERVIEW.md) for how a proof becomes a tree.

The same code has **two entry points**, and the split is the thing to know
before editing anything here:

| | entry | data |
| --- | --- | --- |
| the product | `src/widget.tsx` | `ProofTree.getProofTree` over RPC, in the VS Code infoview |
| the harness | `src/App.tsx` | `public/sample.ndjson`, generated by `../gen.sh` |

`ProofTreeView.tsx`, `proofToTree.ts` and `layout.ts` are **source-agnostic** —
they must not import NDJSON or infoview APIs. Only `taggedRender.tsx` and
`tacticTokens.tsx` may reach for infoview APIs.

```bash
npm install
npm run dev           # the harness, in a browser
npm run build:widget  # esbuild src/widget.tsx → dist/proofTreeWidget.js
npm run typecheck     # tsc -b (covers widget.tsx too)
npm run lint          # eslint .
npm run build         # the harness as a static site → dist-app/
```

Two output directories, deliberately: `vite build` empties its `outDir`, so if
`npm run build` wrote to `dist/` it would silently delete
`dist/proofTreeWidget.js` — the file `ProofTreeWidget.lean` compiles into
itself with `include_str`. Hence `outDir: 'dist-app'`, and hence
`dist/proofTreeWidget.js` being tracked in git despite being generated.

There is **no test runner**. Verification here is: build, run one of the two
entry points, and look at the tree — plus, for the pure modules (`calcEdit`,
`deleteEdit`, `flagEdit`, `completion`, `diagnostics`, `layoutKey`, `elide`),
one-off probes driven against the harness corpus, which is most of what that
corpus is for.

`npm run lint` is load-bearing beyond style: `eslint-plugin-react-hooks` runs
the React Compiler's analysis, so a violation there is not a nit — it usually
means a component silently stopped being memoizable.
