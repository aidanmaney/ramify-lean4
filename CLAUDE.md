# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Lean 4 proof rendered as an interactive tree. The renderer has **two data sources** feeding the same React/d3-dag view:

```
# 1. Offline CLI (dev harness):
proofs/*.lean ──ppharness (Lean CLI)──▶ NDJSON ──proofToTree (web)──▶ d3-dag tree

# 2. Live infoview widget (production target):
cursor pos ──ProofTree.getProofTree RPC──▶ Proof ──proofToTree (web)──▶ d3-dag tree
```

- `lean/` — **ppharness**, a thin owned wrapper around Paperproof's `BetterParser_Tree`. Elaborates a `.lean` file to completion and harvests the elaborator's `InfoTree`s into proof steps, emitting one NDJSON line per proof.
- `lean/ProofTreeWidget.lean` — the **infoview user-widget**: `@[server_rpc_method] ProofTree.getProofTree` runs the *same* `BetterParser_Tree` over the live server's `snap.infoTree`, and `@[widget_module] ProofTreeWidget` (`Component PanelWidgetProps`) `include_str`s the bundled renderer. It is the RPC counterpart of ppharness — no CLI, no NDJSON.
- `web/` — React + Vite + d3-dag renderer that draws goals as boxes, tactics as edge-nodes, hypotheses on edges. `ProofTreeView.tsx` is the shared, source-agnostic view; `App.tsx` feeds it a proof from NDJSON, `widget.tsx` feeds it a proof over RPC.
- `gen.sh` — the CLI seam: runs the parser over `proofs/*.lean` and writes `web/public/sample.ndjson`.
- `ext/proof-tree-companion/` — a small VS Code **companion extension** for widget gestures the infoview API can't express (see "Popout editing"); dev-installed via symlink, no build step.

## Commands

**Lean** (run from `lean/`):
```bash
cd lean && lake exe cache get && lake build   # fetch Mathlib oleans, build — RE-RUN cache get after any `lake clean` (it deletes the oleans; without them an `import Mathlib` file makes the editor compile Mathlib from source for hours)
lake build ppharness                          # rebuild the CLI
echo 'theorem t : True := by trivial' | lake env lake exe ppharness   # parse stdin
lake env lake exe ppharness FILE.lean         # parse a file (lake env puts Mathlib on LEAN_PATH)
```

**Regenerate web data** (from repo root) — do this after editing anything in `proofs/`:
```bash
./gen.sh                                       # proofs/*.lean → web/public/sample.ndjson
```
Do not hand-edit `web/public/sample.ndjson`; it is generated.

**Web** (run from `web/`):
```bash
npm install
npm run dev          # Vite dev server (standalone app, reads sample.ndjson)
npm run build        # tsc -b && vite build (standalone app → dist-app/)
npm run build:widget # esbuild src/widget.tsx → dist/proofTreeWidget.js (the infoview bundle)
npm run typecheck    # tsc -b only (covers widget.tsx too)
npm run lint         # eslint .
```
There is no test runner configured in either half; "verify" means build + run the dev server and inspect the rendered tree.

The two builds have deliberately **separate output dirs** (`vite.config.ts` sets `outDir: 'dist-app'`): vite empties its outDir on every build, so sharing `dist/` would make `npm run build` silently delete `dist/proofTreeWidget.js` — the Lean build input — and break the next `lake build` / editor `setup-file` with "no such file or directory". Both dirs are gitignored artifacts.

**Infoview widget** — the bundle is a Lean build input via `include_str`, so build it *before* `lake build`:
```bash
cd web && npm run build:widget      # produces web/dist/proofTreeWidget.js (gitignored artifact)
cd ../lean && lake build ProofTreeWidget
```
Then open a file in *this* Lake project with `import ProofTreeWidget` and `show_panel_widgets [ProofTreeWidget]` (see `lean/ProofTreeDemo.lean`, which is core-only so it needs no Mathlib). The panel follows the cursor.

`lean/lakefile.toml` declares `web/dist/proofTreeWidget.js` as a Lake `input_file` and wires it into `ProofTreeWidget`'s library via `needs`, so the two commands above actually compose correctly. Without this, `lake build` is a **silent no-op** when only the JS changed: `include_str` is a bare `IO.FS.readFile` at elaboration time, invisible to Lake's dependency graph, so Lake sees `ProofTreeWidget.lean`'s own source as unchanged and reuses the stale `.olean` — hit this for real once, spent a while confirming via `.olean` mtimes and `strings`-grepping the compiled output. **Use `needs`, not the deprecated `extraDepTargets`** — the latter parses and resolves target names fine (a bogus name does error) but empirically does not propagate a changed file's hash into the rebuild trace; `needs` does (confirmed with a real edit → rebuild → `lake build` cycle, checking the compiled `.olean`'s bytes, not just exit status).

## Critical constraints

- **Toolchain is pinned to Lean v4.27.0 on purpose** (`lean/lean-toolchain`, `lean/lakefile.toml`). ppharness drives the frontend with `IO.processCommands` then reads `infoState.trees`. On v4.29+ tactic subtrees elaborate **asynchronously** and aren't attached when read, so `BetterParser_Tree` walks a tree with zero `TacticInfo` nodes and returns empty proofs (`{steps:[], allGoals:[]}`). Keep ppharness and Mathlib on the same v4.27.0. Do not bump without re-validating the harvest path.
- **Mathlib is a build dep only so its oleans land on `LEAN_PATH`** (via `lake env`); that's what lets real `import Mathlib` proofs elaborate at parse time. The Paperproof library itself is core-only.
- `Main.lean` calls `enableInitializersExecution` before the first import and the CLI is built with `supportInterpreter = true`, because importing Mathlib runs its `@[init]` declarations through the interpreter. Both are required; removing either breaks `import Mathlib` sources at runtime.

## Architecture notes that span files

**The wire format is a cross-language contract.** Paperproof's `ProofStep` / `GoalInfo` / `Hypothesis` structs (`lean/.lake/packages/Paperproof/lean/Services/BetterParser.lean`) are mirrored field-for-field in `web/src/paperproof.ts`. ppharness (`lean/Ppharness.lean`) only hand-serializes `Result` (which lacks a derived `ToJson`); everything else rides upstream's derived instances. Changing a field on either side requires changing the other. `BetterParser.annotated.lean` at the repo root is a study copy of the upstream parser annotated for this project (not part of the build).

**How a proof becomes a tree.** The renderer never consumes `paperproof.ts` types directly. `web/src/proofToTree.ts` adapts a `Proof` into `TreeNode[]`: each tactic `step` becomes `goalBefore ──(tactic node)──▶ goalsAfter ++ spawnedGoals`. The tree root is the goal consumed by some tactic but produced by none (`rootIds`). A goal's **local context rides the goal node itself** (`TreeNode.hyps`) and is drawn INSIDE its box, stacked above the `⊢ ` line — the infoview's own hyps-then-turnstile reading, so a goal and the assumptions it holds under are one thing to look at. (It used to be a separate label floating on the goal→tactic edge; merging it killed a whole tier of boxes, connector stubs and band arithmetic, and gave leaf goals — which have no outgoing edge — a context for the first time.) Each line is flagged `used` from the CONSUMING tactic's `tacticDependsOn` (rendered as a `▸` gutter marker + full ink, unused lines recede; fvarIds match `Hypothesis.id`; a leaf goal has no consumer, so nothing is flagged). By default a context shows the **delta** the goal gained over the goal its own producing step consumed (root goals: their binders) **plus any older hyps the consuming tactic uses**; the control rail's ∀ toggle switches to the goal's full context (additive down the tree) by rebuilding the engine with `proofToTree(proof, { fullHyps: true })` — node ids are unchanged, so fold/zoom/sequence state deliberately survives the toggle (the view resets those on a new *proof*, not a new engine). Goal labels carry a `⊢ ` prefix (`TURNSTILE` in proofToTree.ts — the infoview's own goal convention); it's part of the measured label, and the tagged renderer strips it before its text-equality match then re-attaches it as plain text (renderTaggedGoal), so keep the two in sync. Nodes are emitted in DFS preorder so layout ordering reads top-down/left-to-right.

**The layout engine is the heart of the web side** (`web/src/layout.ts`). `createLayoutEngine(data)` builds an engine bound to one tree; folding and relayout are pure functions of `data`. Key design choices:
- **Two layout modes behind one output shape.** `computeLayout(collapsed, only?, focus?, compact?)` returns `PlacedNode`/`PlacedLink` (types.ts) from either positioner, so the renderer is layout-agnostic. The **compact trunk outline** (default; the control rail's ≡ toggle) is a hand-rolled DFS with a global y-cursor and per-branch x-indent — written precisely because Sugiyama forces same-depth nodes into one vertical band: every node gets its own vertical slot (read by scrolling), left edges align per indent, a branching tactic's FIRST child (Paperproof lists the main continuation first) resumes the trunk while later side goals branch right by `TRUNK_INDENT` and are drawn *above* the resumption so branches stay local to their tactic. Connectors are orthogonal │└ elbows dropped from `TRUNK_INSET` inside the parent's left edge — bare lines, deliberately NO arrowheads (flow reads consistently down/right; triangles were noise poking into boxes); overlap-freedom is by construction (exclusive y ranges). The **wide mode** is the original Sugiyama tree (its d3-dag output is normalized into the same placed shape). Fold/accordion/focus/sequence ride the shared visibility sweep, so they work identically in both modes; the view re-centers on a mode toggle (mode is part of `viewKey`) — compact pins the content's left edge near the viewport edge (`COMPACT_LEFT`, a tight inset, not the full `MARGIN.left`), wide centers the root.
- **Stable sibling order under folding** (wide mode): a custom `stableDecross` sorts each Sugiyama layer by a fixed creation-order key (`ORD`) instead of minimizing crossings, so collapsing one subtree never reshuffles unrelated siblings. (The trunk mode is order-stable trivially — it never reorders anything.)
- **Box sizing uses canvas `measureText` in the exact render font**, not char counts — Lean labels are full of wide unicode (ℕ ∀ ∃). Text is pixel-wrapped to a ~100-column width budget so it's always bounded by its box; breaks prefer semantic seams (after `,`/`;`, or before a connective so the continuation STARTS with it — two tiers via `seamRank`: clause boundaries `→ ↔ ∧ ∨ ⊢` beat relations `= ≤ ∣ …`, so `(2 ≤ n → …)` never splits at the `≤` when an `∧` seam is nearby; greedy word break when no seam is usable). Width-wrapped continuation lines carry `WrappedLine.cont` and hang-indent by `CONT_INDENT` in both the measurer and the render (tspan x / tagged line paddingLeft); explicit `\n` lines are NOT continuations. `proofs/wrap.lean` is a deliberately over-long statement that exercises this. The render must match: node/hyp `<text>` set `letterSpacing: 0` (the page CSS sets a nonzero default that canvas wouldn't otherwise account for), and geometry constants (`LINE_H`, `HYP_GAP`, `NODE_PAD`, …) are exported and shared between layout and render. The code-text FAMILY follows the EDITOR's font: `getCodeFontFamily()` (layout.ts) resolves `--vscode-editor-font-family` — the CSS variable the infoview's own `.font-code` uses, present on the webview root — falling back to `monospace` when absent (standalone app, headless). Measurer and every code-text render site share it (UI chrome stays monospace); sizes stay ours (`NODE_FONT_PX` etc.), only the family follows the editor. It follows LIVE: VS Code does **not** reload the webview on a font change — it rewrites the CSS variables on the root element's `style` attribute in place — so `ProofTreeView` watches that attribute with a MutationObserver (the infoview's own components do the same) and calls `refreshCodeFontFamily()`, which clears the width cache on change; the view keys its engine memo on the family so all geometry is re-measured (fold state survives — reset is keyed on the *proof*).
- **A goal's context block is measured as part of its box** (`sizeOf(label, hyps)` → `LayoutNode.hypH`): the box's text stack is the context lines (at `HYP_FONT_PX`/`HYP_LINE_H`, plus `HYP_GAP`) then the label lines, and the box's width is the wider of the two blocks. Context lines are deliberately NOT pixel-wrapped — the box grows to fit them — because a mid-line break would destroy the exact `name : type` string the widget's tagged renderer matches on; only the label half is capped at `MAX_W`. A node's layout band is therefore just comment strip + box, with the box pinned at the bottom, plus a constant layer gap; edges leave a box's bottom and land above the target's whole band.
- `computeLayout(collapsed, only?, focus?)` hides a node iff all its parents are collapsed/hidden (fixpoint sweep). The optional `only` set restricts layout to exactly those ids — used by the "sequence/linearize" feature (`pathBetween` walks single parents to get the ancestor→descendant path; with no branches, Sugiyama renders one column). The optional `focus` set (from `subtreeIds`, a goal's ◎ hover-bar button or ⌥-click in the view) scopes the world to one subtree *without* suspending the fold rule: the sweep ignores out-of-scope nodes, so the focus root lays out as a root and folding keeps working inside (fold state is shared with the full view on purpose).

**Data source is swappable by design — and both sources now exist.** The shared view is `ProofTreeView.tsx` (layout, folding, zoom/scroll, SVG render); it takes one `Proof` and nothing else. Two thin shells feed it: `App.tsx` `fetch`es `SAMPLE_URL` (`sample.ndjson`); `widget.tsx` calls `ProofTree.getProofTree` over RPC inside the infoview. `proofToTree` / `layout.ts` / `ProofTreeView.tsx` are source-agnostic — do not import NDJSON or infoview APIs there.

**The node↔source link (widget only).** `ProofStep.position` (a tactic's LSP range, already on the wire) is the sole source of truth for every node's position — no vendored parser change needed. `proofToTree.ts` sets it three ways: a **tactic** node gets its own step's `position`; a **goal** node gets the `position` of the step that *produced* it (`producingPosition`, keyed by `stepGoalsAfter`) — root goals get none, since they're the theorem statement, not a tactic's output; context lines need no position of their own any more — they live in the goal's box, and that goal's `position` is already the introducing step's.

`ProofTreeView` uses these two ways when the widget supplies the hooks: **tree→source** — clicking a positioned tactic node (whole box) calls `onReveal`; goals stay fold-on-click (their primary interaction), so their secondary actions ride two complementary surfaces: a **hover action bar** (`NodeActionBar`, a pill of real button-sized targets straddling the box's top-right corner, rendered inside the node's `<g>` so box→bar pointer travel can't un-hover it) with `»` reveal and `◎` focus-subtree buttons, and **modifier fast paths on the whole box** — ⌘/Ctrl-click reveals (the editor's own go-to-source gesture), ⌥-click focuses. `onReveal` maps in `widget.tsx` to the companion's `reveal` action (`ProofTree.popoutEdit` RPC with `action: "reveal"`), NOT `ec.revealLocation`: vscode-lean4's reveal always picks the FIRST visible editor for the uri (the main buffer), while the companion targets the lens when one is open — so a node click retargets the lens, whose cursor move flows back as `highlightPos`, closing the tree↔lens loop (without the companion installed, reveal is inert); **source→tree** — `highlightPos` (the editor cursor from `PanelWidgetProps.pos`) accent-outlines exactly ONE node: the innermost (smallest-span) TACTIC whose range contains the cursor (`cursorNodeId`). It must be one, not "whatever contains it": recorded ranges overlap by construction — goals carry their PRODUCER's range, structured tactics (`induction`/`have`) contain everything nested inside, and Paperproof ranges include trailing trivia — so naive containment lights up half a branch. **Two things make the pick land on the node you clicked, and they are only correct together** (measured over `sample.ndjson`'s 86 tactics by simulating the accent lookup for every one): `positionContains` is HALF-OPEN `[start, stop)`, because trivia-inflated ranges make a tactic's `stop` equal its successor's `start`, so an inclusive end lets the neighbour match and the smallest-span tie-break silently prefers whichever is shorter; and the companion leaves the CURSOR at the range's **start**, never its end, because a range's end sits either in the next tactic or (for a structured tactic) deep inside its last nested one. Cursor-at-end + inclusive = 17/86 wrong; cursor-at-start + inclusive = 31/86 wrong; cursor-at-end + half-open = 53/86 wrong and 33 with no accent at all; cursor-at-start + half-open = 0 wrong, 0 missing. Fixing only one of the two makes it worse than the bug. Goals never take the cursor accent (their spans are the producer's, always redundant with its node). The accented node is also TRACKED: when the cursor lands on a different node, the view smooth-scrolls it into view — only if it sits outside a comfortable viewport band, and never from scroll/zoom/fold alone (`trackedCursorNode`; a node hidden by folding is skipped, then tracked when an unfold reveals it). Vertical (the reading axis) centers the node in both modes; horizontally, wide mode centers it, but compact mode NEVER re-centers (that would pull the left-aligned trunk off screen) — it only nudges rightward when a node spills past the right edge, bringing its left edge to `COMPACT_LEFT` (eyeballed, no exact-center math). Clicking the widget BACKGROUND dismisses the accent (clicks focus the infoview without moving the editor cursor, so it would otherwise linger); node clicks stopPropagation, and any real cursor move re-arms it. Both are inert in the standalone app (no `onReveal`/`highlightPos`). What's *not* recoverable this way is a hypothesis's exact identifier token (only the introducing tactic's whole range) and non-root goals having any span of their own (they're synthesized, not written) — closing that gap to token precision needs an additive `snap.infoTree` walk in our own `ProofTreeWidget.lean` (no vendored edit either), not a parser fork.

A node's native SVG `<title>` (hover tooltip) lists ONLY the actions available there (`· click to reveal in source`, `· double-click to edit`, `· ⌥-click to focus this subtree`), plus the `▸ = used by the tactic below` legend on a goal whose context has marks. It used to lead with the node's own un-wrapped text, which the box is already showing — noise that buried the one thing a tooltip is good for. A node with no actions (any tactic in the standalone app) gets no `<title>` at all. When the interactive tagged label (below) takes over a box, the `<title>` retreats to the box `<rect>` so it doesn't stack on the type tooltips.

**In-place tactic editing (widget only).** Double-clicking a tactic node swaps its box for a textarea pre-filled with the tactic's source; Esc cancels, Enter commits single-line tactics (Shift+Enter newline), ⌘/Ctrl-Enter always commits, so does blur — a no-op edit just closes. Two wire facts make a server-side seam necessary: Paperproof's `tacticString` is **prettified for display** (first line only, `rw [...]` re-synthesized) and `ProofStep.position` **includes trailing trivia** — so neither is safe to write back with. `ProofTreeWidget.lean` therefore ships `tacticEdits: Array TacticEdit` (`{start, stop, text}` per distinct step range): the server re-extracts the range's verbatim source and trims trailing trivia with `trimmedEnd` (ProofTreeComments.lean — strips trailing whitespace, then any comment closing at the trimmed end, iterated), so replacing the tight `[start, stop)` can never eat a trailing comment. JS-side the seam is two optional `ProofTreeView` hooks: `getTacticEdit` (keyed by `position.start`, resolved in `widget.tsx` from `tacticEdits`) gates the affordance (hint `· double-click to edit` in the `<title>`), and `onEditTactic` commits via `ec.api.applyEdit` — the editor's own edit pipeline, so it lands on the undo stack and triggers re-elaboration; the tree redraws off the next RPC, and the shape-keyed reset (see comments paragraph) keeps fold/zoom across a same-shape edit. Commit uses a ref (`editingRef`, mirrored via effect) nulled synchronously: committing via Enter unmounts the textarea, whose blur would otherwise re-commit from a stale closure. Disabled in sequence mode and in the standalone app (no hooks). Both editing states (open overlay, dismissed accent) clear on a shape change. Two render facts: the textarea overlay is rendered AFTER the whole nodes loop (SVG paints in document order — inside the node's own `<g>` every later sibling paints over it), and the edited node's box/label/fold-glyph get `visibility: hidden` while it's open (the overlay is bigger than the box, and an accented node would clash through it) and sizes to its content live (width via `measureText` on the longest line, height from the line count) instead of relayouting the tree; and on *editable* tactics the single-click reveal is DEFERRED 300ms and canceled by the dblclick handler (`deferReveal`) — a double-click's first click is a plain click, and an instant reveal steals focus to the editor mid-gesture, eating the second click. The lens (next paragraph) is a hover-bar button, not a modifier gesture, so double-click is the ONLY editing gesture on a tactic.

**Popout editing — the "lens" (widget + companion extension).** A tactic's hover bar carries a `⧉` button that opens the proof in the **lens**. This deliberately is NOT a modifier gesture: it lived on ⇧-double-click and silently stopped working, because ⇧-click is a **selection-extension** gesture in the webview — it highlights the tree's text and the second click never lands as a `dblclick` (plain double-click kept working throughout, which is what isolated it). Do not re-introduce a modifier here; modifiers on tactics are also wanted for LSP hover work. The button is gated on `onPopoutEdit` ALONE, not on the in-place-editing seam: the lens only needs a range to select, so a tactic missing from `tacticEdits` (which keys on the step's exact start) falls back to the node's own trivia-inflated `position` — selecting slightly more but always opening. Because the bar is the entrypoint, tactic bars are placed differently from goals': `NodeActionBar`'s `placement` prop hangs a tactic's bar off the box's RIGHT edge, vertically centred, since a tactic box is one line tall and the compact gap above it (`TRUNK_GAP_STEP`) is shorter than the bar — the goals' top-right-corner placement would collide with the goal box above. **Both placements overlap the box by `BAR_OVERLAP`, and that is load-bearing, not cosmetic**: the bar renders inside the node's own `<g>` and hover is tracked on that `<g>`, so any gap between box and bar is dead space that fires `mouseleave` and unmounts the bar mid-travel — the pointer can never land on it (the bar literally dodges the mouse). A tactic's overlap falls inside `NODE_PAD`, so it covers padding, not glyphs. Belt and braces, the companion also registers a `proofTree.openLens` **command-palette** entry acting on the active editor's cursor: a widget-independent way in, and the isolation test when the tree's button misbehaves (if the palette opens the lens, the whole companion half is proven good). The lens itself is: a slim editor group the companion splits off directly BELOW the Lean infoview's own group, showing the real buffer with the tactic's tight range selected and revealed `AtTop` (the lens is a few lines tall, so the tactic IS its content), `lineNumbers: Off` per-editor. Same window, same document, same Lean server: vim/LSP/keybindings all apply, edits sync with zero re-elaboration, and same-window group focus is reliable. This REPLACED a floating auxiliary-window design that fought VS Code on every front — vscode#198797 (focus lands only visually ~10% of the time, vim chords keep hitting the main window), no window-geometry API (needed macOS-only `osascript` + an Accessibility grant), per-window zoom tricks — all deleted; if tempted to resurrect floats, reread that list. (A second *full* VS Code window is even worse: own Lean server AND a separate in-memory document — unsaved edits don't sync.) The relay: the infoview's `EditorApi` has no `executeCommand`, and both webview-side bridges FAIL — vscode-lean4's `showDocument` silently drops non-file URIs (`parseExtUri`, `external:` ignored), and a synthetic click on a `vscode://` anchor NAVIGATES the webview blank (webviews only intercept trusted clicks) — so `ProofTreeView.onPopoutEdit` → `widget.tsx` calls the `ProofTree.popoutEdit` RPC → the server (ProofTreeWidget.lean) writes `~/.proof-tree-companion/popout-request.json` → `ext/proof-tree-companion` (a build-step-free CommonJS extension, dev-installed by symlinking into `~/.vscode/extensions/aidan.proof-tree-companion-0.0.1`) watches the dir with node `fs.watch`. A nonce dedupes fs.watch's duplicate events; an ownership check keeps other windows' companions from reacting — `getWorkspaceFolder` OR "this window has the doc open", because a file outside any workspace folder has no folder and the workspace test alone would drop its requests in total silence. **The whole relay is invisible by construction** (a file written by a Lean server, read by a watcher in another process), so both ends log: the companion writes every request, skip reason and failure to an Output channel named "Proof Tree Companion", and widget.tsx routes all three companion calls through one `callCompanion` helper whose rejections surface in an inline error banner instead of being swallowed by `void rs.call(...)`. When a gesture "does nothing", read the Output channel first — it distinguishes never-arrived from arrived-and-skipped from arrived-and-threw. Mechanics: the infoview's group is found by its webview tab (`viewType`/label match), focused via the positional `focusNthEditorGroup` commands (the only way to activate an arbitrary group), then `workbench.action.newGroupBelow` (NOT `splitEditorDown` — that would try to duplicate the webview), the doc opens there, and 5 × `workbench.action.decreaseViewHeight` shrink it (best-effort; fewer nudges = taller lens — the split ≈ 9 nudges tall, so height ≈ (9−n) slices; tune here). The lens is REUSED on subsequent popouts, and `findLensColumn` resolves it down a three-step ladder because a remembered `viewColumn` alone is not enough — both ways it goes stale leave a lens plainly visible while the next popout splits another one underneath it: a **window reload** restarts the extension host (memory cleared) but VS Code restores the editor layout, lens and all; and **viewColumns renumber** whenever any group closes, so the remembered number starts naming a different group. The ladder: (1) the remembered column, revalidated by the group still holding the doc; (2) our own tag — `lineNumbers: Off` is a per-editor option nothing else here sets, so it identifies the lens editor across renumbering (but not across a reload: editor options are runtime state); (3) plain "a second group already showing this document", which survives both — the infoview group can't be confused for it, holding a webview tab rather than the uri, and adopting a second view we didn't open beats stacking a third. The same reasoning fixes the close listener: a vanished column number is not a closed lens, so it re-resolves by the tag before restoring the chrome (otherwise closing an unrelated group un-strips the editor and orphans the lens). To maximize the infoview column, `stripEditorChrome` sets — GLOBALLY, there is no per-window/per-group settings API — `workbench.editor.showTabs: "none"`, `breadcrumbs.enabled`/`editor.glyphMargin`/`editor.folding`/`editor.minimap.enabled` false while a lens is open, restored when it closes (tab-group listener watches `lensColumn` vanish); originals are PID-stamped to `~/.proof-tree-companion/chrome-backup.json` so a crash restores on next activation (dead owner only), and a second window's strip adopts the first's originals instead of snapshotting already-stripped values. The companion also exposes the same action as a `vscode://aidan.proof-tree-companion/edit` deep link for OS-side tooling, and is intended to grow the widget's global settings / persistent state. After changing its `package.json`, a full VS Code restart may be needed (manifest rescan); `extension.js` changes need only a window reload. Widget-side chaff cut to match: no `<details>`/summary wrapper around the tree (the tree is the panel's content), height 100vh. **The tree has PRIMACY in the infoview column**: the info card's body renders Tactic state / Expected type / panel widgets / Messages as SIBLINGS, and the blocks above a widget resize on every cursor move, bouncing the tree — there is no section-order API, but the widget shares the webview document, so `useSectionOrderCss` (widget.tsx) injects a `:has()`-scoped stylesheet that turns the hosting body into a flex column and orders the tree (`[data-ptw-root]`, set on the tree root AND the placeholder so the slot never flips) first — the volatile blocks flow below it and take space from the bottom, not the top; the infoview's own `<details>` wrapper summary around the widget (it names panel widgets) is display:none'd as chaff. Selectors are scoped entirely on `[data-ptw-root]` so no other infoview surface is touched.

**Interactive subterm tooltips (widget only).** A goal box's label and its context lines' types get the infoview's own hover behavior (type popup per subterm) via core `Widget.goalToInteractive` → `CodeWithInfos` on the Lean side and `InteractiveCode` from `@leanprover/infoview` on the JS side — no ProofWidgets machinery, no vendored parser change. `collectTaggedGoals` in `ProofTreeWidget.lean` is an additive `snap.infoTree` walk that re-prints every tactic's goals with tags kept (the vendored `printGoalInfo` computes the same tagged print and drops the tags via `.fmt.pretty`), keyed by mvarId string = `GoalInfo.id`; it ships as `ProofTreeData.taggedGoals`, which forces the payload to derive `Server.RpcEncodable` (tags hold live `WithRpcRef`s — session-bound, hence never in the CLI's NDJSON). JS-side the seam is two optional `ProofTreeView` hooks (`renderTaggedGoal`/`renderTaggedHyps`, returning ReactNodes per line) implemented in `web/src/taggedRender.tsx` — with `tacticTokens.tsx` (see the tactic-token paragraph) one of only two renderer-adjacent modules allowed to import infoview APIs; the view just swaps its SVG `<text>` for a `<foreignObject>` in the identical line geometry. Three invariants make this safe: **text equality** — a tagged line is used only if its stripped text exactly equals the plain string the layout measured (`taggedRender` checks; any mismatch falls back to plain SVG text per node/line); **no second wrapping** — `web/src/taggedText.ts` slices the `TaggedText` tree at the layout's own line-break offsets (duplicating tags that span a break), so the HTML lines are non-wrapping (`white-space: pre`) and can't disagree with the measured box; and **font normalization** — `InteractiveCode` wraps its output in `<span class="font-code">`, which the infoview styles with the *editor's* font and foreground color, so uncorrected it renders bigger than the measured box (and wrong-colored on our light boxes in dark themes). Every tagged line is wrapped in `.ptw-tagged`, and `taggedRender` injects a `.ptw-tagged .font-code { font: inherit; … }` rule so the rich text inherits the very font the canvas measurer used. The hover popups keep their native editor styling because the infoview portals them to `document.body`, outside any `.ptw-tagged` ancestor. The same injected sheet also fixes a **popup flicker**: the infoview renders a popup's loading (and error) state as a bare TEXT NODE inside `.tooltip-code-content` and its resolved state as real elements, so it would pop up showing `Loading..` and then resize under the pointer. `.tooltip:has(.tooltip-code-content):not(:has(.tooltip-code-content > *))` is exactly "content hasn't arrived", and holds the popup hidden for 150ms before revealing it anyway. Written to apply ONLY in that state on purpose: the resolved popup gets `animation: none`, so it is never delayed AND a failure to animate (a hidden document never advances CSS animations) cannot strand a populated popup invisible — which the tempting "hide all, reveal by animation" shape could. Slow calls and errors still surface, just 150ms later. This is the ONE selector here not scoped to `[data-ptw-root]`, unavoidably: the popups are portalled outside our subtree, so there is no ancestor to scope on. It is confined to appearance timing, and to tooltips carrying code content, so the infoview's menu tooltips are untouched. **Ref lifetime is the subtle part.** `widget.tsx` splits the payload in two: `stable` holds only PLAIN data (proof text, comments, `tacticEdits`) and updates just when the proof text changes, so layout/fold state survives cursor moves; the ref-carrying `taggedGoals`/`tokenInfos` live in a separate `interactive` state tracking the LATEST successful in-proof response. They must not be pinned to `stable`: a `WithRpcRef` is only resolvable in the RPC session that issued it, and a session dies on a worker crash/exit, an `RpcNeedsReconnect`, a server restart or the file closing — after which the client silently opens a new one whose store knows nothing of the old ids. Pinning them meant rendering one arbitrarily old response's refs forever, so after any reconnect every popup failed with `RPC reference 'N' is not valid` and only editing the proof could recover it (`tokenInfos` made it far more visible — one ref per identifier token instead of per goal). Refreshing per response is what makes it self-heal, and a rejected call clears them outright. The update is identity-compared against the response object so `useAsyncPersistent`'s hold-previous-value-while-loading can't loop; responses with no steps (cursor outside the proof) deliberately don't clear it, so tooltips survive a trip outside the proof.

**The widget's RPC path mirrors the CLI's harvest.** `lean/ProofTreeWidget.lean`'s `getProofTree` is `Paperproof.getSnapshotData` (`.tree` mode) minus the single-tactic branch: `withWaitFindSnapAtPos` → `BetterParser_Tree fileMap snap.infoTree` → `{steps, allGoals, taggedGoals}`. No `uri` field is needed: the panel widget already gets it in `props.pos`. The **same v4.27.0 async-tactic caveat applies** — the live server must have fully elaborated the proof for `snap.infoTree` to contain `TacticInfo`; an empty parse returns an empty proof (`steps := []`), which the widget renders as "no proof here" — the not-in-a-proof state is data, not an error-message string for the client to pattern-match.

**Tactic labels are syntax-coloured from the server's own semantic tokens (widget only).** `ProofTreeWidget.lean` runs the very pair the editor's `textDocument/semanticTokens` request uses — `FileWorker.collectSyntaxBasedSemanticTokens fileMap snap.stx` (keywords/syntactic categories) ++ `collectInfoBasedSemanticTokens snap.infoTree` (identifiers classified by what they elaborated to), through `computeAbsoluteLspSemanticTokens` and `handleOverlappingSemanticTokens` — so a token means here exactly what it means in the editor, with no Lean lexer reimplemented in JS. **The server's own token pass misses constants, and that had to be filled in.** `collectInfoBasedSemanticTokens` emits tokens ONLY for identifiers bound to local `fvar`s and for field projections — a constant (`Nat.Prime`, `Nat.strong_induction_on`, `Nat.add_zero`) gets nothing, because the editor colours those from its TextMate grammar rather than from semantic tokens. We have no TextMate grammar, and the token list is also what carries the hover popups, so every constant in every tactic silently had neither colour nor tooltip. `collectConstIdentTokens` (ProofTreeWidget.lean) fills the gap from the info tree, mirroring upstream's shape (`deepestNodes`, an `.original` head so macro-generated syntax is skipped, `.getAppFn.isConst` because an ident usually elaborates to the constant already applied to its implicits) and leaving conflicts to `handleOverlappingSemanticTokens`. All three collectors are merged in one place, `semanticTokensFor`. They ride the EXISTING `TacticEdit` (`tokens : Array TacticToken`, absolute LSP positions), because the tokens index into the same verbatim `text` that entry already carries. JS-side `web/src/tacticTokens.tsx` (no infoview imports; it is plain colouring) turns them into one ReactNode per wrapped line and feeds `ProofTreeView`'s new `renderTaggedTactic` hook, which reuses the *same* `<foreignObject>` render branch as the goal tagged labels. Two invariants: **colour only, never geometry** (tokens change `color`, never the text, so the measured boxes stay honest), and **the line-offset match is the guard** — `lineOffsets(text, lines, prefix: true)` returns null unless the wrapped label lines are a prefix of `text`, and any mismatch falls back to plain SVG text. Prefix, not exact (goals use exact): Paperproof prettifies a structured tactic to its FIRST LINE, so `induction n with` is a genuine prefix of a source range running to the end of the `with` block — an exact test would have switched colouring off for precisely the interesting tactics. **Known gap**: the guard still fails for 12 of `sample.ndjson`'s 86 tactics, all `rw [...]` and multi-binder `intro`, which render entirely plain (no colour, no popups). Paperproof splits `rw [a, b]` into one step per rewrite whose `position` points at the RULE (`List.prod_append,`) while re-synthesising `tacticString` as `rw [List.prod_append]` — so there the source text is a substring of the label rather than the label being a prefix of the source, the opposite alignment. Supporting it means matching both directions and offsetting token spans by where the source text sits inside the label.

**Diagnosing the Lean half offline.** The RPC handler needs a live server, but the pieces below it don't: a scratch file that runs `Lean.Elab.IO.processCommands` over a **core-only** source (Mathlib needs `enableInitializersExecution` + `supportInterpreter`, which `lake env lean --run` can't give you) yields real `InfoTree`s, and `mkHoverIndex` / `semanticTokensFor` can then be exercised directly. Two sweeps found real bugs that reading could not: comparing `HoverIndex.innermost` against upstream's `InfoTree.hoverableInfoAtM?` at EVERY byte offset (0 disagreements over 1700 — which is how the hover index was cleared of suspicion), and dumping every emitted token with the info node it resolves to, which is what exposed constants having no token at all. Those helpers are deliberately not `private` so a probe can import them. Token colours are hardcoded to VS Code's default LIGHT palette rather than the `--vscode-symbolIcon-*` theme variables, because node fills are fixed light pastels: theme-following colours would go light-on-light and vanish in dark themes.

**Per-token hover popups on tactics (widget only)** ride the same token pass. `ProofTreeWidget.lean` ships `tokenInfos : Array TacticTokenInfo` — per token a `Widget.CodeWithInfos` that is one `.tag` wrapping the token's **source text**, carrying the `InfoWithCtx` the editor's own hover would use. EVERY token is offered, not just identifiers: `hoverEligible` mirrors the eligibility test inside `InfoTree.hoverableInfoAt?` (anything with elaborator info, plus field/option/error-name nodes, minus the `nullKind`/`withAnnotateState` steering nodes), so a tactic keyword resolves to its `TacticInfo` — and since `makePopup` ends with `doc := ← i.info.docString?`, which is populated for ANY info kind, that yields the tactic's own documentation. Restricting this to naming tokens was a mistake: the reference text on `induction` or `Nat.Prime` is exactly what makes the widget a substitute for reading the source rather than a summary of it. Tokens with no info node (punctuation, most syntactic keywords) find nothing and cost nothing. That shape is the whole trick: `InteractiveCode` resolves the tag through `Lean.Widget.InteractiveDiagnostics.infoToInteractive` — the same RPC behind the goal-label tooltips and the editor's hover — so the popup is native, and because the tagged text is the SOURCE text rather than a pretty-printed expression, what is drawn is byte-identical to what the layout measured. Cost is controlled two ways, since the token set is now broad. The tree is walked ONCE per request into a `HoverIndex` (items sorted by start, plus a prefix-max-of-stop array) shared by every token — calling `InfoTree.hoverableInfoAt?` per token would re-walk the whole tree on every cursor move — and `innermost` binary-searches then scans backwards, stopping the moment the running max stop falls at or before the query offset, since no earlier item can contain it. And one RPC reference is allocated per distinct info NODE, not per token: a tactic's keyword and punctuation all resolve to the same `TacticInfo`, and `rpcStoreRef` keys on the `WithRpcRef` id, so sharing the value keeps them one store entry (and lets the client reuse UI state for it). There is deliberately NO cross-request cache — the dominant per-call costs are `BetterParser_Tree` and `collectTaggedGoals` (which pretty-prints every goal), both of which predate this; caching the whole payload on `(uri, version, command)` is the real lever if latency ever shows up, and wants measurement first. Note `WithRpcRef.mk`, not `⟨_⟩` — the constructor is private. JS-side `tacticTokens.tsx` renders a token interactively only when `flattenTaggedText(code)` equals the slice being drawn (the same equality guard as goals; it fails for a token straddling a wrap, which then renders as plain coloured text — tooltip lost, geometry intact), which makes `tacticTokens.tsx` the SECOND module allowed to import infoview APIs alongside `taggedRender.tsx` (whose `ensureTaggedStyle` it shares for the `.ptw-tagged` font normalisation). `tokenInfos` is excluded from the stable-proof signature for the same reason as `taggedGoals`: the refs are freshly allocated every call.

**`tokenInfos` is a FLAT list keyed by absolute token position, and must stay that way.** The client indexes it once, globally, and every tactic looks its own tokens up by position. Splitting it per tactic by "which tactic's range contains this token" is wrong and was the bug that made popups look broken for `exact`, `Nat.Prime` and most others: tactic ranges NEST — a structured `induction`/`have` contains every tactic in its branches — so containment resolves to an ancestor, not the owner, and the owner then renders no popups at all. Measured over `sample.ndjson`, 53 of 86 tactics lost their tokens to an enclosing tactic. The same nesting means the server emits a token once per *containing* tactic, so `getProofTree` dedupes `tokenInfos` by position (`seenTok`) while each `TacticEdit.tokens` list stays complete, since colouring is per tactic.

**Hovering a tactic lights up its source range (widget only).** The hover-weight sibling of click-to-reveal: `ProofTreeView.onHoverTactic(pos | null)` reports raw enter/leave, `widget.tsx` debounces it (`HOVER_DWELL_MS`, so sweeping the pointer across the tree sends nothing) and relays `highlight`/`clear` actions through the companion, which paints a `TextEditorDecorationType` (`editor.wordHighlightBackground`) on every visible editor for the uri. Deliberately NOT reveal: reveal moves the cursor and steals focus, which would make hovering unusable. These two actions are the only chatty traffic on the relay, so the companion's log skips them.

**Source comments render in the tree.** Comments are parser trivia — never in the `InfoTree` — so both data paths re-lex the *raw source* of just the proof's command through the shared `lean/ProofTreeComments.lean` (its own `lean_lib`; handles `--`, nested `/- -/`, strings, char literals) and ship `comments: [{text, start, stop}]` on the wire (CLI: extra field in `resultToJson`, range from a `commandRange` fold over the InfoTree; widget: `snap.stx.getRange?`, and the field rides the stable-proof signature). The range is extended to its final line's end because a syntax range's stop excludes trailing trivia — exactly where a last-line trailing comment lives. The theorem's docstring falls inside the command range **deliberately**. Attribution is JS-side and source-agnostic (`attributeComments` in proofToTree.ts), built around one quirk: **Paperproof step ranges include trailing trivia**, so range-containment IS the trailing-comment test (`simp -- c` puts the comment inside `simp`'s range). Rules in order: contained in a step → that step (innermost; unless another step starts between comment and container end — then it's that inner step's leading comment); entirely before the first tactic (incl. the docstring) → the ROOT goal ("the plan" slot); else next step by start; else the previous step. The same trivia quirk means tactic labels can carry their trailing comments verbatim — `cleanLabel` scrubs every comment's exact text out of them. Rendering: an italic, muted, box-less strip at the very TOP of the node's band (comment → box, mirroring source order): `commentSize` in layout.ts wraps it via the shared wrapper *measured italic* (italics are wider) at `COMMENT_FONT_PX`, `commentBlockH` joins the band and `commentW` the effective width in both layout modes. In compact mode a parented node's strip hangs INDENTED off the incoming connector (`COMMENT_INDENT`, git-graph style): the straight trunk lane runs continuously past the comment down to the node's box, so the strip annotates the lane instead of interrupting it — root comments (no incoming lane) stay flush-left, and wide mode keeps centered strips. `proofs/commented.lean` exercises every rule. Related: the view's fold/zoom reset and auto-centering key on the proof's SHAPE (its step goal ids), not proof identity, so editing a comment (or a tactic's text) live in the widget re-measures geometry without resetting fold state or scroll.

**Controls are a floating icon rail, not a top bar.** All view controls live in a vertical icon-button column at top-right (`ControlRail` in ProofTreeView.tsx: ⊞⊟ expand/collapse, ⇅ accordion, ≡ compact, ∀ full hyps, ⇝ sequence, ◎ exit focus when focused, +−⛶ zoom/fit) — deliberately NO top bar, so the eye falls straight from the infoview's expected-types block onto the tree; words live in tooltips, toggles get pressed styling; rail/action-bar chrome is styled on the editor's own widget palette (`--vscode-editorWidget-background/-border`, `--vscode-icon-foreground`, `--vscode-toolbar-hoverBackground`) with light fallbacks for the standalone app, and corners are VS Code-tight (rail 3px, tactic boxes 4px vs goals 6px — a pill-round tactic read as a label, not an editable box). `headerExtra` (the standalone app's proof picker) and the sequence-hint pill float at top-left. The whole scroll container is `user-select: none` — the tree is a diagram driven by click/double-click/drag, and a stray selection fights all three (that is how the ⇧ gesture broke); the in-place editor's textarea opts back in with `user-select: text`, and the infoview's hover popups are portalled to `document.body` so they're unaffected. Because floaters overlay the content, a short (26px) **headroom veil** (a `pointer-events: none` gradient strip from the editor background to transparent) fades scrolled content out under them instead of letting it collide — kept deliberately shallow so nodes stay crisp as high as possible (the veil is absolute/zero-layout, so its height is pure fade distance, not reserved space). Wheel handling: zoom is `exp(-deltaY * 0.008)` (browser-page feel); plain scrolling has a **vertical gesture lock** — a wheel gesture that starts vertical stays vertical (manual `scrollTop` with `preventDefault`; a ≥180ms idle gap starts a new gesture), while horizontal scrolling is unrestricted — because the compact layout is read by vertical scrolling and trackpad drift would walk it sideways.

`web/src/makeTree.ts` is a seeded synthetic-tree generator for layout experiments, independent of real proof data.
