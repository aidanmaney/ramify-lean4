# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Lean 4 proof rendered as an interactive tree. The renderer has **two data sources** feeding the same React/d3-dag view:

```
# 1. Offline CLI (dev harness):
proofs/*.lean ──ppharness (Lean CLI)──▶ NDJSON ──proofToTree (web)──▶ d3-dag tree

# 2. Live infoview widget (production target):
cursor pos ──ProofTree.getProofTree RPC──▶ Proof ──proofToTree (web)──▶ d3-dag tree
```

- `lean/` — **ppharness**, a thin owned wrapper around Paperproof's `BetterParser_Tree`. Elaborates a `.lean` file to completion and harvests the elaborator's `InfoTree`s into proof steps, emitting one NDJSON line per proof.
- `lean/ProofTreeWidget.lean` — the **infoview user-widget**: `@[server_rpc_method] ProofTree.getProofTree` runs the *same* `BetterParser_Tree` over the live server's `snap.infoTree`, and `@[widget_module] ProofTreeWidget` (`Component PanelWidgetProps`) `include_str`s the bundled renderer. It is the RPC counterpart of ppharness — no CLI, no NDJSON.
- `web/` — React + Vite + d3-dag renderer that draws goals as boxes, tactics as edge-nodes, hypotheses on edges. `ProofTreeView.tsx` is the shared, source-agnostic view; `App.tsx` feeds it a proof from NDJSON, `widget.tsx` feeds it a proof over RPC.
- `gen.sh` — the CLI seam: runs the parser over `proofs/*.lean` and writes `web/public/sample.ndjson`.
- `ext/proof-tree-companion/` — a small VS Code **companion extension** for widget gestures the infoview API can't express (see "Popout editing"); dev-installed via symlink, no build step.

## Commands

**Lean** (run from `lean/`):
```bash
cd lean && lake exe cache get && lake build   # fetch Mathlib oleans, build — RE-RUN cache get after any `lake clean` (it deletes the oleans; without them an `import Mathlib` file makes the editor compile Mathlib from source for hours)
lake build ppharness                          # rebuild the CLI
echo 'theorem t : True := by trivial' | lake env lake exe ppharness   # parse stdin
lake env lake exe ppharness FILE.lean         # parse a file (lake env puts Mathlib on LEAN_PATH)
```

**Regenerate web data** (from repo root) — do this after editing anything in `proofs/`:
```bash
./gen.sh                                       # proofs/*.lean → web/public/sample.ndjson
```
Do not hand-edit `web/public/sample.ndjson`; it is generated.

**Web** (run from `web/`):
```bash
npm install
npm run dev          # Vite dev server (standalone app, reads sample.ndjson)
npm run build        # tsc -b && vite build (standalone app → dist-app/)
npm run build:widget # esbuild src/widget.tsx → dist/proofTreeWidget.js (the infoview bundle)
npm run typecheck    # tsc -b only (covers widget.tsx too)
npm run lint         # eslint .
```
There is no test runner configured in either half; "verify" means build + run the dev server and inspect the rendered tree.

The two builds have deliberately **separate output dirs** (`vite.config.ts` sets `outDir: 'dist-app'`): vite empties its outDir on every build, so sharing `dist/` would make `npm run build` silently delete `dist/proofTreeWidget.js` — the Lean build input — and break the next `lake build` / editor `setup-file` with "no such file or directory". Both dirs are gitignored artifacts.

**Infoview widget** — the bundle is a Lean build input via `include_str`, so build it *before* `lake build`:
```bash
cd web && npm run build:widget      # produces web/dist/proofTreeWidget.js (gitignored artifact)
cd ../lean && lake build ProofTreeWidget
```
Then open a file in *this* Lake project with `import ProofTreeWidget` and `show_panel_widgets [ProofTreeWidget]` (see `lean/ProofTreeDemo.lean`, which is core-only so it needs no Mathlib). The panel follows the cursor. `lean/ProofTreeTour.lean` is the guided walkthrough — six theorems, one feature cluster each (reading, layout gestures, editing, calc, the frontier chips, the error ribbon), with a docstring per section saying what to try; its last two sections are deliberately unfinished, so like the other demo fixtures it does not compile and is not a Lake target. Its claims were verified over the live server path (the LSP-probe recipe): the frontier's two goals both carry `+`/`calc` chips (`<, ≤, =` offered on the order goal), its `unsolved goals` is chip-covered and drawn 0, and the failed `rw` resolves to its recovered dashed node with the error on it. `lean/ProofTreeExercises.lean` is the tour's WORKBOOK — five goals to prove from the tree, each seeded with one honest opening move so its remaining goals sit at the frontier with chips, hints in the docstrings, solutions in a comment block at the bottom. Two invariants keep it honest, both verified: the exercises file elaborates with exactly five `unsolved goals` and nothing else, and the printed solutions are extracted from the comment block VERBATIM and elaborated (that sweep is what caught `Nat.pos_pow_of_pos` not existing — the core name is `Nat.two_pow_pos`); probed over the live wire, every seed's pending goals carry `+`/`calc` chips and every `unsolved goals` is chip-covered. Difficulty is tuned so `omega` alone can't one-shot any of them — each needs one idea first (a witness, an antisymmetry split, a positivity `have`); ex 5's seed enters the `succ` branch via `with | succ k ih =>` deliberately, because a bare `induction n` leaves the case variables INACCESSIBLE (`n✝`) and a chips-only flow can then never name them in a `have`. `lean/ProofTreeGoals.lean` is the harder sibling at Natural Number Game difficulty: six STATEMENTS only — no seeds, no solutions in the file — each proof a lone `sorry` the reader replaces by double-clicking its node (a `sorry` is an ordinary editable tactic, which is what makes goals-only files workable at all: a bare `by skip` harvests ZERO steps — `getGoalsChange` cancels a no-op's goals — so the widget would show "no proof here", while `by sorry` draws root + stub; measured on the wire, `steps: ['sorry']` with a live `tacticEdits` entry). Solvability is verified against the NNG vocabulary strictly — a solutions twin using only `rfl`/`rw`/`induction`/`intro`/`exact`/`apply`/`cases` (no omega, no simp, no decide) compiles clean, with each proof matching its docstring's hinted shape — and the file itself compiles with exactly six `sorry` warnings and nothing else.

`lean/lakefile.toml` declares `web/dist/proofTreeWidget.js` as a Lake `input_file` and wires it into `ProofTreeWidget`'s library via `needs`, so the two commands above actually compose correctly. Without this, `lake build` is a **silent no-op** when only the JS changed: `include_str` is a bare `IO.FS.readFile` at elaboration time, invisible to Lake's dependency graph, so Lake sees `ProofTreeWidget.lean`'s own source as unchanged and reuses the stale `.olean` — hit this for real once, spent a while confirming via `.olean` mtimes and `strings`-grepping the compiled output. **Use `needs`, not the deprecated `extraDepTargets`** — the latter parses and resolves target names fine (a bogus name does error) but empirically does not propagate a changed file's hash into the rebuild trace; `needs` does (confirmed with a real edit → rebuild → `lake build` cycle, checking the compiled `.olean`'s bytes, not just exit status).

## Critical constraints

- **Toolchain is pinned to Lean v4.27.0 on purpose** (`lean/lean-toolchain`, `lean/lakefile.toml`). ppharness drives the frontend with `IO.processCommands` then reads `infoState.trees`. On v4.29+ tactic subtrees elaborate **asynchronously** and aren't attached when read, so `BetterParser_Tree` walks a tree with zero `TacticInfo` nodes and returns empty proofs (`{steps:[], allGoals:[]}`). Keep ppharness and Mathlib on the same v4.27.0. Do not bump without re-validating the harvest path.
- **Mathlib is a build dep only so its oleans land on `LEAN_PATH`** (via `lake env`); that's what lets real `import Mathlib` proofs elaborate at parse time. The Paperproof library itself is core-only.
- `Main.lean` calls `enableInitializersExecution` before the first import and the CLI is built with `supportInterpreter = true`, because importing Mathlib runs its `@[init]` declarations through the interpreter. Both are required; removing either breaks `import Mathlib` sources at runtime.

## Architecture notes that span files

**The wire format is a cross-language contract.** Paperproof's `ProofStep` / `GoalInfo` / `Hypothesis` structs (`lean/.lake/packages/Paperproof/lean/Services/BetterParser.lean`) are mirrored field-for-field in `web/src/paperproof.ts`. ppharness (`lean/Ppharness.lean`) only hand-serializes `Result` (which lacks a derived `ToJson`); everything else rides upstream's derived instances. Changing a field on either side requires changing the other. `BetterParser.annotated.lean` at the repo root is a study copy of the upstream parser annotated for this project (not part of the build).

**How a proof becomes a tree.** The renderer never consumes `paperproof.ts` types directly. `web/src/proofToTree.ts` adapts a `Proof` into `TreeNode[]`: each tactic `step` becomes `goalBefore ──(tactic node)──▶ goalsAfter ++ spawnedGoals`. The tree root is the goal consumed by some tactic but produced by none (`rootIds`). A goal's **local context rides the goal node itself** (`TreeNode.hyps`) and is drawn INSIDE its box, stacked above the `⊢ ` line — the infoview's own hyps-then-turnstile reading, so a goal and the assumptions it holds under are one thing to look at. (It used to be a separate label floating on the goal→tactic edge; merging it killed a whole tier of boxes, connector stubs and band arithmetic, and gave leaf goals — which have no outgoing edge — a context for the first time.) Each line is flagged `used` from the CONSUMING tactic's `tacticDependsOn` (rendered as a `▸` gutter marker + full ink, unused lines recede; fvarIds match `Hypothesis.id`; a leaf goal has no consumer, so nothing is flagged). A context has FOUR breadths, cycled by one rail button (`HYP_MODES`, glyph shows the current mode since four states can't be read off a pressed style): **`delta`** (glyph `Δ`) is what the goal gained over the goal its own producing step consumed (root goals: their binders) **plus any older hyps the consuming tactic uses**; **`full`** (`∀`) is the whole context, additive down the tree; **`used`** (default, `▸`) is what the REST OF THE PROOF under this goal actually depends on — the union of `tacticDependsOn` over every step in the goal's SUBTREE (`subtreeUsed`, a memoized DFS in proofToTree), not just its immediate consumer. **No counterfactual re-elaboration is needed for that to be honest about `omega`/`linarith`/`simp_all`**: Paperproof computes `tacticDependsOn` from the elaborated PROOF TERM (`findHypsUsedByTactic` — the mvar assignment's fvars, the upstream comment says outright "it wouldn't work for linarith etc" if it read syntax), so implicit uses count; the known blind spots, accepted as data, are `decide`-style proofs (the term goes through `of_decide_eq_true` and mentions no hyp fvars) and delayed-assigned goals (upstream reads only `eAssignment`). **fvarIds are NOT stable down the tree** — `rw … at h` / `simp at h` mint a NEW fvarId for `h` in the child goal, so a descendant's dependency can arrive under an id the ancestor's context never held — so the walk carries `(fvarId, username)` pairs (the name resolved in the reporting step's own `goalBefore`, where the id is guaranteed live) and `contextFor` matches id-first with a username FALLBACK for ids the goal doesn't know; measured over the corpus the fallback fires exactly twice, both genuine (factorization's `hk`, re-minted by `simp at hk` and then consumed by an `omega` that never names it — also the proof that implicit uses land). The fallback's known false positive — a descendant binding that SHADOWS an ancestor name — did not occur in the corpus. **`new`** (`↓`) is only what the PRODUCING tactic introduced as a binding — the fvarIds present here but absent from the producer's `goalBefore` (`intro h`, `obtain ⟨a, ha⟩`, `induction … with | succ k ih`, `have h :=`), with none of `delta`'s "plus used older" augmentation. `new` is what the tactic ABOVE bound, `used` what the subtree BELOW mentions — incomparable; the IMMEDIATE-consumer set (still the ▸ gutter flag, below) is ⊆ `used` ⊆ `full`, while `delta` contains `new` plus only the immediate part of `used`, so `used ⊄ delta` any more (a hyp used only deep in the subtree is `used`-shown but `delta`-hidden). **A goal with NO consuming tactic falls back to `delta`'s rule under `used`, and that carve-out is what makes the mode safe as the DEFAULT.** "What the rest of the proof uses" is undefined when there is no rest of the proof yet — and an unconsumed goal is precisely the live FRONTIER, the one being written against, where an empty box reads as broken rather than as data. Measured over the corpus, exactly 2 goals are unconsumed and they hold 25 context lines between them (all of which the un-fallen-back mode dropped); with the fallback, 0 goals render empty under `▸` that would have shown lines under `Δ`, and both leaves' output is byte-identical to `Δ`'s — the bar being "no worse than what that goal showed before this became the default". `new` can still legitimately come back EMPTY, showing the `⊢ ` line alone: on a ROOT goal (no preceding tactic — even the theorem's own binders are the signature's, not a tactic's) or on a goal produced by a non-binding tactic (`rw`, `exact`); that is data, not a rendering gap. The `▸` gutter flag stays IMMEDIATE-consumer in every mode — in `used` mode it now carries information rather than being vacuous (marked = the very next tactic uses it, unmarked = only something deeper does); the marker and its reserved width are still dropped whenever the flags don't SEPARATE anything (all-used or none-used) — a rule stated once but enforced in two places that must agree, `sizeOf`'s reservation and `HypBlock`'s `anyUsed`. Measured across the corpus (143 goals, flag files excluded): 129 / 457 / 373 / 895 context lines for new / used / delta / full, with immediate-used at 303; immediate ⊆ subtree-used ⊆ full verified per goal (0 violations, engine output byte-checked against an independent replication). `proofToTree`'s own `hypMode` default is `used` too, so the module and the rail cannot drift. Switching rebuilds the engine with `proofToTree(proof, { hypMode })` — node ids are unchanged, so fold/zoom/sequence state deliberately survives the toggle (the view resets those on a new *proof*, not a new engine). Goal labels carry a `⊢ ` prefix (`TURNSTILE` in proofToTree.ts — the infoview's own goal convention); it's part of the measured label, and the tagged renderer strips it before its text-equality match then re-attaches it as plain text (renderTaggedGoal), so keep the two in sync. Nodes are emitted in DFS preorder so layout ordering reads top-down/left-to-right.

**The layout engine is the heart of the web side** (`web/src/layout.ts`). `createLayoutEngine(data)` builds an engine bound to one tree; folding and relayout are pure functions of `data`. Key design choices:
- **Two layout modes behind one output shape.** `computeLayout(collapsed, only?, focus?, compact?)` returns `PlacedNode`/`PlacedLink` (types.ts) from either positioner, so the renderer is layout-agnostic. The **compact trunk outline** (default; the control rail's ⋔ toggle selects the OTHER one) is a hand-rolled DFS with a global y-cursor and per-branch x-indent — written precisely because Sugiyama forces same-depth nodes into one vertical band: every node gets its own vertical slot (read by scrolling), left edges align per indent, a branching tactic's children are laid out **top-to-bottom in SOURCE order** (`srcRank`), the last resuming the trunk while earlier ones branch right by `TRUNK_INDENT` and sit above it, so branches stay local to their tactic. Source order must be COMPUTED, not taken from Paperproof's child order (main continuation first): for `have … := by` the two coincide, but for a real case split they are backwards — `by_cases` lists `pos` then `neg`, so the old "first child on the trunk" rule drew the `neg` branch ABOVE `pos` and walking the cursor up the buffer jumped between branches. `srcRank` is the earliest source position in a node's whole SUBTREE, not its own: a goal carries its PRODUCER's position, so every child of one tactic reports the same position and sorting on that is a no-op. Measured over `proofs/`: 0 backward jumps in compact vertical order across all 7 proofs (was 1 in euclid). The wide mode can't put source order on the vertical axis (that axis is depth), but `ORD` — the `stableDecross` key — is assigned from `srcRank` too, so siblings there read left-to-right in source order (0 inversions measured). Connectors are orthogonal │└ elbows dropped from `TRUNK_INSET` inside the parent's left edge — bare lines, deliberately NO arrowheads (flow reads consistently down/right; triangles were noise poking into boxes); overlap-freedom is by construction (exclusive y ranges). The **wide mode** is the original Sugiyama tree (its d3-dag output is normalized into the same placed shape). Fold/accordion/focus/sequence ride the shared visibility sweep, so they work identically in both modes; the view re-centers on a mode toggle (mode is part of `viewKey`) — compact pins the content's left edge near the viewport edge (`COMPACT_LEFT`, a tight inset, not the full `MARGIN.left`), wide centers the root.
- **Stable sibling order under folding** (wide mode): a custom `stableDecross` sorts each Sugiyama layer by a fixed creation-order key (`ORD`) instead of minimizing crossings, so collapsing one subtree never reshuffles unrelated siblings. (The trunk mode is order-stable trivially — it never reorders anything.)
- **Box sizing uses canvas `measureText` in the exact render font**, not char counts — Lean labels are full of wide unicode (ℕ ∀ ∃). Text is pixel-wrapped to a ~100-column width budget so it's always bounded by its box; breaks prefer semantic seams (after `,`/`;`, or before a connective so the continuation STARTS with it — two tiers via `seamRank`: clause boundaries `→ ↔ ∧ ∨ ⊢` beat relations `= ≤ ∣ …`, so `(2 ≤ n → …)` never splits at the `≤` when an `∧` seam is nearby; greedy word break when no seam is usable). Width-wrapped continuation lines carry `WrappedLine.cont` and hang-indent by `CONT_INDENT` in both the measurer and the render (tspan x / tagged line paddingLeft); explicit `\n` lines are NOT continuations. `proofs/wrap.lean` is a deliberately over-long statement that exercises this. The render must match: node/hyp `<text>` set `letterSpacing: 0` (the page CSS sets a nonzero default that canvas wouldn't otherwise account for), and geometry constants (`LINE_H`, `HYP_GAP`, `NODE_PAD`, …) are exported and shared between layout and render. The code-text FAMILY follows the EDITOR's font: `getCodeFontFamily()` (layout.ts) resolves `--vscode-editor-font-family` — the CSS variable the infoview's own `.font-code` uses, present on the webview root — falling back to `monospace` when absent (standalone app, headless). Measurer and every code-text render site share it (UI chrome stays monospace); sizes stay ours (`NODE_FONT_PX` etc.), only the family follows the editor. It follows LIVE: VS Code does **not** reload the webview on a font change — it rewrites the CSS variables on the root element's `style` attribute in place — so `ProofTreeView` watches that attribute with a MutationObserver (the infoview's own components do the same) and calls `refreshCodeFontFamily()`, which clears the width cache on change; the view keys its engine memo on the family so all geometry is re-measured (fold state survives — reset is keyed on the *proof*).
- **A goal's context block is measured as part of its box** (`sizeOf(label, hyps)` → `LayoutNode.hypH`): the box's text stack is the context lines (at `HYP_FONT_PX`/`HYP_LINE_H`, plus `HYP_GAP`) then the label lines, and the box's width is the wider of the two blocks. Context lines are deliberately NOT pixel-wrapped — the box grows to fit them — because a mid-line break would destroy the exact `name : type` string the widget's tagged renderer matches on; only the label half is capped at `MAX_W`. A node's layout band is therefore just comment strip + box, with the box pinned at the bottom, plus a constant layer gap; edges leave a box's bottom and land above the target's whole band.
- `computeLayout(collapsed, only?, focus?)` hides a node iff all its parents are collapsed/hidden (fixpoint sweep). The optional `only` set restricts layout to exactly those ids — used by the "sequence/linearize" feature (`pathBetween` walks single parents to get the ancestor→descendant path; with no branches, Sugiyama renders one column). The optional `focus` set (from `subtreeIds`, a goal's ◎ hover-bar button or ⌥-click in the view) scopes the world to one subtree *without* suspending the fold rule: the sweep ignores out-of-scope nodes, so the focus root lays out as a root and folding keeps working inside (fold state is shared with the full view on purpose).

**Data source is swappable by design — and both sources now exist.** The shared view is `ProofTreeView.tsx` (layout, folding, zoom/scroll, SVG render); it takes one `Proof` and nothing else. Two thin shells feed it: `App.tsx` `fetch`es `SAMPLE_URL` (`sample.ndjson`); `widget.tsx` calls `ProofTree.getProofTree` over RPC inside the infoview. `proofToTree` / `layout.ts` / `ProofTreeView.tsx` are source-agnostic — do not import NDJSON or infoview APIs there.

**The node↔source link (widget only).** `ProofStep.position` (a tactic's LSP range, already on the wire) is the sole source of truth for every node's position — no vendored parser change needed. `proofToTree.ts` sets it three ways: a **tactic** node gets its own step's `position`; a **goal** node gets the `position` of the step that *produced* it (`producingPosition`, keyed by `stepGoalsAfter`) — root goals get none, since they're the theorem statement, not a tactic's output; context lines need no position of their own any more — they live in the goal's box, and that goal's `position` is already the introducing step's.

`ProofTreeView` uses these two ways when the widget supplies the hooks: **tree→source** — clicking a positioned tactic node (whole box) calls `onReveal`; goals stay fold-on-click (their primary interaction), so their secondary actions ride two complementary surfaces: a **hover action bar** (`NodeActionBar`, a pill of real button-sized targets straddling the box's top-right corner, rendered inside the node's `<g>` so box→bar pointer travel can't un-hover it) with `»` reveal and `◎` focus-subtree buttons, and **modifier fast paths on the whole box** — ⌘/Ctrl-click reveals (the editor's own go-to-source gesture), ⌥-click focuses. `onReveal` maps in `widget.tsx` to the companion's `reveal` action (`ProofTree.popoutEdit` RPC with `action: "reveal"`), NOT `ec.revealLocation`: vscode-lean4's reveal always picks the FIRST visible editor for the uri (the main buffer), while the companion targets the lens when one is open — so a node click retargets the lens, whose cursor move flows back as `highlightPos`, closing the tree↔lens loop (without the companion installed, reveal is inert); **source→tree** — `highlightPos` (the editor cursor from `PanelWidgetProps.pos`) accent-outlines exactly ONE node: the innermost (smallest-span) TACTIC whose range contains the cursor (`cursorNodeId`). It must be one, not "whatever contains it": recorded ranges overlap by construction — goals carry their PRODUCER's range, structured tactics (`induction`/`have`) contain everything nested inside, and Paperproof ranges include trailing trivia — so naive containment lights up half a branch. **Two things make the pick land on the node you clicked, and they are only correct together** (measured over `sample.ndjson`'s 86 tactics by simulating the accent lookup for every one): `positionContains` is HALF-OPEN `[start, stop)`, because trivia-inflated ranges make a tactic's `stop` equal its successor's `start`, so an inclusive end lets the neighbour match and the smallest-span tie-break silently prefers whichever is shorter; and the companion leaves the CURSOR at the range's **start**, never its end, because a range's end sits either in the next tactic or (for a structured tactic) deep inside its last nested one. Cursor-at-end + inclusive = 17/86 wrong; cursor-at-start + inclusive = 31/86 wrong; cursor-at-end + half-open = 53/86 wrong and 33 with no accent at all; cursor-at-start + half-open = 0 wrong, 0 missing. Fixing only one of the two makes it worse than the bug. Goals never take the cursor accent (their spans are the producer's, always redundant with its node). **Parts of a proof belong to NO tactic's range**, and containment alone escalated them to the enclosing construct: a structured tactic's range stops at its first case marker (`induction n … with` is `23:4 → 24:4`, ending exactly ON the `|`), and a bullet `·` sits just past the range of the tactic before it — so `| _ n ih =>` resolved all the way up to the `have … := by` at the top of the proof. `tacticNodeAt` (proofToTree.ts, shared with the offline probe so the two can't drift) therefore takes the innermost containing tactic and then prefers the nearest tactic that has already CLOSED at or before the cursor from strictly inside it: on a case marker that is the `induction` the marker belongs to, on a bullet the tactic that split the goal. Inside a leaf tactic no such candidate exists, so the measured property above — cursor at a tactic's own start resolves to that tactic — is untouched (re-measured: 86/86, 0 wrong, 0 missing). **But that CLOSED-before rule fires far beyond the gaps it was written for, and on its own it makes the accent lag the cursor by a line.** A `calc` link's term text, a bullet, and a commented-out line all belong to no tactic's range, so the rule reaches back to the previous tactic: measured on the scratch file's `calc_workout`, a cursor on `_ ≤ _ := by linarith` accented the PREVIOUS link's `ring`, a cursor on the `calc` head accented the `have` above it, and a cursor on chain 2's last link accented the NEXT bullet's `calc`. That reads as latency rather than as a wrong answer — you move down a line and the accent shows where you just were — which is why it was reported as "slow and inconsistent" rather than as an off-by-one. So a tactic that STARTS on the cursor's own line now wins outright, before either of the other rules; the cursor may sit before it on the line (`= 2 * … := by ring` is mostly term text with `ring` at the end) and that still means "this line", so the first tactic on the line stands in. Measured over `sample.ndjson` plus the scratch file, sampling every 4th column of every line carrying exactly one tactic: **3014/3520 (85.6%) resolved to a tactic on that line before, 3520/3520 (100%) after**, with the cursor-at-own-start invariant holding at 262/262. Nothing about the accent is gated on the RPC — `highlightPos` is `props.pos` passed straight through and the tree stays rendered from `stable` while a fetch is in flight — so there was no latency to fix, only this. A cursor inside a COMMENT is resolved separately: comments are trivia sitting inside the enclosing structured tactic's range but owning none of their own, so the innermost rule yanked the accent up to the branch's `have`/`by_cases` and back down again. Instead a comment resolves to the node whose strip is SHOWING it, read straight off `TreeNode.commentRanges` (the attribution proofToTree already computed) rather than re-derived, so the accent can never drift from where the comment is drawn; a `--` comment's span is extended to end-of-line first, since the lexed range stops at the last character but the cursor naturally rests past it. The accented node is also TRACKED: when the cursor lands on a different node, the view scrolls it into view — only if it sits outside a comfortable viewport band, and never from scroll/zoom/fold alone (`trackedCursorNode`; a node hidden by folding is skipped, then tracked when an unfold reveals it). Vertical (the reading axis) centers the node in both modes; horizontally, wide mode centers it, but compact mode NEVER re-centers (that would pull the left-aligned trunk off screen) — it only nudges rightward when a node spills past the right edge, bringing its left edge to `COMPACT_LEFT` (eyeballed, no exact-center math). **The follow runs on OUR schedule, not the UA's** (`FOLLOW_MS`, 130ms, ease-out): `behavior: "smooth"` was the previous answer and its duration is fixed by the browser and tuned for page navigation, so a hop to the very next tactic cost the same as a jump across the proof, and walking the cursor down a proof left the tree visibly trailing — each cursor move restarting an animation the one before it had not finished. The in-flight animation is now held and CANCELLED by the next move, so a burst of cursor moves lands exactly where the final one alone would (verified: 5 rapid moves settle at the same scrollTop as that last position on its own). A jump longer than a viewport skips the animation entirely — you cannot track one that big by eye, so easing it only spends time. The rAF loop is backed by a `setTimeout` that snaps to the target, and that is not padding: **a hidden webview fires no animation frames at all** (measured in the preview — `document.hidden` true, 0 frames in 200ms), so without it the follow would simply never happen there. That also means the preview harness cannot time the eased path (no frames, and hidden-tab timer throttling puts `setTimeout` granularity around a second); what it does establish is that the follow lands on exactly the right scroll offset, through both the jump and the timer paths. Clicking the widget BACKGROUND dismisses the accent (clicks focus the infoview without moving the editor cursor, so it would otherwise linger); node clicks stopPropagation, and any real cursor move re-arms it. Both are inert in the standalone app (no `onReveal`/`highlightPos`). What's *not* recoverable this way is a hypothesis's exact identifier token (only the introducing tactic's whole range) and non-root goals having any span of their own (they're synthesized, not written) — closing that gap to token precision needs an additive `snap.infoTree` walk in our own `ProofTreeWidget.lean` (no vendored edit either), not a parser fork.

A node's native SVG `<title>` (hover tooltip) lists ONLY the actions available there (`· click to reveal in source`, `· double-click to edit`, `· ⌥-click to focus this subtree`), plus the `▸ = used by the tactic below` legend on a goal whose context has marks. It used to lead with the node's own un-wrapped text, which the box is already showing — noise that buried the one thing a tooltip is good for. A node with no actions (any tactic in the standalone app) gets no `<title>` at all. When the interactive tagged label (below) takes over a box, the `<title>` retreats to the box `<rect>` so it doesn't stack on the type tooltips.

**A `rw … at h` keeps its location clause, which the vendored parser drops.** Paperproof's `prettifySteps` matches `` `(tactic| rw [$_,*] $(_)?) `` and then RE-SYNTHESISES the label as `s!"rw [{rule}]"`, one step per rewrite rule — the matched location clause is never referenced again. So `rw [h] at hn` reached the tree labelled `rw [h]`, which is not a shortening but a DIFFERENT TACTIC: one rewrites the goal, the other a hypothesis, and the tree drew them identically (the boxes either side were already telling the truth — `hn : ¬Even n` above, `hn : Odd n` below — so only the label lied). `collectRwLocations` / `withRwLocation` (ProofTreeComments.lean, so BOTH wires ship it) put the clause back, and both wires apply it to every step the moment `BetterParser_Tree` returns, BEFORE anything else reads a label: tokens align against the label, brief mode collapses it, completion is keyed off it, so it has to be one string everywhere. Forking the vendored parser was the alternative and is the standing thing not to do here. The clause is found by SYNTAX over the same roots as `calcBlocks`/`tacticSlots` (all three now share `nodesOfKind`), and by KIND rather than by argument index — the index is `rwSeq`'s current shape, not a contract — taking only a `location` node starting at or after the rule list, so a nested `by … at h` inside a rewrite rule cannot be mistaken for the tactic's own. Two guards keep it idempotent and narrow: only a label in the exact shape the prettifier emits (`rw [`, which it uses for `rewrite` too) is touched, and one that already ends with the clause is returned unchanged — which is what protects the forms whose quotation does NOT match (`rw (config := …) [h] at hn` keeps its raw first-line label). Containment is half-open, and every node of one `rw` picks up the same clause: a split step's start is the RULE's position and the synthetic closing `rfl`'s is the bare `]`, both inside the tactic, so a 4-rule `rw … at h` reads as one tactic across its four boxes. **Alignment gets better, not worse** — the risk was `alignInLabel`, since the label is the coordinate space for token colouring. Measured over every shape: a single-rule `rw [h] at hn` now makes label and surface source IDENTICAL (one full segment, where before the clause was correctly clipped as text the label did not own); a multi-rule `rw [a, b] at hn` labelled `rw [a] at hn` aligns in two segments (`rw [a` head + `] at hn` tail located in the source) with the other rule clipped; 9 of 9 shapes align with 0 characters of disagreement, and the clause is coloured in 8 — the exception being the synthetic `rfl` node, whose label contains a word (`rfl`) absent from the source, so only the `rw [` head aligns exactly as it did before. Brief mode's bracket-list rule keeps the clause (`rw [List.prod_append, …] at hn`, every kept run byte-verbatim). Measured over `proofs/`: exactly 2 of 153 labels change (`factorization.lean:29`, `odd_sums.lean:75`), the other 151 byte-identical and the step count unchanged.

**In-place tactic editing (widget only).** Double-clicking a tactic node swaps its box for a textarea pre-filled with the tactic's source; Esc cancels, Enter commits single-line tactics (Shift+Enter newline), ⌘/Ctrl-Enter always commits, so does blur — a no-op edit just closes. Two wire facts make a server-side seam necessary: Paperproof's `tacticString` is **prettified for display** (first line only, `rw [...]` re-synthesized) and `ProofStep.position` **includes trailing trivia** — so neither is safe to write back with. `ProofTreeWidget.lean` therefore ships `tacticEdits: Array TacticEdit` (`{start, stop, text}` per distinct step range): the server re-extracts the range's verbatim source and trims trailing trivia with `trimmedEnd` (ProofTreeComments.lean — strips trailing whitespace, then any comment closing at the trimmed end, iterated), so replacing the tight `[start, stop)` can never eat a trailing comment. JS-side the seam is two optional `ProofTreeView` hooks: `getTacticEdit` (keyed by `position.start`, resolved in `widget.tsx` from `tacticEdits`) gates the affordance (hint `· double-click to edit` in the `<title>`), and `onEditTactic` commits via `ec.api.applyEdit` — the editor's own edit pipeline, so it lands on the undo stack and triggers re-elaboration; the tree redraws off the next RPC (see the refresh paragraph below — the cursor does NOT move on a commit, so the document, not the cursor, has to be what re-fires it), and the shape-keyed reset (see comments paragraph) keeps fold/zoom across a same-shape edit. **Select-all and the clipboard are handled asymmetrically, on purpose.** ⌘/Ctrl-A is implemented outright (`setSelectionRange`) — it touches no clipboard and needs no permission. The clipboard three are deliberately NOT intercepted: whether ⌘/Ctrl-C/X/V reach a focused textarea inside a VS Code webview as native clipboard ACTIONS isn't observable up front (the workbench owns most keybindings), and replacing the browser's own handling would break paste outright wherever the async Clipboard API is unavailable or unpermitted — it could only make a working case worse. So the keydown handler does NOT `preventDefault`; it clears a flag that `onCopy`/`onCut`/`onPaste` set, and on the next tick fills in from `navigator.clipboard` only if no native event arrived. The native path therefore always wins when it works, and the fallback writes through `setEditing` (the textarea is controlled, so writing `ta.value` would be overwritten on the next render) restoring the caret via `setTimeout`, not rAF — a hidden webview never fires animation frames. Verified in the preview with a stubbed `navigator.clipboard`: ⌘A selects all; with no native event, copy writes the selection, cut writes it and removes it leaving the caret at the cut point, paste splices at the selection; and firing a native `paste`/`copy` alongside the keydown leaves the value untouched and `writeText` uncalled (no double-paste). Commit uses a ref (`editingRef`, mirrored via effect) nulled synchronously: committing via Enter unmounts the textarea, whose blur would otherwise re-commit from a stale closure. Disabled in sequence mode and in the standalone app (no hooks). Both editing states (open overlay, dismissed accent) clear on a shape change.

**The overlay keeps its SYNTAX COLOURING while you type (widget only)** — a mirror element behind a see-through textarea, which is the only way to paint rich text under a real caret. It needed no new colouring machinery: `renderTaggedTactic` already tolerates its label and the source disagreeing (that is exactly what `alignInLabel` is for, since `tacticString` is a display string), so a DRAFT is just another such string and is passed straight in as the label, with `value.split("\n")` as the lines — `lineOffsets` skips one separator per line boundary, so that satisfies its exact-reconstruction contract for a multi-line draft. Colour therefore comes from the SAVED source's tokens realigned onto the draft: typing at the end aligns fully (the draft starts with the source), deleting from the end clips cleanly, and a mid-string edit keeps colour up to the edit point and loses it after. Newly typed text is never coloured until commit; colouring it would need the server to re-tokenize the draft, which is an RPC per keystroke and is deliberately not done. **The textarea only goes transparent when there is a mirror to show** (`background`/`color` transparent, `caretColor` explicit), so a failed alignment degrades to today's plain editor rather than to an invisible one; ADD and MIDPOINT overlays are skipped outright, since those hang off a GOAL node whose `position` is its producer's range and the tokens would be a different tactic's. Scroll is synced from the textarea's `onScroll` by DOM walk to `[data-ptw-mirror]`, not a ref, for the `react-hooks/refs` reason above. **The trap is inherited CSS, and it is invisible until measured**: a textarea is insulated from ancestor styles by the UA stylesheet and a plain div is not, so the mirror must PIN what the textarea computes. Measured in the preview — the app root's `text-align: center` put the mirror's glyphs 68.5px right of the caret, and an inherited `text-rendering: optimizeLegibility` would have changed glyph ADVANCES silently and only for some strings; `unicode-bidi` differed too. With `textAlign`/`textRendering`/`unicodeBidi` pinned, the two agree exactly: identical computed font metrics, identical box (0px on all four edges), equal `scrollWidth`/`scrollHeight`, glyph origin 0px from the textarea's content left, and line boxes at exactly `LINE_H` pitch. That style-diff assertion is the check worth rerunning if this is touched, since a new ancestor rule shows up as text drifting away from the caret rather than as an error.

**The overlay COMPLETES from what is already on screen (widget only).** Three local sources, none of which costs an RPC or a round trip: the **hypotheses** of the goal the tactic consumes (`TreeNode.hyps`, already on both wires — `used` first, since `tacticDependsOn` has already marked what this step is about); the goal's **subterms**, walked out of the tagged print the hover tooltips already use (`taggedSubterms` in taggedText.ts, fed to the view through the `getGoalTerms` hook so `ProofTreeView` stays source-agnostic and the ref-carrying `taggedGoals` stay in widget-land); and every imported **tactic name** (`ProofTreeData.tacticNames`, from `Tactic.Doc.allTacticDocs` — what `Lean.Server.Completion.tacticCompletion` is itself built from, minus the LSP item machinery and the docstrings that are the bulk of its 215ms). Tactic names are environment-only, so they are computed once per `getProofTree` and ride `proofTreeCache` — once per EDIT, never per keystroke — and are attached OUTSIDE the stable-proof signature, since stringifying ~500 strings into every signature comparison would be pure cost for a value that cannot change while the file is open. **Full `Lean.Server.Completion.idCompletion` over RPC was measured and deliberately NOT used**: it is public and does accept a synthetic `Syntax.ident` built from a typed prefix plus a goal's `ContextInfo`/`LocalContext` (verified — hypotheses and constants both come back), but on a Mathlib environment it costs 3.8s cold and ~525ms warm and returns up to **240,284** items for a one-character prefix, which would need truncation, cancellation and an explicit trigger to be usable — and the lens (`⧉`) already gives real editor completion by being a real editor. The subterm tier is the one that matters for `calc`: a chain restates part of its goal at every link, and measured over `proofs/calc.lean` **5 of 5** link right-hand sides the author wrote appear verbatim as a tagged subterm of a goal already drawn. Candidate sets are tiny (avg 15/goal, max 29, 72 distinct across that proof), so no ranking, paging or fuzzy matching is needed. **Two matchers, because the tiers key on different things** (`completion.ts`, pure so a probe can exercise it): names match the identifier token AROUND the caret — extended forwards as well as back, or completing from mid-word leaves the tail behind (`exact h|ab` + `hab` → `habab`) — while terms match the text back to the last STRUCTURAL boundary (line start, `:=`, or a relation symbol) and forward to the next one. Terms are offered even when that text is EMPTY, because having just typed `_ = ` the goal's RHS is the likeliest next thing and that is the moment the feature exists for; names are not, or every empty caret would dump ~500 tactic names on screen — and an empty draft has no boundary at all, so it correctly offers nothing. Two filters are load-bearing rather than cosmetic, since these strings get typed into the buffer: anything containing `✝` is dropped (inaccessible names print with it and will not round-trip into source), as is any single-token term (tier 1 already covers those). **An EXACT match leads the list, and is never filtered out.** Dropping it looks reasonable — accepting it changes no text — and is actively wrong: it left the next-longest candidate SELECTED, so finishing `ring` and pressing Enter inserted `ring1`. It is kept, hoisted to the front whichever pool it came from, and marked `exact`, which the view reads to make Enter mean COMMIT there rather than costing a second keystroke to accept a no-op (Tab still just closes the list). Tactic matches are additionally sorted shortest-first, because `allTacticDocs` order is arbitrary and for a prefix match the shortest candidate IS the exact one — so `ring` sorts ahead of `ring1`/`ring_nf` for free, and a partial `rin` still offers `ring` first. Verified live: `rin` → `ring, ring1, rintro, ring_nf`; `ring` → `[ring], ring1, ring_nf` with Enter committing, while a non-exact `nlin` + Enter accepts `nlinarith` and keeps the editor open. The pretty-printer's output is not *guaranteed* re-parseable, so this is a suggest-don't-trust source — fine for completion, and for the calc case it round-trips because the printed form is what the author was transcribing anyway. Three traps, all of which this file has been bitten by before: the textarea's `onBlur` COMMITS, so the list's `onMouseDown` must `preventDefault` or clicking an item commits the edit and unmounts the editor mid-gesture (verified: mousedown is default-prevented, no blur, no commit); the list owns Arrow/Enter/Tab/Escape only while it is open, with `⌘/Ctrl-Enter` checked FIRST so "always commits" stays true and Escape dismissing the LIST before it cancels the edit on a second press; and accepting writes through `setEditing` with the caret restored by `setTimeout`, not rAF, because a hidden webview never fires animation frames. The list's colours come from the overlay's own `--ptw-edit-*` palette with `--ptw-accent`/`--ptw-accent-text` for the selection, NOT the `--vscode-editorWidget-*` chrome the rail uses: those carry light fallbacks for the standalone app, and pairing them with theme-following text rendered the selected row light-on-light in a dark theme — the same "fix one half and get the mirror bug" trap that ties the node fills to the token palette. Two ordering facts worth keeping: the completion helpers must be declared AFTER `nodes` (they read it, and the React Compiler bails on the surrounding memos otherwise), and the accepted item's textarea is passed in explicitly rather than read from a component-level ref — eslint's `react-hooks/refs` forbids the latter inside a function called from JSX, and it taints every other ref-touching call in the same handler, `commitEdit` included. Two render facts: the textarea overlay is rendered AFTER the whole nodes loop (SVG paints in document order — inside the node's own `<g>` every later sibling paints over it), and the edited node's box/label/fold-glyph get `visibility: hidden` while it's open (the overlay is bigger than the box, and an accented node would clash through it) and WIDENS to its content live (via `measureText` on the longest line) while its HEIGHT stays fixed, instead of relayouting the tree — a box that grows a line at a time while you type reflows nothing but reads as the tree shifting under you, so a replace keeps the box's own height (it stands exactly where the box was) and an add is one line (the goal box it hangs under can be many, and an empty textarea that tall is all void); overflowing text stays reachable because a textarea scrolls to keep its caret in view; and on *editable* tactics the single-click reveal is DEFERRED 300ms and canceled by the dblclick handler (`deferReveal`) — a double-click's first click is a plain click, and an instant reveal steals focus to the editor mid-gesture, eating the second click. The lens (next paragraph) is a hover-bar button, not a modifier gesture, so double-click is the ONLY editing gesture on a tactic.

**The overlay has the BUFFER's unicode input — `\dvd` → `∣` (widget and app both).** Without it the tree could only ever edit ASCII tactics, which in Lean is most of a sentence short, and the fallback was to leave the tree for the lens over a single character. The table and the state machine are UPSTREAM's: `@leanprover/unicode-input` is the very package vscode-lean4 drives the editor's own input mode with (1855 entries, `$CURSOR` and all), so nothing here reimplements a vocabulary or a replacement rule and none of it can drift from the buffer. What `web/src/abbreviation.ts` adds is the one host upstream has never been pointed at: a CONTROLLED React `<textarea>`. Upstream's two adapters both assume otherwise — vscode-lean4 feeds `AbbreviationRewriter` a `TextDocument`'s `contentChanges`, and `@leanprover/unicode-input-component` drives a `contenteditable` by writing `innerHTML` — whereas ours takes its value from React state and must restore the caret after the render that applies it, the same constraint the clipboard fallback and completion acceptance already live under. So `AbbrevSession` owns a SHADOW copy of the draft and every path that writes `editing.value` (onChange, completion acceptance, the clipboard fallback) must report it through `syncAbbrev`, or a later `flush()` resurrects a stale draft. `sync(value, caret)` is ONE idempotent entry point rather than separate text/caret hooks, because the view has several events that can carry either and their relative order is not something to depend on — a text change feeds the change through and replaces what it finished, an unchanged value with a moved caret replaces any abbreviation the caret LEFT (the buffer's rule, and what makes clicking away from `\alpha` yield `α`).

Three things were settled by running it, and two were outright bugs that reading could not have caught. **`Range.offsetEnd` is upstream's LAST CONTAINED offset (`offset + length - 1`), not the exclusive end**, so slicing a replacement at it keeps the range's last character — `\alp` expanded to `αp`. **`run` takes a THUNK, not a promise**: an `async` body runs to its first `await`, and `forceReplace`'s first `await` is on the call to our own `replaceAbbreviations`, so passing `rewriter.replaceAll…()` as an ARGUMENT rewrites the text before the "did anything change?" baseline is even read — every replacement went silently missing while `flush` worked perfectly. That same synchronous-until-first-await fact is what makes **`flush()` synchronous**, which it has to be: commit runs from a blur/keydown handler with nothing to await into, and committing `\alpha` must write `α`, never `\alpha`. And **React's `onSelect` is not reliably delivered** — it is React's own synthesised event, and the headless harness never fired it at all — so the caret-leave rule also rides `onKeyUp` and `onClick`, the two plain DOM events that definitely follow a caret move; `sync` being idempotent is what makes the overlap free.

**Held in STATE, not a ref, and that is the counter-intuitive part.** A mutable per-session helper is exactly what a ref is for, and it is the one thing that does not work here: `react-hooks/refs` treats a ref READ inside a function called from the overlay's JSX as render-phase, and the taint spreads to every other ref-touching call reachable from there — bisected, adding the read to `syncAbbrev` alone lit up `commitEdit`, `acceptCompletion` and `clipboardFallback`, and emptying that one function's body cleared all four. Attaching `ref={taRef}` to the textarea is likewise a render-phase USE, which is why the emit finds the element by DOM walk (`[data-ptw-edit] textarea`), the same reason `onScroll` walks to the mirror. As state the session is simply a render value, and its being mutable costs nothing since nothing ever compares it; it is rebuilt in the existing adjust-during-render block that already resets the completion list, keyed on the node id. A PENDING abbreviation is underlined, by a third transparent-text layer over the textarea — the mirror trick from the other side, and the only way to decorate text under a real caret. It sits ABOVE the textarea rather than below, because with no mirror the textarea's own background is opaque and would hide it; it paints nothing but thin rules, so glyphs and caret read straight through. It pins the same `textAlign`/`textRendering`/`unicodeBidi` the mirror does and for the same measured reason — a div inherits ancestor text CSS a textarea is insulated from. Tab expands what is pending and takes priority over the completion list's own Tab (that is what Tab means in the buffer, and the two can hardly collide — nothing this completes contains a leader), falling through when nothing is pending. Settings ride the companion's `theme-colors.json` for the third time (`lean4.input.enabled/leader/eagerReplacementEnabled/customTranslations`, custom translations as an ARRAY for the same decoding reason `colors` is one), but the TABLE is bundled — so with no companion the editor still expands `\dvd`, on vscode-lean4's own defaults, and only a customised input mode needs the trip. `ThemeAbbrev.abbreviation` is spelled out because `abbrev` is a Lean keyword.

Verified two ways. Offline over the real table, driving the real session keystroke by keystroke: `\dvd `→`∣ `, `\alpha `→`α `, `\to `→`→ `, `\ne `→`≠ `, `\R `→`ℝ `, `exact \langle h`→`exact ⟨ h`, `\l1 `→`→₁ ` (a real table entry, not `\l` then `1`); `diffAt` exact for insert/backspace/leader-before-leader; `\alp` left pending and `flush()` synchronously yielding `α`; `\<>` flushing to `⟨⟩` ($CURSOR stripped); the pending span covering `\alp` at the right offset; a custom leader plus a custom translation (`#foo `→`☺ `). The underline layer's box matches the textarea's on all four edges and its glyphs sit **0.01px** from where the canvas measurer puts them. The Lean decode was checked against an old-format payload with no `input` key (colours kept, input defaulted), a wrong-typed `leader: 42` (that field alone defaults), and `{}`.

**What re-fires the RPC (widget only).** `getProofTree`'s deps used to be the cursor alone (`pos.uri/line/character`), which quietly made "the cursor moved" the only way the tree could ever change. That is wrong for every edit the widget itself makes — an in-place tactic commit, a (+) insertion, a `sorry` stub all go through `applyEdit` and leave the cursor exactly where it was — and equally for typing in the buffer or the lens: the file re-elaborated, the tree did not, and nudging the cursor was the only way to see your own edit land. The document is therefore a second dep: `useServerNotificationEffect("textDocument/publishDiagnostics")` bumps a `docRev` counter that rides the dep list. Diagnostics are the right signal because they are published when the file worker has re-elaborated, i.e. precisely when a re-parse can return something new (it is what the infoview's own panels refresh on). Elaboration publishes them repeatedly as it progresses, so this fires in bursts — affordable rather than ignored: `DOC_SETTLE_MS` is a trailing debounce down to one call per burst, the server caches the whole payload on `(uri, version, command start)`, and `stable` only re-lays-out when the proof's TEXT signature changes, so an identical re-parse costs one cached round trip and no tree re-render. There is no loop risk (a response publishes no diagnostics), and the RPC session survives edits, so `rs` identity is stable.

**Adding tactics from the tree (widget only).** A PENDING goal — one no tactic consumes, i.e. the live frontier while a proof is being written — grows a dashed ghost (+) chip below its box (tactic-styled: the tactic that isn't there yet). Clicking opens the same textarea overlay as in-place editing, empty, hung BELOW the box so the goal stays readable while you answer it; commit INSERTS instead of replacing (`onAddTactic`), and an empty commit just closes. A second chip beside it, `sorry`, stubs the goal in ONE click with no overlay — parking a branch while the rest of the proof keeps elaborating. Two chips rather than one plus a modifier, deliberately: the lens gesture is the recorded precedent that modifiers on tree nodes silently stop working. Both are `FrontierChip`s (dashed, unfilled — a slot, not a node); the stub takes its colour from the syntax palette's `--ptw-tok-sorry`, so a stub reads the same in the tree as the keyword does in a tactic label. **A chip is offered only for an unconsumed goal reached through `goalsAfter`.** An unconsumed SPAWNED goal is not the frontier: Paperproof emits side goals no tactic ever consumes because they restate goals already handled inside the branches (factorization.lean's `induction … with` spawns two, from the merged `intro p hpm` binders), so keying on "no consuming step" alone put 2 chips on a COMPLETE proof. Measured across the incomplete-proof corpora, every genuine frontier goal arrives via `goalsAfter` and none via `spawnedGoals`. Where and how to insert is then computed as data in proofToTree (`TreeNode.addSpec`) from the producing step's shape: a producer ending in `with` gets `| case => ` (checked BEFORE the split rule — an induction with a single case still needs its marker, and a bare line after `with` is a syntax error); several `goalsAfter` get a `· ` bullet; otherwise a plain line. **The insertion COLUMN comes from the source, via `TacticEdit.tacticIndent`, because neither obvious client-side answer works.** The producing step's own `start.character` lies whenever Paperproof SPLIT the tactic — `rw [a, b]` is one step per rule, so the step for `b` starts at the rule inside the brackets (col 13 of `      rw [h, hk]`) and indenting by it put a new tactic 7 columns too deep. But the bare line indent lies the other way on a bulleted line: `  · constructor` has indent 2 while that `constructor`'s own branches belong at col 4, under the tactic rather than the `·`. `tacticIndentAt` (ProofTreeComments.lean, non-`private` so a probe can check it) skips whitespace THEN a bullet marker — `·`/`.` only before whitespace, so `.foo` dot-notation isn't mistaken for one — and deliberately does NOT skip a `| case =>` marker, since case insertions write their own and want the marker's column. `AddSpec.producer` exists so the client can look the value up; `AddSpec.indent` remains only as the source-agnostic fallback (the CLI ships no `tacticEdits`, and the standalone app renders no chips). **The split test must read `goalsAfter`, never `stepGoalsAfter`** — the latter folds in `spawnedGoals`, so a `have … := by` (one continuation + one spawned body) counted 2 and emitted `· tac` where a plain next line belongs, putting the continuation at a bullet's structure. That was the reported wrong-indentation bug. `after` is the LAST-in-source step among the producer's subtrees, so a new bullet lands below its written siblings — matching Lean's positional bullet binding — except the by-body, which must stay inside the block. The widget inserts at the END OF THE LINE holding the anchor's TIGHT stop (resolved via `tacticEdits`; end-of-line so a trailing comment stays glued to its tactic; the huge character value is clamped by the editor, since the widget never holds the document text). Known v1 limit, recorded in `addSpecFor`: with SEVERAL pending siblings every (+) anchors at the same spot, so adding out of source order attaches text to the wrong goal. The standalone app passes no `onAddTactic`, so chips never render there; verified end-to-end by temporarily appending a ppharness-harvested INCOMPLETE proof to sample.ndjson with a stubbed hook (then reverted): chip → overlay → Enter fired the hook with the right spec, Escape cancelled, empty commit was a no-op, and the `sorry` chip fired straight through without opening an overlay. The insertions are also checked by ELABORATING them: applying each proposed `sorry` to the real source and running `lake env lean` over the result gives zero errors that aren't `unsolved goals` (i.e. nothing mis-indented or unparseable) across all three forms, and drops the file's error count by exactly one each time — proving the stub attached to the goal it was offered for, not a neighbour. (Blur-commit needed a synthetic focusout: the hidden preview tab emits no native focus transitions.)

**`calc` chains are a LIST, not a split — and their links are filled in place.** A `calc` block reaches the tree as ONE tactic node whose links arrive as its CHILDREN, so a chain fans out sideways where everything else runs down the trunk (the closest shape is `have … := by`, which opens exactly one side proof). Two consequences, one for layout and one for editing, and both come back to the same fact: a chain is the steps of ONE computation and nothing continues after it — the chain IS the proof of the goal.

Layout: `TreeNode.chain` (set in proofToTree from `/^calc\b/` on the RAW `tacticString` — read off the label rather than a server-side syntax kind because the flag has to work on BOTH wires, and the CLI ships no syntax) makes `trunkLayout` skip its usual "last child in source order resumes the trunk at the parent's own indent" rule, so every link indents equally and they read as a column. Without it a 3-link chain drew two indented links and one flush-left, which reads as a branch rejoining. A real case split KEEPS trunk resumption: there the last branch genuinely is where the proof ends up, and indenting every branch would step the trunk right at every split and drift a case-heavy proof off the page. The renderer needs no change — it picks elbow-vs-straight geometrically (`|tLeft - sLeft| < 0.5`) and `linkSpans` mirrors that. `elide.ts` propagates `chain` from a cut's LAST constituent tactic onto the marker, or a calc swallowed by ⇉ combine loses its column (exact for a combine run, which is linear, so only its last member has children outside the cut). Measured over `proofs/`: 3 chain nodes, 0 whose children disagree on x, and 9 of the 10 proofs byte-identical in placement — only `proofs/calc.lean` moves, by exactly the 6 nodes expected.

Editing: **a calc chain's work-in-progress state is a HOLE, not a missing tactic.** The chain must end at the goal's RHS, so it can never simply be left short — you write `_ = c := ?_`. Measured: a `:= ?_` link's goal moves from `spawnedGoals` into `goalsAfter` (a `:= by …` link stays spawned), so such a link is ALREADY pending and already grew a (+) chip — but `addSpecFor`'s anchor (the last-in-source step among the producer's subtrees) sits INSIDE the block, so that chip dropped a line into the middle of the chain and broke it. `ProofTree.CalcHole` (ProofTreeComments.lean, the shared source/editing-seam lib, so BOTH wires ship it — it is plain data, unlike the ref-carrying tagged goals) closes this with two independent walks, because neither half knows the other's coordinates: the info tree gives goal → hole SPAN (a `Term.syntheticHole` whose elaborated `expr` is the metavariable) and the SYNTAX gives the link structure, which no info node records. **The join is exact, not positional** — a `?_`'s mvarId IS Paperproof's `GoalInfo.id` (verified byte-identical across two independent elaborations), so nothing assumes the order links are reported in. Three details each rule out a real construct: the calc `_` LHS placeholder is a `Term.hole`, NOT a `syntheticHole`, so filtering on the kind excludes it (it is not a goal either); a hole is paired with its SMALLEST containing link, so a nested calc can't claim an inner one's hole; and a `?_` outside any calc link is DROPPED, because `refine ⟨?_, ?_⟩` is better served by the existing `· ` bullet insertion, which is what one writes there by hand.

That gives two `AddSpec` kinds that act on the hole's own range instead of a line anchor (`calcEdit`, kept a pure module so a probe can run the REAL edit math and elaborate the result; a third, `calc-append`, joins them below). **hole** replaces the `?_` with `by <tactic>` — `by`, not a bare term, so the redraw shows a real tactic node standing where the chip was (a term-mode `sorry` would close the goal with no node at all). **calc-link** (the third chip, `step`) inserts a whole new link on the hole's line, pushing it down. Inserting ABOVE a hole is the only always-valid way to GROW a chain: the new link takes the previous RHS as its `_`, and the hole's goal simply restates from the new RHS, so the chain still ends where the goal needs it to — whereas appending after a well-formed chain is always ill-typed. It is therefore offered only when the enclosing step is a `calcStep`, never a `calcFirstStep`, whose LHS is the chain's real head rather than a `_`; that the two are distinct SYNTAX KINDS is what makes the gate free. Its overlay opens prefilled `_ = ` and committing that unchanged is the empty commit of this form (`commitEdit` compares against `original`, so a bare `_ = ` is never written). Verified by ELABORATING the results: each fill/stub/grow applied to the real source parses and typechecks, and the remaining unsolved goal is exactly the OTHER hole — i.e. the edit attached to the link it was offered for, not a neighbour; and in the preview (temporary holed proof + stubbed hook, then reverted) the first link showed `+`/`sorry` and no `step`, later links all three, each firing once with the right hole.

**Opening a chain — the way IN to calc mode.** `step` can only GROW a chain that already has a hole, so on a bare goal the tree had nothing to offer and the first `calc` still had to be written by hand — which is the one step the tree couldn't help with. A third chip, `calc`, is offered on a pending goal that IS a relation (and isn't already a link — the two chain gestures are mutually exclusive, so a goal never carries more than three chips). It asks for the one thing that cannot be inferred, the first INTERMEDIATE expression (and, when there is a choice, the first link's RELATION — see the `Trans` paragraph below), then inserts a two-link skeleton through the ordinary line-insertion path, so indent, bullets and `| case =>` markers are handled already:

    calc _ = <mid> := ?_
      _ = _ := ?_

**Both endpoints are `_`, which is the whole point**: Lean solves them by unifying the chain against the goal, so the skeleton contains NO pretty-printed terms and nothing in it can fail to round-trip back into source — the standing risk with any "write the goal back out" feature. Measured: `_` elaborates as the first link's LHS and as the last link's RHS, for `=` and `≤` alike, and the resulting goals print concretely (`a + 0 = a`, `a = c`) rather than leaking metavariables. TWO links rather than one because a lone link is a `calcFirstStep`, which nothing can be inserted above; the second link is what `step` then grows against, so the chain builds forward from the LHS. The relation set comes from `calcRelations` (proofToTree), which prefers the server's `Trans` enumeration and falls back to `spineRelation`'s reading of the goal's TYPE STRING when a wire doesn't ship one. That fallback's test is deliberately conservative: collect the relation-ish tokens at BRACKET DEPTH 0 and fire only when there is exactly one and it is chainable. Measured over the corpus's 59 distinct goals, 35 are offered; the discriminating cases are `2 ≤ n → ∃ p, …` (declined — two depth-0 tokens, so the `≤` is not the goal's spine), `∀ p ∈ l, Nat.Prime p` and `∃ k, m + 1 = 2 * k ∨ …` (declined on the binder head), `Even n ∨ Odd n` and `False` (no relation), against `∑ i ∈ Finset.range (n+1), (2*i+1) = (n+1)^2` (offered — `∑` is a term, not a binder whose body is the goal). A false positive costs an edit the author can undo; a false negative hides the affordance, so the bias is toward offering. Verified end to end: from a bare pending `a = c`, the chip's skeleton elaborates with nothing but `unsolved goals` and yields two concrete pending links, the second of them `step`-able — start, grow, fill, all from the tree.

**Closing a chain — the third calc chip, and the way back IN to a chain already written by hand.** `step` and the `calc` skeleton only ever operate on a chain the tree itself created (both keep a trailing `?_`), so a chain someone WROTE — the overwhelmingly common case — was something the tree could only watch. A hand-written chain in progress is short: its links stop before the goal's RHS. Measured, that still elaborates — Lean leaves the remainder as a `calc.step` goal, which arrives in the calc step's `goalsAfter` and is therefore already an ordinary pending goal in the tree, drawn at the BOTTOM of the chain's column (srcRank puts it after the links with no special casing) and badged `calc.step`. What it was missing is the idiomatic way to continue: `addLinkFor` now offers **calc-append** there, which inserts `_ <rel> _ := ?_` as a NEW LAST link. That closes the residue against the chain — the new link's `_` LHS takes the previous RHS and its `_` RHS unifies with the goal's, the same reason the skeleton's endpoints are `_` — so nothing has to be typed and the chip commits in ONE CLICK, like `sorry`. What it buys is re-entry: the residue becomes an ordinary hole, which every other calc gesture already understands (verified by re-harvesting after the edit — `first: false`, so `+`/`sorry`/`step` all light up on it). The relation is read off the RESIDUE's own type via `spineRelation`, not off any link: the residue carries the chain's COMPOSITE relation, which need not be any single link's (`=` then `≤` leaves a `≤`). The three chain gestures are mutually exclusive on one goal — a hole grows upward, the residue grows downward, and `calc` opens a chain only where neither applies — so a goal still never carries more than three chips.

Where and how to append is `CalcChain` (ProofTreeComments.lean, beside `CalcHole` and on both wires), keyed by the calc tactic's own start, which IS `ProofStep.position.start` for the step the residue hangs off — the join needs no mvarId. It carries the final link's end (the line to insert after; end-of-LINE, so a trailing comment stays glued to its link) and the column the links are written at. **That column is READ, not guessed**: the obvious `calc`'s own column plus two happens to match all three corpus chains, but it is a convention, whereas the parser anchors subsequent steps on the second link by `colGe`, so a link written one column shallower than the existing ones is silently not part of the chain. `collectCalcChains` takes the SECOND link's column — the one the chain's own links already prove parses — falling back to calc+2 only for a one-link chain, which is a broken file anyway (below).

**A `calc` with no SUBSEQUENT step does not parse, which is why a half-written chain can make the whole tree vanish — and repairing that is the third thing the `step` chip does.** `calcSteps` wraps the subsequent-step list in its own `withPosition`, so with nothing after the first link the `colGe` anchor is whatever token follows the block and the guard is vacuous: the parser tries to read the NEXT thing as a calc step. Measured on the real sources — such a block inside a `·` bullet swallows the following sibling bullet (`· ` is `·` cdot notation, so it parses as a term and then fails at `with`), and one followed by a plain tactic swallows that; either way the command fails to PARSE and everything under the calc is simply absent from the tree. It is what a chain looks like WHILE YOU TYPE IT, and the damage is not local: on the scratch file a bare `calc (a + b) ^ 2` in the first of three bullets took the other two chains with it, 2 steps where the repaired file has 12. It is the first thing to check when a `calc` "disappears" — though the tree now DRAWS the block in that state rather than going silent (next paragraph). Note the trigger is the missing SUBSEQUENT step, not the missing relation — `calc a + 0 = a := by omega` alone breaks exactly the same way as a bare `calc a + 0`, and conversely a bare `calc e` that ENDS its block parses fine, leaving the ordinary `calc.step` residue (`_` elaborates as the chain's whole span). The widget's own gestures can never create the state — the skeleton opens with two links, and `step`/append only ever add more.

The syntax SURVIVES, though, and that is the opening. `CalcBlock` (ProofTreeComments.lean) drops links carrying `Syntax.missing` — in a broken block the trailing `calcStep` is the parser's failed attempt on the next tactic, and measured, its range covers the following `· trivial` verbatim, so using it to place an insertion would write into a neighbouring tactic — and reports `CalcChain.broken`. The `calcFirstStep` is intact in that state (`missing=false`, exact range), which is the one thing needed: appending one link after it hands the parser back its `colGe` anchor. So the repair reuses the `calc-append` EDIT unchanged — a chain that stopped short and one that never parsed both want a link after their last well-formed one — and the chip commits in one click. Verified by elaborating the real chip's real edit on the scratch source: the file goes from "everything after the calc missing" to one outstanding goal (the `?_` it just created), and re-harvesting shows both previously-swallowed chains back, `broken: false`, one of them now an ordinary residue the existing `+`/`sorry`/`step` gestures handle — so the repair is also the way back in.

**A chain is drawn from the MOMENT `calc` is typed, which needs the SYNTAX rather than the info tree.** `calcBlocks` used to fold `TacticInfo`s whose own kind is `calcTactic` and skip any block with `links.isEmpty` — so the states you are actually in while writing a chain (`calc`, `calc a + 0`, `calc a = b :=`) produced no `CalcChain` at all, and since such a block doesn't parse, the tree simply lost everything below it with no explanation. It now DESCENDS syntax (`calcNodes`) over every `TacticInfo`'s `stx` plus, widget-side, `snap.stx` (the whole command) as `extra`: a calc that never elaborated has no info node of its own, but its syntax survives inside the enclosing tactic's. Zero well-formed links is reported, not skipped. Two things had to be measured rather than reasoned about. **`hasMissing` does not reject a link the parser invented**: after a bare `calc`, the FOLLOWING bullet is read as the first link's term (`· trivial` is cdot notation, so nothing is `missing`) and its range covers a neighbouring tactic verbatim — using it to place an insertion would write into that tactic. Lean's own layout rule rules it out, and that is the filter: a link on a LATER line must be indented past the `calc`. `broken` is then `hasMissing || links.isEmpty`. And **`CalcChain.stop` is the last well-formed link (or the end of the `calc`'s own line), never the block's syntax range**, which when broken runs on into the swallowed tactic — the client hands `stop` to the cursor accent, so a calc must not be able to claim a neighbour's positions. `CalcChain` also carries `links` (how many are well-formed), `text` (the verbatim source over `[tacticStart, stop)`, the drawn label) and `firstBare`. Harvested across every typing state: `calc`, `calc e`, `calc e = e`, `calc e := `, `· calc e := by tac` all report with correct link counts and a `stop` that never spills.

**The repair chip lives on the `calc` node, and the node is SYNTHESIZED when nothing stands for it.** `brokenChainByGoal` now yields `{chain, step?}`. When a step exists (the first link was complete, so the block half-elaborated) the calc is already drawn: `repairSpec` rides THAT tactic node, not the goal above it, which is where a chip pointed at nothing. When no step exists, `proofToTree` invents one — id `calc:<line>:<col>` (collision-free against mvarIds, `tactic:`, and elide.ts's markers), label the verbatim `chain.text`, `chain: true` so it lays out as a column, `synthetic: true`, and `position` from `[tacticStart, stop)`. It is emitted before `visitGoal`'s `!step` return so DFS pre-order — which `combineRuns` and elide.ts's slot arithmetic rely on — is preserved; `srcRank` sorts it by `position.start` for free. One guard follows from `synthetic`: `combineRuns` BLOCKS it — merging it would hide its repair chip inside a box that carries no chips at all. **It IS editable, though, and that is the one place a `tacticEdits` entry is built from something other than a step.** The general invariant stands (never FABRICATE an entry — bogus offsets would make `alignInLabel` colour characters the label doesn't own), and this entry does not violate it: `[tacticStart, stop)` is a measured range, `CalcChain.text` is the server's own verbatim slice of exactly it, and the synthesized node's LABEL *is* that text — so the label-vs-source alignment is an IDENTITY here rather than the guesswork the invariant guards against, and the block gets syntax colouring it never had. `getProofTree` emits one per `broken` chain whose `tacticStart` isn't already in the steps loop's `seen` set, which is precisely the client's own "no step stands for it, so synthesize a node" condition — keep the two pointing at each other. Editing it matters more than it sounds: a block that doesn't parse is UNFINISHED TEXT, and the repair chip offers only the single canned fix (append a well-formed link), so without this the one node standing for text you are still typing was the only tactic in the tree you couldn't double-click. `stop` being the last WELL-FORMED link rather than the block's syntax range is what makes the edit safe — the range can never reach the tactic the parser swallowed. Verified offline over core-only sources (`IO.processCommands`, the documented recipe): for `calc a + 0 = a := by rfl` with nothing after, and for a bare `calc a + 0`, the reported range's slice equals `text` exactly, and **every** semantic token inside it resolves to a hover info node (5/5 and 2/2 — better than expected for an unparsed block, since the tokens still sit inside the enclosing `by`'s elaborated syntax), while a well-formed chain is correctly not reported broken. End-to-end in the preview over a real harvested broken chain with stubbed hooks: the overlay prefills byte-exact with the two-line verbatim block and opens two lines tall, plain Enter inserts a newline rather than committing (the original is multi-line, so ⌘/Ctrl-Enter is the commit), Escape and an unchanged commit both write nothing, and a real commit fires with the exact `[178:4, 179:52)` range. Applying that edit to the real source leaves the `have` above, the commented-out neighbours below and the swallowed sibling bullet all untouched, elaborates with zero diagnostics, and re-harvests 3 → 14 steps with 1 → 0 broken chains and all three of the file's chains back — so editing is a second way back in alongside the chip, which still works on the same node (its picker expands and dismisses as usual). The chip lane's gate widened from `type === "goal"` to also admit a synthetic node or any tactic carrying `addLink`; mutual exclusion is unaffected (a goal still shows at most three chips, a calc node exactly one). The standalone app passes no `onAddTactic`, so it draws the node with no chips — "there is a chain here that didn't parse", which is the honest reading.

**Repairing depends on whether the first step is BARE, and all three shapes were settled by elaborating them.** `calcFirstStep`'s justification is optional (`ppIndent(colGe term (" := " term)?)`), so `calc a ≤ b` is the chain's starting EXPRESSION, not a link missing its proof. Appending `_ ≤ _ := ?_` after it therefore reads as `(a ≤ b) ≤ _` and fails to synthesize `Trans` — measured, not guessed. So `CalcChain.firstBare` splits the repair three ways: a justified first link gets one appended link (`calc-append`); a BARE one is COMPLETED with ` := ?_` *and* given a subsequent link in the same edit (completing alone leaves the block unparsed, since the missing subsequent step is the actual trigger — all three ways elaborated); and a `calc` keyword with NO link writes its first two links (`calc-first`, which always needs an intermediate expression, since both links' free ends are `_` and nothing would pin the middle). `calc a = b :=` — links 0, not bare — is the one state left visibility-only: the author is mid-keystroke on the justification and there is no honest edit to suggest. Verified by elaborating the REAL chip's real edit and re-harvesting: the repaired file's only diagnostic is `unsolved goals`, the previously-swallowed sibling branches are back as steps, and the chain returns `broken: false` with holes the ordinary `+`/`sorry`/`step` gestures handle — so the repair is also the way back in.

**Which relation the next link chains is PICKED, from the real `Trans` instances.** Every generated link used to reuse the goal's own relation, so the commonest shape — prove `a ≤ c` by `a = b` first, then `b ≤ c` — could not be expressed from the tree at all. (Mathlib's own calc widget has the same limitation: `Mathlib/Tactic/Widget/Calc.lean` pretty-prints the goal's relation and reuses that symbol for every step; it never touches `Trans`. Core only ever SYNTHESISES `Trans r s ?t` with both inputs known, in `mkCalcTrans`. There is no API for "given T, which R and S compose to it".) `calcRelationsFor` (ProofTreeComments.lean, so BOTH wires ship it — plain relation SYMBOLS, no refs) builds one: `getCalcRelation?` for T, then `SynthInstance.getInstances` on `Trans ?r ?s T` with both inputs open, then per candidate `isDefEq` + **verify with `trySynthInstance (Trans r s T)`**, which is `mkCalcTrans`'s own test. Measured, `getInstances` filters tightly by the outParam (3–9 candidates), and pairs still carrying mvars after unification are dropped — that is what discards Mathlib's wildcard `[IsTrans α r] : Trans r r r`. **The gate on offering anything is that T chains with ITSELF**, and it is not a convenience: `Trans Eq r r` and `Trans r Eq r` are core instances holding for ANY binary relation, so "some pair verified" accepts `Even n ∨ Odd n` (measured — `∨ then =` synthesises fine). Requiring `(T, T)` is name-free, rejects `∨`/`∧`/`≠`, and is exactly the assumption the two-link skeleton already makes. Options are deduped by FIRST relation, preferring the pair whose second is T, with `(T, T)` first — so `≤` yields `[≤/≤*, =/≤]` and `<` yields `[</<*, ≤/<, =/<]`. Three bugs here were only findable by running it. **`getCalcRelation?` must be given a `consumeMData`'d type**: a `have`'s CONTINUATION goal arrives wrapped in `mdata noImplicitLambda`, and that decomposition is `getAppNumArgs`-based, which sees an `.mdata` head and answers 0 — so the entirely ordinary `⊢ (a + b) ^ 2 ≤ 2 * (a ^ 2 + b ^ 2)` sitting under `have hsq : (0 : ℝ) ≤ (a - b) ^ 2 := sq_nonneg _` was declined outright, exactly where one most wants to open a chain. The string-level heuristic this replaced never saw the wrapper, so the symptom was a chip that used to appear and stopped; the raw `Expr` dump is what showed it. The other two: `ctx.runMetaM {}` starts with an EMPTY local context, so inferring anything about a goal throws `unknown free variable` (`goalToInteractive` gets away with it because it enters the context itself) — hence `mvarId.withContext`; and an instance may state its relation as a LAMBDA (core's `Nat.instTransLe`), leaving a beta-redex that prints as `(fun a b => a ≤ b) x y` and so failed the 3-token arity check that keeps a symbol WRITABLE — hence `headBeta`. That arity check is load-bearing, since the symbol is written into source: it correctly declines `Nat.ModEq` (`x ≡ y [MOD n]`) rather than emitting an unwritable `≡`. Enumeration runs only for genuinely PENDING relation goals (usually 0–3), via `calcRelationGoals`, whose rule is VERBATIM the client's (`goalsAfter` only, never `stepGoalsAfter`, plus the half-open containment owner of a broken block — keep the two comments pointing at each other, since a drift shows up as chips silently vanishing rather than as an error); and `proofTreeCache` already makes the whole payload once-per-edit rather than once-per-cursor-move. An entry with EMPTY `options` is a positive "not chainable"; NO entry means the wire didn't ship the field, and only then does `spineRelation` stand in. Measured over the 110 distinct goals of `proofs/` plus the scratch file (enumerating for EVERY goal, not just pending ones — the sweep worth rerunning if this is touched, since it is what catches a shape the server declines and the heuristic accepts): the server offers on 63, the heuristic on 66, they agree on 107, and the only three the heuristic offers that the server does not are all `≠`. That is the one known loss versus the old vocabulary, and it is honest — you cannot build a multi-link `≠` chain.

**The chip lane is RESERVED by the layout, and the repair chip has exactly one home.** Two bugs met here, and only the second is about geometry. First: the repair was attached to BOTH the goal and the `calc` node standing for the block, so one edit was offered twice and the upper lane drew over the node between them. The rule is that the chip always rides the `calc` — the thing the repair acts on — whether that is a real step's node or the synthesized one, and never the goal above it. Second, and general: the lane hangs BELOW a node's box, outside the band, so unlike the comment strip and the case badge nothing reserved room for it and whatever the trunk cursor placed next simply drew on top. That was invisible while chips only ever appeared on PENDING goals — leaves, with a generous `TRUNK_GAP_BRANCH` beneath — and became a real overlap the moment a chip could sit on an interior node, where the gap is the tight `TRUNK_GAP_STEP` (14) against a lane needing 19. `LayoutNode.chipH` now reserves `CHIP_TOP_GAP + CHIP_LANE_H`, and it is added to a node's OCCUPIED EXTENT rather than to its band — the box must stay pinned at the band's bottom, since every edge endpoint and label offset is measured from there, so only what comes after is pushed down. It is an engine option (`chips`) fed from `!!onAddTactic`, because `addSpec`/`addLink` are computed on both wires but only the widget DRAWS chips: reserving unconditionally would give the standalone app a band of empty space under every pending goal. `CHIP_TOP_GAP` also went 4 → 8, since the chips read as stuck to their box. Measured over the corpus plus the incomplete probes, worst-case vertical clearance from a lane's bottom to the next band: **1px before, 24px after** (and negative wherever the successor sat at `TRUNK_GAP_STEP`). The check worth rerunning is that clearance sweep rather than a boolean overlap test — the boolean read 0 even while the lanes were visibly colliding, because it compared against boxes and the thing being overlapped was a case badge, and because no chip-bearing node in the corpus had a child until the duplicate above created one.

**The picker is the chip lane, expanded.** Clicking `calc` or `step` with more than one option REPLACES the lane in place with one ghost chip per relation plus a leading `×`, expanding rightward from the gesture and collapsing back onto it — a row of the vocabulary already here rather than an HTML menu, so it stays inside the SVG with no portal or focus management. **One option is no choice**: the chip then goes straight through to its previous behaviour, which is what keeps the CLI/fallback path and the overwhelmingly common `=`-only case at one click. Picking clones the spec with `rel`/`rel2` (`rel2` set only when the option isn't `same`); a `same` APPEND still commits in one click, everything else opens the overlay for the midpoint — prefilled `_ <rel> ` for a `calc-link`, empty for the midpoint forms. `calcEdit` stays pure and grows one branch: a non-`same` relation writes TWO links (`_ R <mid> := ?_` / `_ S _ := ?_`) instead of one. Widths are MEASURED (`≤`, `↔` and `∣` are not `=`), which forced `FrontierChip` to take a `fontFamily`: `measureText` measures in the editor's code font while the chip painted `monospace`, so the two would otherwise disagree. `picking` holds ranges, so it is dismissed everywhere `editing` is — the `×`, a background click, Escape (a document listener, since the row owns no focused element), and BOTH reset branches, the `shapeKey` one especially, since the edit that just landed is exactly what invalidates it. Verified in the preview over harvested incomplete proofs with a stubbed hook (then reverted): the row renders unclipped, `×`/Escape/background all dismiss and restore the lane, `≤` commits in one click, `=` opens the overlay and commits `rel = / rel2 ≤` with the typed midpoint, and each resulting edit elaborates with nothing but `unsolved goals`.

**Which goal a broken block hangs off depends on how far it got, and the two cases are found differently** (`brokenChainByGoal`, proofToTree). If its FIRST link was complete, the block half-elaborated and a step stands for it, so the goal is that step's `goalBefore` — found by CONTAINMENT of the block's start, innermost (latest-starting) first, because the step may be labelled with the enclosing bullet (`· calc a + 0 = a := by omega`) rather than the calc. If it produced no step at all, the goal is the PENDING one whose producer sits closest above it in the source. **Containment being HALF-OPEN is what keeps the second case out of the first**: the producer above a bare calc has a trivia-inflated range ending exactly AT the calc's start, and an inclusive test would hand the chain that tactic's own goal instead — the same half-open fact the cursor accent rests on. That also means the repair chip is offered on a goal that need NOT be pending, unlike every other chip, so `addLink` is computed outside the `pending` gate. On a broken block the other chips are SUPPRESSED and `step` stands alone on the lane: `+` and `sorry` would insert above a block that stays unparsed, and even `sorry` cannot close a goal the parser never reached. Measured on the scratch file: one `step` chip on the calc's goal, `+`/`sorry`/`calc` still on the two genuinely-unwritten sibling branches, and the corpus's 10 complete proofs unchanged at 0 chips and 0 chains flagged broken.

While verifying this, the multi-line branch of the (+) insertion turned out to be **wrong inside a bullet or a case marker**: continuation lines were indented by the bare `indent`, which is the very column the tactic itself starts at once a `· ` or `| succ k ih => ` prefix is in front of it, so Lean read the continuation as a sibling tactic (`  · have h : p := by` / `    exact hp` fails with "expected '{' or indented tactic sequence" — elaborated, not reasoned about). Continuations now indent past the first line's CONTENT (`indent + prefix.length + 2`).


**Lean's diagnostics, drawn on the tree (`web/src/diagnostics.ts` + the ribbon/pill, widget only).** The tree could read, navigate, edit, insert, complete, delete and undo before this and still showed NOTHING about what had gone wrong — the one thing you most want while writing a proof was the one thing you had to leave the tree for. **The SOURCE is the `getProofTree` payload itself** (`ProofTreeData.diagnostics`, one `TreeDiag` per entry of `doc.diagnosticsRef` — the very ref the publish path and `getInteractiveDiagnostics` serve), and it got there the hard way, through TWO wrong sources. The first build read them off the `textDocument/publishDiagnostics` notification the widget already receives for `docRev`, which is free and WRONG. The notification is EDGE-triggered and a webview subscribes only after it loads, so whenever elaboration finished first — a server restart on a small file, reliably — no notification ever arrived and the feature drew nothing until the next edit. Debugged live over three instrumented rounds that each showed the chain intact (`kept=3`, `byNode=3`) whenever bursts happened to arrive after mount, and empty (`hits=0/0`) on a clean restart: the classic symptom shape of an edge-triggered capture, "works while I watch it". Payload-borne diagnostics are LEVEL-triggered — they arrive with every response, so the drawn errors can never be out of step with the drawn tree, and the notification goes back to being only the refresh signal. The second wrong source was `snap.msgLog`, and it is the sharper trap because every offline probe blesses it: **on the live server the compat snapshot's `msgLog` is EMPTY** — v4.27's file worker rebuilds the old `Snapshots.Snapshot` from the new incremental architecture (`FileWorker/Utils.lean` `mkCmdSnaps`), and the `cmdState` it hands them has its `messages` already drained into the reporting stream that fills `diagnosticsRef` — while the CLI's `IO.processCommands` populates `cmdState.messages` normally, so the msgLog path passes every `lake env lean --run` measurement and returns `[]` in production. What settled it was **driving the real server over LSP from a script** (initialize → didOpen → wait for `$/lean/fileProgress` to empty → `$/lean/rpc/connect` → `$/lean/rpc/call ProofTree.getProofTree`) and reading the actual payload — the recipe to reach for whenever the widget path disagrees with the offline probes, since it needs no VS Code and no round trip through a human. **The probe must initialise with `initializationOptions: { hasWidgets: true }`, as vscode-lean4 does**, or it blesses a third bug the editor still exhibits: the message string must come from `d.toDiagnostic.message`, never `d.message.stripTags` — in widget mode an embed's text lives INSIDE the `MsgEmbed` constructor and the outer tag's subtext is empty, so `stripTags` walks past all of it (measured: 9/9 messages flattened to `""` with widgets on, 9/9 full without — the tooltip showed a bare `⨯`). `toDiagnostic`'s own `prettyTt` recurses into every embed kind, and it keeps the multi-line goal state of an `unsolved goals` (`.goal` embeds print via `g.pretty`). Because the reporter fills the ref ASYNCHRONOUSLY, the diagnostics count is the fourth component of `proofTreeCache`'s key: a request racing the reporter would otherwise cache a partial list under a key that never changes again for that version (the count only grows within one, so settled files stay cached across cursor moves). Client-side they ride `interactive` (the latest in-proof response), NOT `stable`: they are plain data so no ref-lifetime concern applies, and `stable` refreshes only when the proof's TEXT changes while diagnostics can change without it; the span filter still runs against `stable`'s proof, so a response from a different theorem contributes nothing rather than the wrong theorem's errors. **Not the `getInteractiveDiagnostics` RPC**, and that was checked rather than assumed: measured against the v4.27.0 source, the file worker publishes `(sticky ++ doc.diagnosticsRef).map (·.toDiagnostic)` and the RPC serves that SAME ref, with `toDiagnostic` differing only in `message := prettyTt message` — so the RPC buys the message's TAGS and nothing structural, at the cost of a round trip per elaboration burst plus the session-bound-ref lifetime dance; worth having eventually (measured: every one of 10 fixture messages carries 3–26 `expr` embeds once the client asks for widgets) but as a separate on-demand fetch, not as what the ribbon is drawn from.

The module is pure and separate for the `calcEdit.ts` / `deleteEdit.ts` / `lensGoals.ts` reason — a probe drives the REAL filter and the REAL mapping over the real corpus offline — and three of its rules were settled by that measurement rather than by reading. **`proofSpan` prefers the DECLARATION's range**, not the extent of the steps: `declaration uses 'sorry'` is reported on the declaration NAME, above every tactic, so a steps-derived span dropped the one warning that most needs showing. **`UnsolvedGoals` is NOT dropped in the filter**, though the plan said it would be as redundant with the frontier chips: a chip is only offered for a goal reached through `goalsAfter`, and an unfinished `induction` BRANCH arrives spawned — measured, `err_unsolved` leaves the `zero` case open, the tree draws 0 chips for it, and dropping the tag lost the only signal that anything was wrong. It is dropped in `attachDiagnostics` instead, and on a PROOF-level test (does this proof draw any chip at all) rather than a per-node one, because `unsolved goals` is reported at the enclosing block and so never resolves to a node whatever the resolver does. And **the pending-goal fallback matches by LINE, not by position.** A failing tactic has no node — it records no `TacticInfo`, so nothing is harvested for it (the recovery parser now draws many of these, but not the term-position failures `errToSorry` swallows) — so the error falls back to the open goal nearest above, which is both drawn and already carrying the `+`/`sorry`/`calc` chips. Blaming the previous TACTIC was the alternative and is wrong: it worked. A goal's position is its PRODUCING tactic's range, which routinely sits to the RIGHT of the diagnostic on the same line — measured, `unsolved goals` on `| zero =>` reports at column 9 while the goal `skip` left open is positioned at the `skip` itself, so a strict position test found nothing at all. The anchor is `range.start` throughout, which is forced rather than chosen: in `msgToInteractiveDiagnostic` both `range.start` and `fullRange.start` are the same `low`, while `range.end` is truncated to `{line+1, column 0}` for any multi-line message (a VS Code squiggly-size workaround) — a point inside no tactic at all. A null span keeps everything, deliberately: a proof whose FIRST tactic fails harvests no steps (2 of 9 broken fixtures), which is exactly when the diagnostics are the only thing left to show.

**`Lsp.Range` must never cross the wire, and this is the third form of the same lesson.** `proofSpan` reads `proof.declRange`, and the field was typed `Option Lsp.Range` on the RPC side — whose second field is `end`, so its derived `ToJson` emits `{start, end}` while every span the client reads is `{start, stop}` (`ProofStepPosition`). The CLI escaped it only because `Ppharness.lean` hand-serializes that one field and renames `end` to `stop` there, so the two wires disagreed on a single key. It fails LOUDLY on the client — `cmpPos` reads `.line` off an `undefined` stop — but only once a diagnostic exists to compare, so the feature looked simply absent. Fixed by giving the widget wire its own `DeclRange` structure (`start`/`stop`); use it, or an existing start/stop pair, for any new span. The neighbouring half of the same bug: `incoming` in widget.tsx rebuilds the `Proof` FIELD BY FIELD, so a field left out is silently absent rather than a type error — `declRange` was missing there too, and `proofSpan` then fell back to the extent of the STEPS, which begins at the first tactic and so drops `declaration uses 'sorry'` (reported on the declaration NAME). Both halves have to be right, and neither is visible in a type.

**Filtering is widget-side, ATTACHING is view-side, and the split is the same one everything else here uses**: the wire shape and the proof's own span are the widget's business, and which nodes exist is the view's. **The supplemental parser (`lean/ProofTreeRecover.lean`) draws what Paperproof structurally cannot: failed tactics and term-mode proofs.** The vendored parser is goal-identity-keyed and bottom-up — the only relation it can express is "this mvar became those mvars" inside one `TacticInfo` — and two whole classes of proof state therefore had NO representation. A FAILED tactic is an undetectable absence: `evalTactic`'s error handler does `s.restore (restoreInfo := true)`, rolling the failed attempt's info subtree back, and `closeUsingOrAdmit` may then assign `sorryAx` so even the enclosing step's `goalsAfter` looks proved. Measured: a mid-proof failure left a hole in the tree, and a proof whose ONLY tactic failed harvested zero steps AND zero goals — both wires dropped it, so **the tree vanished at exactly the moment it was most needed**. A TERM-MODE proof (`:= term`, no `by`) rendered nothing: the traversal consumes exactly one of seventeen `Info` constructors. The recovery module is the one file allowed to import Paperproof's types (`ProofTreeComments` stays `import Lean` only; never fork the vendored parser — the standing rule), and its single load-bearing design decision is that it **emits Result-shaped data** — real `ProofStep`s and `GoalInfo`s merged into the parse result the moment `BetterParser_Tree` returns, on BOTH wires, before anything reads a label — so `stepByGoal`, layout, folding, comments, brief, elide, token colouring, editing and the diagnostics mapping all work downstream with no new client machinery (`diagnostics.ts` needed ZERO changes: a recovered node's position is the slot's range, so `tacticNodeAt` hits it). `ProofStep` is upstream's type and cannot grow a field, so synthetic-ness rides a SIDECAR keyed by `position.start` (`recovered: [{start, kind: "failed" | "skipped" | "term"}]`), emitted only when nonempty — which is what keeps the complete corpus byte-identical through `gen.sh` (measured, twice). **Part A, failed tactics.** A slot (from `tacticSlots`) is covered iff some step's START falls inside it, half-open; the uncovered set is filtered to outermost-uncovered and minus broken-`calc` slots (that state has its own synthesized node and repair chip). **Uncovered alone is NOT failed** — `skip` records no step either, since `getGoalsChange` cancels a no-op's goals as common — so classification is gated on an ERROR landing inside the slot (the CLI reads its frontend `messages`; the widget reads `doc.diagnosticsRef` — NOT `snap.msgLog`, which is empty on the live path, see the diagnostics paragraph's `mkCmdSnaps` trap: this gate was silently dead in the widget until the payload-diagnostics work drove the real server and caught it); uncovered slots after the failure in the same block are `skipped` (the sequence aborted), chained under GHOST goals (`goal_<line>_<col>` — underscores because `Name.mkSimple "goal:12:2"` serializes with guillemets, measured; each ghost restates its predecessor, which is what a restated box should say — the failed tactic changed nothing). The goal a failure was attacking is found two ways, both measured on the fixtures: a PENDING goal nearest above (the producer's own print — `err_in_run`, `err_tail_skipped`), else an INVISIBLE one from the raw `TacticInfo.goalsBefore/goalsAfter` lists — unconsumed, unproduced, exactly what a failure orphans — printed with the vendored public `printGoalInfo` and **grafted into the `spawnedGoals` of the step whose SLOT contains the failed slot** (slots, not step ranges: an `induction … with` step's range is truncated at its first case marker, the recorded trap, so step-range containment misses its own branches — this bug was hit and fixed by measurement). That graft is what draws an unfinished `induction` branch as a real branch — `err_nested_branch`'s zero-case goal hangs off the `induction` with its case badge for free (the badge rides the GoalInfo's own tag) — and a `have`'s failed `by` side proof as a side branch; with no containing step the goal is the root, which it is (`err_terminal`). Recovered steps' labels are verbatim slot slices (tight stops), so label ≡ source and `alignInLabel` is an identity — the broken-calc argument — and the widget's downstream `tacticEdits`/token/hover pass covers them with no second copy, so a failed tactic is editable, which is exactly what one wants to do to it. **Popout editing — the "lens" (widget + companion extension).** A tactic's hover bar carries a `⧉` button that opens the proof in the **lens**. This deliberately is NOT a modifier gesture: it lived on ⇧-double-click and silently stopped working, because ⇧-click is a **selection-extension** gesture in the webview — it highlights the tree's text and the second click never lands as a `dblclick` (plain double-click kept working throughout, which is what isolated it). Do not re-introduce a modifier here; modifiers on tactics are also wanted for LSP hover work. The button is gated on `onPopoutEdit` ALONE, not on the in-place-editing seam: the lens only needs a range to select, so a tactic missing from `tacticEdits` (which keys on the step's exact start) falls back to the node's own trivia-inflated `position` — selecting slightly more but always opening. Because the bar is the entrypoint, tactic bars are placed differently from goals': `NodeActionBar`'s `placement` prop hangs a tactic's bar off the box's RIGHT edge, vertically centred, since a tactic box is one line tall and the compact gap above it (`TRUNK_GAP_STEP`) is shorter than the bar — the goals' top-right-corner placement would collide with the goal box above. **Both placements overlap the box by `BAR_OVERLAP`, and that is load-bearing, not cosmetic**: the bar renders inside the node's own `<g>` and hover is tracked on that `<g>`, so any gap between box and bar is dead space that fires `mouseleave` and unmounts the bar mid-travel — the pointer can never land on it (the bar literally dodges the mouse). A tactic's overlap falls inside `NODE_PAD`, so it covers padding, not glyphs. The same reasoning fixes the close listener: a vanished column number is not a closed lens, so it re-resolves by the tag before restoring the chrome (otherwise closing an unrelated group un-strips the editor and orphans the lens). To maximize the infoview column, `stripEditorChrome` sets — GLOBALLY, there is no per-window/per-group settings API — `workbench.editor.showTabs: "none"` and `breadcrumbs.enabled`/`editor.glyphMargin`/`editor.minimap.enabled`/`editor.stickyScroll.enabled` false while a lens is open, restored when it closes. Sticky scroll matters more than it sounds: it pins the enclosing `theorem … := by` to the top of the editor, which in a lens a few lines tall eats a large share of the height AND re-renders as the cursor moves between tactics — the jitter you feel while typing. **The lens carries INLINE GOAL STATE (`lensGoals.ts`, the `annotate` action).** `⊢ …` is drawn at the end of each tactic's last line as an `after` decoration, so a proof read in the lens shows its intermediate states the way an Alectryon page does — and it costs no lines and no width the code was using, which is the only reason it fits a pane this small. The text is computed CLIENT-side (the widget holds the proof and the tight line ends) and passed through `popoutEdit`, which grew an `annotations` field; the RPC stays a file writer. LENS ONLY, deliberately — the main buffer has the infoview for this, and stamping every tactic line there would compete with what is being edited.

Three things were settled by MEASURING the real text over the corpus rather than by reasoning, and the first two were wrong on the first attempt. **The line must be the TIGHT stop**, from `tacticEdits`: a Paperproof range includes trailing trivia and runs into the next tactic, so the raw stop put every annotation one tactic late — `induction n using …` labelled with the goal after `intro n`, `omega` labelled with the goal after the `have` above it — a systematic off-by-one that reads as plausible nonsense rather than as an error. **`∎` means BOTH goal lists are empty.** Keying it on `goalsAfter` alone marked every `induction … with` as closed, which is precisely backwards: that tactic branched. So the text prefers `goalsAfter` and falls back to `spawnedGoals`, and only a step with neither is `∎` — note this is NOT `stepGoalsAfter`, which merges them and would label a `have … := by` with a goal belonging to the block underneath it. And **several steps share a line** (a split `rw [a, b]`, a `tac <;> tac`), so the last in SOURCE order wins: the state after the whole line is the only thing one annotation can honestly report. Measured over `proofs/`: 125 annotations, 0 past the end of their file, 0 duplicated lines, 1 clipped at the 72-char cap. Companion side verified in a `vm` sandbox: the lens editor is painted and the main editor never is, a line past the document end is DROPPED rather than clamped (a goal on the wrong line is worse than one missing), the setting off clears instead of painting, no lens is a silent no-op, an empty list clears, and the decoration is an `after` with `isWholeLine` false. Annotations are positional, so the companion drops them on the first `onDidChangeTextDocument` and the widget re-sends whenever the proof it holds changes — gated on having opened a lens at least once, or every re-elaboration would write a relay file for a pane that does not exist.

**Two things buy the lens room WITHOUT a global setting, and they are what the font scale was standing in for.** `foldToCursor` runs `editor.foldAll` then `editor.unfoldRecursively` at the cursor, so everything off the path to the tactic collapses to one-line stubs — the other branch of a `by_cases`, the `have` block you are not in — which is the same cut the tree makes with ⇥/⇳ one surface over. That is why **`editor.folding: false` came OUT of the strip**: disabling folding globally made the commands silent no-ops, and the gutter it was saving is free in a lens that already has `lineNumbers: Off`. It is best-effort by construction — folding ranges come from the language server (or VS Code's indentation fallback), so how much collapses depends on what Lean's server publishes, and with none the commands do nothing and the lens is exactly as it was. `wrapLens` runs `editor.action.toggleWordWrap`, which is the whole point of using a COMMAND rather than `editor.wordWrap`: it flips that editor's own session state, so unlike the font size it leaks to no other editor and no other window. Being a toggle with no "set" form forces two rules — `lensWrapped` (cleared wherever `lensColumn` is) so a second popout does not flip it back off, and a skip when `editor.wordWrap` is already non-`off`, which would otherwise turn the user's own preference off. Both run only while the lens is the ACTIVE editor, since `foldAll` acts on whatever is focused and folding the MAIN buffer instead would be a destructive-feeling surprise far from where the user is looking; both run BEFORE `revealAtFraction`, since both change which lines are visible; and a throw in either is caught, so a missing folding provider costs the gain and never the popout. Exposed as `proofTree.lensFold` / `proofTree.lensWordWrap`, both default on. Verified in a `vm` sandbox over the real source: the order is wrap → foldAll → unfoldRecursively → reveal, a second popout re-folds but does NOT re-toggle wrap (1 toggle, 2 folds), an already-wrapping editor gets 0 toggles, both settings off leave only the reveal, a non-active lens issues 0 fold/wrap commands, and a throwing `foldAll` still reaches the reveal.

**`editor.fontSize` was in that set and has been REMOVED.** It shrank the lens font (a derived scale off the user's own, not a literal) to fit ~4 more lines, and it was the one strip felt everywhere OUTSIDE the lens: settings are user-global, so opening a lens resized the text in the main editor and in every other window. Buying four lines by making the file you are actually reading smaller is the wrong trade, and unlike the chrome keys — margins, tabs, minimap, whose absence costs nothing to read — this one degraded the thing it was meant to serve. `lensShrinkNudges` is now the only height knob. The removal is backwards-safe for crash recovery: `restoreEditorChrome` iterates the SNAPSHOT's own keys rather than `STRIP_KEYS`, so a backup written by an older version still has its `editor.fontSize` undone. **There is no per-editor alternative, checked rather than assumed**: the shipped `vscode.d.ts` gives `TextEditorOptions` exactly `tabSize`/`indentSize`/`insertSpaces`/`cursorStyle`/`lineNumbers` (which is why `lineNumbers: Off` can tag the lens and font cannot), decoration render options have no `fontSize`, and no proposed API ships. Smuggling `font-size` through a decoration's `textDecoration` CSS string does paint smaller glyphs per editor, and is still wrong twice over: VS Code measures character advance width from the CONFIGURED font, so cursor, click hit-testing and selection rectangles stay on the old grid — unusable in a pane meant for typing — and it gains no lines either, since line height derives from the fontSize setting rather than the painted glyphs. Per-window zoom would need a second window, which is the design already rejected above. The global scope is the standing tradeoff for all of these: while a lens is open the MAIN editor is also small-font and sticky-scroll-less (tab-group listener watches `lensColumn` vanish); originals are PID-stamped to `~/.proof-tree-companion/chrome-backup.json` so a crash restores on next activation (dead owner only), and a second window's strip adopts the first's originals instead of snapshotting already-stripped values. The companion also exposes the same action as a `vscode://aidan.proof-tree-companion/edit` deep link for OS-side tooling, and is intended to grow the widget's global settings / persistent state. After changing its `package.json`, a full VS Code restart may be needed (manifest rescan); `extension.js` changes need only a window reload. Widget-side chaff cut to match: no `<details>`/summary wrapper around the tree (the tree is the panel's content), height `calc(100vh − <measured offset>)` (see `useFrameOffset` in the DiagnosticPill paragraph). **The tree has PRIMACY in the infoview column**: the info card's body renders Tactic state / Expected type / panel widgets / Messages as SIBLINGS, and the blocks above a widget resize on every cursor move, bouncing the tree — there is no section-order API, but the widget shares the webview document, so `useSectionOrderCss` (widget.tsx) injects a `:has()`-scoped stylesheet that turns the hosting body into a flex column and orders the tree (`[data-ptw-root]`, set on the tree root AND the placeholder so the slot never flips) first — the volatile blocks flow below it and take space from the bottom, not the top; the infoview's own `<details>` wrapper summary around the widget (it names panel widgets) is display:none'd as chaff. Selectors are scoped entirely on `[data-ptw-root]` so no other infoview surface is touched.

**Interactive subterm tooltips (widget only).** A goal box's label and its context lines' types get the infoview's own hover behavior (type popup per subterm) via core `Widget.goalToInteractive` → `CodeWithInfos` on the Lean side and `InteractiveCode` from `@leanprover/infoview` on the JS side — no ProofWidgets machinery, no vendored parser change. `collectTaggedGoals` in `ProofTreeWidget.lean` is an additive `snap.infoTree` walk that re-prints every tactic's goals with tags kept (the vendored `printGoalInfo` computes the same tagged print and drops the tags via `.fmt.pretty`), keyed by mvarId string = `GoalInfo.id`; it ships as `ProofTreeData.taggedGoals`, which forces the payload to derive `Server.RpcEncodable` (tags hold live `WithRpcRef`s — session-bound, hence never in the CLI's NDJSON). JS-side the seam is two optional `ProofTreeView` hooks (`renderTaggedGoal`/`renderTaggedHyps`, returning ReactNodes per line) implemented in `web/src/taggedRender.tsx` — with `tacticTokens.tsx` (see the tactic-token paragraph) one of only two renderer-adjacent modules allowed to import infoview APIs; the view just swaps its SVG `<text>` for a `<foreignObject>` in the identical line geometry. Three invariants make this safe: **text equality** — a tagged line is used only if its stripped text exactly equals the plain string the layout measured (`taggedRender` checks; any mismatch falls back to plain SVG text per node/line); **no second wrapping** — `web/src/taggedText.ts` slices the `TaggedText` tree at the layout's own line-break offsets (duplicating tags that span a break), so the HTML lines are non-wrapping (`white-space: pre`) and can't disagree with the measured box; and **font normalization** — `InteractiveCode` wraps its output in `<span class="font-code">`, which the infoview styles with the *editor's* font and foreground color, so uncorrected it renders bigger than the measured box (and wrong-colored on our light boxes in dark themes). Every tagged line is wrapped in `.ptw-tagged`, and `taggedRender` injects a `.ptw-tagged .font-code { font: inherit; … }` rule so the rich text inherits the very font the canvas measurer used. The hover popups keep their native editor styling because the infoview portals them to `document.body`, outside any `.ptw-tagged` ancestor. The same injected sheet also fixes a **popup flicker**: the infoview renders a popup's loading (and error) state as a bare TEXT NODE inside `.tooltip-code-content` and its resolved state as real elements, so it would pop up showing `Loading..` and then resize under the pointer. `.tooltip:has(.tooltip-code-content):not(:has(.tooltip-code-content > *))` is exactly "content hasn't arrived", and holds the popup hidden for 150ms before revealing it anyway. Written to apply ONLY in that state on purpose: the resolved popup gets `animation: none`, so it is never delayed AND a failure to animate (a hidden document never advances CSS animations) cannot strand a populated popup invisible — which the tempting "hide all, reveal by animation" shape could. Slow calls and errors still surface, just 150ms later. The same sheet also drops a popup's **empty type line**: the infoview renders `{exprExplicit} : {type}` with the separator UNCONDITIONAL, and core's `makePopup` fills neither field for a `TacticInfo` (it produces `exprExplicit` only for term/field info, and `Info.type?` is none for a tactic), so hovering a tactic keyword — whose whole value is its docstring — used to lead with a line reading just `" : "`. Both halves missing is precisely "this div has no element children" (`.tooltip-code-content > .font-code.pre-wrap:not(:has(> *))`, plus its trailing `<hr>`, or the popup would open on a rule with nothing above it); a popup with a real expr or a real type keeps its line, colon and all. Popup styling otherwise stays exactly as the infoview ships it — it differs from VS Code's own editor hover (which syntax-highlights a signature block), and matching the editor was considered and rejected: the infoview's authors have their reasons, and consistency *within* the panel is what matters. These are the only selectors here not scoped to `[data-ptw-root]`, unavoidably: the popups are portalled outside our subtree, so there is no ancestor to scope on. Both are confined to tooltips carrying code content, so the infoview's menu tooltips are untouched. **Ref lifetime is the subtle part.** `widget.tsx` splits the payload in two: `stable` holds only PLAIN data (proof text, comments, `tacticEdits`) and updates just when the proof text changes, so layout/fold state survives cursor moves; the ref-carrying `taggedGoals`/`tokenInfos` live in a separate `interactive` state tracking the LATEST successful in-proof response. They must not be pinned to `stable`: a `WithRpcRef` is only resolvable in the RPC session that issued it, and a session dies on a worker crash/exit, an `RpcNeedsReconnect`, a server restart or the file closing — after which the client silently opens a new one whose store knows nothing of the old ids. Pinning them meant rendering one arbitrarily old response's refs forever, so after any reconnect every popup failed with `RPC reference 'N' is not valid` and only editing the proof could recover it (`tokenInfos` made it far more visible — one ref per identifier token instead of per goal). Refreshing per response is what makes it self-heal, and a rejected call clears them outright. The update is identity-compared against the response object so `useAsyncPersistent`'s hold-previous-value-while-loading can't loop; responses with no steps (cursor outside the proof) deliberately don't clear it, so tooltips survive a trip outside the proof.

**The widget's RPC path mirrors the CLI's harvest.** `lean/ProofTreeWidget.lean`'s `getProofTree` is `Paperproof.getSnapshotData` (`.tree` mode) minus the single-tactic branch: `withWaitFindSnapAtPos` → `BetterParser_Tree fileMap snap.infoTree` → `{steps, allGoals, taggedGoals}`. No `uri` field is needed: the panel widget already gets it in `props.pos`. The **same v4.27.0 async-tactic caveat applies** — the live server must have fully elaborated the proof for `snap.infoTree` to contain `TacticInfo`; an empty parse returns an empty proof (`steps := []`), which the widget renders as "no proof here" — the not-in-a-proof state is data, not an error-message string for the client to pattern-match.

**Tactic labels are syntax-coloured from the server's own semantic tokens (widget only).** `ProofTreeWidget.lean` runs the very pair the editor's `textDocument/semanticTokens` request uses — `FileWorker.collectSyntaxBasedSemanticTokens fileMap snap.stx` (keywords/syntactic categories) ++ `collectInfoBasedSemanticTokens snap.infoTree` (identifiers classified by what they elaborated to), through `computeAbsoluteLspSemanticTokens` and `handleOverlappingSemanticTokens` — so a token means here exactly what it means in the editor, with no Lean lexer reimplemented in JS. **The server's own token pass misses constants, and that had to be filled in — for the POPUP, not the paint.** `collectInfoBasedSemanticTokens` emits tokens ONLY for identifiers bound to local `fvar`s and for field projections — a constant (`Nat.Prime`, `Nat.strong_induction_on`, `Nat.add_zero`) gets nothing. The first account said the editor colours those from its TextMate grammar, and that is FALSE — checked against the shipped lean4 grammar, which has NO identifier rule at all (keywords, `Prop/Type/Sort`, `sorry`, strings, numerals, attributes, `true/false` — nothing else) — so a qualified constant in the buffer is PLAIN foreground, and painting ours function-blue made the tree visibly disagree with the editor (reported off a `Nat` prefix glowing blue over a plain buffer; on a FAILED ident only the prefix carries a token, the field-notation fallback having resolved `Nat` alone). The token still must exist, because the token list is also what carries the hover popups. So `collectConstIdentTokens` (ProofTreeWidget.lean) fills the gap from the info tree, mirroring upstream's shape (`deepestNodes`, an `.original` head so macro-generated syntax is skipped, `.getAppFn.isConst` because an ident usually elaborates to the constant already applied to its implicits), leaving conflicts to `handleOverlappingSemanticTokens` — and its tokens are reclassified at the WIRE to `"const"` (`wireTokenType`, by start position, so the pipeline the editor shares stays untouched and real `.function` fvar tokens keep their colour). The client paints no unmapped type — `TOKEN_COLOR["const"]` is undefined, so the run inherits the label foreground in the built-in palette and the companion-resolved one alike — which is exactly the buffer's rendering, popup intact. Measured on the wire: `exact Nat.dvd_trans h hbb` crosses as keyword/const/variable/variable and the failed `exact Nat.no_such_lemma n` as keyword/const with `n` token-less, plain in both. All three collectors are merged in one place, `semanticTokensFor`. They ride the EXISTING `TacticEdit` (`tokens : Array TacticToken`, absolute LSP positions), because the tokens index into the same verbatim `text` that entry already carries. JS-side `web/src/tacticTokens.tsx` (no infoview imports; it is plain colouring) turns them into one ReactNode per wrapped line and feeds `ProofTreeView`'s new `renderTaggedTactic` hook, which reuses the *same* `<foreignObject>` render branch as the goal tagged labels. Two invariants: **colour only, never geometry** (tokens change `color`, never the text, so the measured boxes stay honest), and **the LABEL is the coordinate space**. The second one is the whole subtlety. Tokens carry absolute document positions, so they index into the step's verbatim source (`TacticEdit.text`) — but the wrapped lines were measured from the node's LABEL, and Paperproof's `tacticString` is a *display* string that disagrees with that source in three measured ways: the label is a prefix of the source (a structured tactic is prettified to its first line, `induction n with`); the source is a prefix of the label (consecutive binders are merged for display, `intro p hpm`, while the step covers just `intro p`); or the source is *embedded* in the label (`rw` is re-synthesised per rewrite rule, so a step labelled `rw [Nat.add_zero]` has a range covering only `Nat.add_zero` — and for a multi-rule `rw`, covering the rule plus its trailing separator, `List.prod_append,`). **A split step is widened back to the tactic it came from, server-side** (`surfaceTacticRange`, ProofTreeWidget.lean), because the rule range is unusable at both ends: double-clicking a `rw` opened an editor holding `List.prod_append,` — and *inconsistently*, since the last rule has no separator and the synthetic closing `rfl` step's range is the bare `]` — while the tokens, being confined to that range, never included the `rw` keyword, so the label's own `rw` had neither colour nor docstring popup. The answer is the smallest `TacticInfo` containing the step's tight range and starting strictly before it, subject to two conditions that each rule out a real construct and neither of which is sufficient alone: **its first token must be the step LABEL's first token** — the smallest strict container of an `induction n with` step (whose range is truncated at its first case marker) is the enclosing `by` block, and of an `omega` inside `| succ k ih => omega` it is the whole `induction`, while a split step is by construction labelled after the tactic it came out of, which is also what makes the label alignable against the widened source at all; and **it must start on the step's own LINE**, since nested `have … := by have …` puts a `have` step inside an outer `have` whose head token matches, and only the line rules it out (the cost: a `rw` broken across lines widens only for the rules on its first line). Containment must be tested against the step's TIGHT end (`trimmedEnd`), or the trailing-trivia inflation pushes a step at the very end of its tactic (that `rfl`, whose range is the bare `]`) past the tactic that owns it and it never widens. **Do not reach for `tacticIndentAt` here**, which the first version did: it deliberately does not skip a `| case =>` marker (it exists to place INSERTIONS), so on the entirely ordinary `| succ d hd => rw [Nat.add_succ, hd]` it anchored on the `|` and nothing widened at all — the bug survived a probe that only covered `| zero => rfl`, where not widening is the right answer. `TacticEdit.stepStart` keeps the client's key on the step while `start`/`stop`/`text`/`tokens` describe the surface tactic; a consequence worth knowing is that all four nodes of a 4-rule `rw` now edit, hover-highlight and open-in-lens the same whole tactic. Verified by elaborating core-only sources through `IO.processCommands` and running the real `surfaceTacticRange` over `BetterParser_Tree`'s steps: every rule of `rw [Nat.add_zero, h1, h2]` widens (its `rfl` closer too), as do a bulleted `· rw […]`, both branches of `induction n with | zero => rw […] | succ d hd => rw […]`, and the `rw` half of `skip <;> rw […]`; `induction … with`, `| zero => rfl`, `omega`, and every step of a nested `have … := by have …` correctly do not. So `lineOffsets` runs EXACT against the label (the same contract goals use — the lines are `wrapText(label)` by construction), and `alignInLabel` (tacticTokens.tsx) returns the SEGMENTS over which the two texts are known to agree character-for-character (`{labelAt, srcAt, len}` each): a token shifts through whichever segment holds its start and is clipped to that segment's end. Clipping is load-bearing, not defensive — past a segment the label has `]` where the source has `,`, so an unclipped token could colour a character it doesn't own. It returns a LIST rather than one window because widening (above) makes the two-segment case the common one: `rw [hl₁prod]` against `rw [List.prod_append, hl₁prod, hl₂prod, ← hk]` shares the `rw [` head and then the rule itself, wherever it sits in the real bracket list — a single window could only ever cover one of the two, and covering the rule alone is exactly what left `rw` with no colour and no popup. When the label's rule is the FIRST one the shared head already runs through it, and the leftover is the closer the display string added back, so the head segment alone is the answer. Any failure to align falls back to plain SVG text for the node. This started as a prefix-only test (`lineOffsets(text, lines, prefix: true)`), which handled only the first of the three cases and left 12 of `sample.ndjson`'s 86 tactics — every `rw` and multi-binder `intro` — with no colour and no popups; measured after the rewrite, 86/86 align with 0 characters of disagreement inside the clipped window. The probe worth rerunning if this is touched: bundle `proofToTree` + `alignInLabel` with esbuild (`--alias:@leanprover/infoview=…` to dodge the DOM import), reconstruct each step's source from `position` — replicating `trimmedEnd`, NOT a plain whitespace trim, or the trailing-comment cases look like failures that aren't — and assert the label and shifted source agree over every returned segment (86/86 align, 0 disagreeing characters; 76 cover the label's head, and the 10 that don't are precisely the `rw` steps the server now widens).

**Brief mode (the rail's ⋯) collapses boilerplate WITHIN a tactic label to `…`.** The within-tactic analogue of the Alectryon `.fold`/`.none` subtree elision, one level finer — it is the only thing that touches a tactic's own `label` text. `collapseLabel` (`web/src/briefLabel.ts`, a pure string transform, no proof data, so both data paths share it and a probe can exercise it directly) rewrites the label by three conservative, width-gated rules: the RHS of a top-level `:=` that isn't `by` (a binding's derivation — `obtain ⟨m, hmdvd, hm2, hmlt⟩ := Nat.exists_dvd_of_not_prime2 hn hp` → `obtain ⟨m, hmdvd, hm2, hmlt⟩ := …`, keeping the bindings and, on a `have`, the stated type; a `:= by` opens a subtree the tree already folds, so it is left whole); the scrutinee of `rcases`/`cases … with` (`rcases … with h | h`); and an over-long `[ … ]` argument list keeping the first item (`rw [List.prod_append, …]`). Never `⟨ … ⟩` (that is where the binding constructor lives, the point of rule 1), never the head keyword or `with | case` tails, never `induction`'s variable. A fourth rule collapses a **`calc` chain's first line to `calc …`**, and it deliberately INVERTS rule 1 — which is why it has to exist rather than fall out of the others. Everything after the keyword is ALREADY DRAWN, by the TREE rather than by the label: the chain's starting expression is the LHS of the goal box directly above, the first link's relation is the goal box below, and a `:= by tac` justification is that tac's own tactic node. So rule 1's carve-out is backwards here (it keeps `:= by`, a folded subtree, and elides a term RHS) — for a calc the `by` half is the redundant one and a term justification is the only part drawn nowhere else. Measured on the corpus, rule 1 alone fired on exactly the wrong cases: it collapsed `calc a + 0 = a := Nat.add_zero a` and left the 50- and 128-char labels whole. It also normalises a presentation ACCIDENT: `tacticString` is the tactic's first LINE, so how much of a chain lands in its label depends purely on where the author broke the source — the same construct measured 16, 50 and 128 chars across the corpus — while the width gate still keeps a genuinely short head (`calc (a + b) ^ 2`, `calc _ = b := ?_`) whole. The result reads as a small `calc …` marker over the column of link goals the chain-as-column layout already produces, which is what a chain IS. The `…` is a single U+2026, and the assembler normalises spacing around it to read like source (`:= …`, `[a, …]`, `rcases … with p`) — the synthetic spaces belong to no kept run, so the token remap stays exact. **The crux is that the label is the coordinate space for token colouring** (previous paragraph): shortening it would break `alignInLabel`. So the collapse ships as a KEEP map (`TreeNode.elision = { original, keep }`, `KeepSeg = {outAt, srcAt, len}`) and the node's `label` becomes the COLLAPSED string that `sizeOf` measures — brief is therefore an ENGINE-tier toggle (a `proofToTree` option in the engine `useMemo` deps, NOT the paint-only `outline` one). It is deliberately OUT of `viewKey` and sets no `anchorRoot`, unlike reflow: it only shortens some label text, so every node keeps its id and its place in the trunk, and re-centring on the root would scroll you away from whatever you were reading for a change that moved no structure. The shared `[nodes]` anchor pins the node nearest the viewport centre instead — same treatment as ⇉ combine (measured: scroll unchanged and the tracked node holding at 0px drift across a toggle). `renderTacticTokens` then aligns tokens against `elision.original` as before, and adds one compose step — `mapRange(keep, …)` shifts each source-aligned span from original-label space into collapsed-label space, DROPPING any that land in an elided gap — so the kept bits keep their colour and hover popups while the elided ones vanish. Each `…` is a titled pseudo-span (muted, `--ptw-comment`, `cursor: help`) carrying the elided source as a native `<title>` for hover-reveal — no relayout-on-hover, which this codebase avoids everywhere. `elisionsOf` finds the `…` offsets by scanning the collapsed text (robust to those synthetic spaces) and pairs them with the gap texts in order. Composes with reflow for free (reflow wraps whatever label it is handed) and with gallery/side-by-side (placement only). **Brief also elides a `calc` link's LHS to `_`, exactly as the source writes it.** This is the one brief rule that touches a GOAL label rather than a tactic's. A chain's link restates the previous link's right-hand side as its own left-hand side — which the source never writes out (only the first link names its LHS; every later one opens with `_`) and which the tree draws in the box directly above. `chainLhsElisions` (proofToTree) elides a link's LHS iff it is some SIBLING link's RHS. That test is ORDER-FREE, which is what makes it correct: the wire order is not source order (`stepGoalsAfter` puts `goalsAfter` before `spawnedGoals`, so a chain mixing `:= by` and `:= ?_` links comes back reversed), and it degrades exactly right — a TERM-justified link produces no goal at all, so the link after it finds no sibling RHS and keeps its LHS, which is correct since with nothing drawn above it that text is not redundant. The chain HEAD is excluded separately (its LHS is what the source writes on the `calc` line, and it is already the LHS of the goal the chain proves); without that guard a chain returning to its start (`calc a = b … _ = a`) would elide its own head. The label is built by SLICING the original type (`"_" + type.slice(hidden.length)`), so the pretty-printer's spacing is preserved and a mismatch simply leaves the label whole. The subtlety is the widget's tagged renderer, which matches a goal's interactive print against the label by TEXT EQUALITY — a shortened label would fail that and drop the whole goal to plain SVG text, losing every subterm tooltip. `TreeNode.goalElision` carries the hidden text so `computeTaggedGoal` can rebuild the print the same way (`{append: [{text: "_"}, sliceTaggedText(fmt, hidden.length, …)]}`), which reuses the existing line-slicing unchanged; the `_` carries no tag, correctly, since it stands for text that isn't drawn. Verified: the rebuilt flat text equals the elided label and the surviving tags are exactly the RHS subterms (none from the hidden LHS). Measured over `proofs/calc.lean`'s 7 link goals: 4 elide, 0 malformed, and the `calc` chip's offer set is unchanged at 35/59 across the corpus after `spineRelation` was factored out of `calcRelation` to serve both. Standalone app: the collapse still shortens labels (visible), but the titled `…` and colour preservation are widget-only, since `renderTaggedTactic` is only wired there; a failed `alignInLabel` falls back to the plain collapsed text. **Diagnosing the Lean half offline.** The RPC handler needs a live server, but the pieces below it don't: a scratch file that runs `Lean.Elab.IO.processCommands` over a **core-only** source (Mathlib needs `enableInitializersExecution` + `supportInterpreter`, which `lake env lean --run` can't give you) yields real `InfoTree`s, and `mkHoverIndex` / `semanticTokensFor` can then be exercised directly. Two sweeps found real bugs that reading could not: comparing `HoverIndex.innermost` against upstream's `InfoTree.hoverableInfoAtM?` at EVERY byte offset (0 disagreements over 1700 — which is how the hover index was cleared of suspicion), and dumping every emitted token with the info node it resolves to, which is what exposed constants having no token at all. Those helpers are deliberately not `private` so a probe can import them. Token colours come from the shared palette in `web/src/theme.ts` (see the theming paragraph), NOT from the `--vscode-symbolIcon-*` variables — those look like the obvious source and aren't: in VS Code's own defaults only `function`, `variable`, `class`/`enum` and `field`/`interface` carry distinct colours, while `keyword`, `string`, `number`, `type`, `property` and `namespace` all resolve to plain `foreground`, so binding to them would flatten most of a tactic to one colour. There is no CSS variable anywhere in a webview carrying TextMate token colours; the editor's syntax highlighting is tokenized extension-side and shipped as pre-coloured HTML. **The palette is nonetheless read from the user's ACTUAL theme now, the long way round** (`--ptw-tok-*`, overridden inline on the view's root by `ProofTreeView`'s `tokenColors` prop). The webview genuinely cannot do it — re-verified against the shipped `vscode.d.ts`: `ColorTheme` exposes nothing but `kind`, and the whole public API has ZERO token-colour members — but an EXTENSION can, because the active theme is a contribution of some installed extension and its JSON is on disk. So the companion resolves it (`workbench.colorTheme` → the contributing extension in `vscode.extensions.all` → `contributes.themes[].path` → parse, following the `include` chain — Dark+ includes dark_vs) and writes `~/.proof-tree-companion/theme-colors.json`; `ProofTree.themeColors` reads that back, which is the RETURN path the relay otherwise lacks (a webview can't read files and the companion can't reach the webview). It is deliberately its own RPC rather than a `getProofTree` field: that payload is keyed on `(uri, version, command start)`, so a theme switch would not invalidate it and the colours would not change until the next EDIT. The client refreshes on the SAME MutationObserver that already watches the root's `style` for font and light/dark changes, plus a second read 400ms later because the companion writes from its own listener and the two race. **The file is also the only channel a webview has for a VS Code SETTING**, and it now carries two — `editor.bracketPairColorization.enabled` and `proofTree.outlineOnly` — which forced two changes it is worth knowing about. Changing a setting moves no CSS variable, so the observer alone would never see it; there is no push channel here (a file written by an extension, read by the server on demand), so the refetch also rides `docRev` (any re-elaboration) and the webview regaining focus — between them a toggled setting lands as soon as you type in the buffer or click the tree, with no round trip added per cursor move. And `ThemeColors`'s `FromJson` is HAND-WRITTEN, because the derived one does not honour the structure's field defaults: a missing key is an error, not the default. That matters on this wire and nowhere else, since the two ends ship separately — the companion is a dev-installed extension that is easily older than the server. Measured: with the derived instance a `theme-colors.json` written before `outline` existed failed to decode outright, so `themeColors` fell back to `{}` and the user lost the WHOLE PALETTE over one absent flag until the extension host happened to restart. Every field is optional now and a wrong-typed value degrades to that field's default alone, so a new field can only ever be ignored by an old reader and defaulted by a new one (verified against the old-format payload, an unknown-field payload, `{}`, and wrong-typed values). The companion's config listener watches both setting keys as well as the theme and its customisations, or toggling one would not be republished until the next theme change. **The scope map is VS Code's OWN documented default table** (semantic token type → TextMate scope: `variable` → `variable.other.readwrite`, `keyword` → `keyword`, `function` → `entity.name.function`, …), not a hand-picked list. That is what makes it match: with `semanticHighlighting` on — which is the norm — the BUFFER resolves Lean's semantic tokens through exactly this table, so using anything else guarantees divergence. The first version guessed instead, and both guesses were wrong: `variable` asked for `variable.other`, which Catppuccin does not define, so a last-resort "closest sub-scope" pass picked the SHORTEST `variable.other.*` rule in the file — `variable.other.env`, a rule about shell environment variables — painting every Lean fvar GraphQL-blue where the theme's real `variable.other.readwrite` is `#cdd6f4`; and `keyword.control` was preferred over `keyword` on an asserted-not-measured claim about Dark+ (the documented answer is plain `keyword`, and Dark+ then gives #569CD6, not the #C586C0 the built-in palette had used). Ordinary TextMate precedence still applies within a scope lookup (a selector matches a scope it PREFIXES, longer selector wins, ties to the later rule), and the sub-scope fallback survives only as a last resort — with the documented scopes it rarely fires. Verified offline against the real theme files with a stubbed `vscode`: all **26** distinct installed themes resolve all 8 token types with no errors, and Catppuccin Mocha comes back with the values its own JSON states. **What Lean's own tokens do NOT cover had to be measured, not reasoned about**, and the answer is narrower than it looks. Dumping every token for `calc (a + b) ^ 2` (offline, `semanticTokensFor` over a core-only elaboration) leaves exactly `( + ) ^ 2` with no token at all: Lean core emits only `keyword`, `variable`, `property`, `function` (plus `leanSorryLike`) — everything else in `SemanticTokenType` is documented as "not used by the Lean core" — and `collectSyntaxBasedSemanticTokens` pushes a keyword token only for atoms whose first character `isIdFirst` (or `#`), so numerals, operators and brackets are all skipped. Those three are NOT the same case, and treating them alike is what left the tree visibly different from the buffer:

- **Numerals** the editor colours from the lean4 TextMate grammar's `constant.numeric.lean4` rule. We have no grammar, so `collectNumberTokens` (ProofTreeWidget.lean) fills it — the same gap-filling as `collectConstIdentTokens`, from the other end, `.original` atoms only so macro-generated numerals are skipped.
- **Operators** (`=`, `*`, `:=`, `≤`) have no grammar rule EITHER, so they are unscoped in the buffer too and fall to the editor foreground — which is already what the tree paints them (`--ptw-node-text` is `--vscode-editor-foreground`). Emitting our own `operator` tokens would move the tree AWAY from the buffer, which is why `TOKEN_SCOPES` deliberately has no `operator` entry.
- **Brackets** are coloured by BRACKET-PAIR COLOURISATION, a separate mechanism layered on top of tokens (`editor.bracketPairColorization.enabled`, on by default) that cycles six colours by NESTING DEPTH. That is the only thing colouring a bracket in Lean, and it explains why they looked plain in the tree while the buffer showed them coloured. `bracketDepths` (tacticTokens.tsx) reproduces it, applied ONLY to the runs no token claimed so it can never override a token's colour. The six colours are workbench REGISTRY entries, so unlike token colours they ARE exposed to the webview as `--vscode-editorBracketHighlight-foregroundN` and need no companion round trip — only the on/off SETTING does, which rides the same theme payload. Depth uses a STACK, not a counter: a closer that matches nothing is left uncoloured rather than dragging the rest of the line down a level (verified on `f (a] b)`, plus correct nesting on `rw [h, foo (bar [x])]` and `⟨…⟩`). User overrides ride along (`editor.tokenColorCustomizations` / `semanticTokenColorCustomizations`, flat and `[Theme Name]`-scoped, appended last so they win). When theme colours are present the 72%-toward-foreground softening is NOT applied: that exists because a vendor palette is calibrated for its own background, which is exactly untrue of colours read from the theme in use. No companion, no file, or an older server all mean the same thing — keep the built-in palette.

**Per-token hover popups on tactics (widget only)** ride the same token pass. `ProofTreeWidget.lean` ships `tokenInfos : Array TacticTokenInfo` — per token a `Widget.CodeWithInfos` that is one `.tag` wrapping the token's **source text**, carrying the `InfoWithCtx` the editor's own hover would use. EVERY token is offered, not just identifiers: `hoverEligible` mirrors the eligibility test inside `InfoTree.hoverableInfoAt?` (anything with elaborator info, plus field/option/error-name nodes, minus the `nullKind`/`withAnnotateState` steering nodes), so a tactic keyword resolves to its `TacticInfo` — and since `makePopup` ends with `doc := ← i.info.docString?`, which is populated for ANY info kind, that yields the tactic's own documentation. Restricting this to naming tokens was a mistake: the reference text on `induction` or `Nat.Prime` is exactly what makes the widget a substitute for reading the source rather than a summary of it. Tokens with no info node (punctuation, most syntactic keywords) find nothing and cost nothing. That shape is the whole trick: `InteractiveCode` resolves the tag through `Lean.Widget.InteractiveDiagnostics.infoToInteractive` — the same RPC behind the goal-label tooltips and the editor's hover — so the popup is native, and because the tagged text is the SOURCE text rather than a pretty-printed expression, what is drawn is byte-identical to what the layout measured. Cost is controlled two ways, since the token set is now broad. The tree is walked ONCE per request into a `HoverIndex` (items sorted by start, plus a prefix-max-of-stop array) shared by every token — calling `InfoTree.hoverableInfoAt?` per token would re-walk the whole tree on every cursor move — and `innermost` binary-searches then scans backwards, stopping the moment the running max stop falls at or before the query offset, since no earlier item can contain it. And one RPC reference is allocated per distinct info NODE, not per token: a tactic's keyword and punctuation all resolve to the same `TacticInfo`, and `rpcStoreRef` keys on the `WithRpcRef` id, so sharing the value keeps them one store entry (and lets the client reuse UI state for it). The cross-request cache this note used to defer now EXISTS (`proofTreeCache`, a one-entry `initialize`d `IO.Ref` keyed on `(uri, DocumentMeta.version, command start)`): the handler runs on every cursor move but nothing in the payload depends on the cursor beyond which command snapshot it lands in, so walking a proof line-by-line recomputed an identical payload — five info-tree walks plus `collectTaggedGoals` pretty-printing every goal — per keypress. Caching the `WithRpcRef`-carrying halves is SAFE, verified against the v4.27.0 source and worth restating because it looks wrong: a ref's id is minted once by `WithRpcRef.mk`, but session registration happens at response-ENCODE time (`rpcStoreRef` is `StateM RpcObjectStore`, run while serialising into whichever session made the request, and it reuses the same client-side `RpcRef` per `WithRpcRef.id`) — so a reconnected session re-registers the cached refs in its own store and the client-side self-heal is untouched. The document VERSION is what must gate reuse (stale `InfoWithCtx` against an old environment), and it is in the key. The handler also EARLY-OUTS to `{steps := [], allGoals := []}` before all enrichment (tagged goals, tokens, hover index) when the parse yields no steps — the cursor sits outside a proof most of the time, and the client reads none of the rich payload in that state. Note `WithRpcRef.mk`, not `⟨_⟩` — the constructor is private. JS-side `tacticTokens.tsx` renders a token interactively only when `flattenTaggedText(code)` equals the slice being drawn (the same equality guard as goals; it fails for a token straddling a wrap, which then renders as plain coloured text — tooltip lost, geometry intact), which makes `tacticTokens.tsx` the SECOND module allowed to import infoview APIs alongside `taggedRender.tsx` (whose `ensureTaggedStyle` it shares for the `.ptw-tagged` font normalisation). `tokenInfos` is excluded from the stable-proof signature for the same reason as `taggedGoals`: the refs are freshly allocated every call.

**`tokenInfos` is a FLAT list keyed by absolute token position, and must stay that way.** The client indexes it once, globally, and every tactic looks its own tokens up by position. Splitting it per tactic by "which tactic's range contains this token" is wrong and was the bug that made popups look broken for `exact`, `Nat.Prime` and most others: tactic ranges NEST — a structured `induction`/`have` contains every tactic in its branches — so containment resolves to an ancestor, not the owner, and the owner then renders no popups at all. Measured over `sample.ndjson`, 53 of 86 tactics lost their tokens to an enclosing tactic. The same nesting means the server emits a token once per *containing* tactic, so `getProofTree` dedupes `tokenInfos` by position (`seenTok`) while each `TacticEdit.tokens` list stays complete, since colouring is per tactic.

**Hovering a tactic lights up its source range (widget only).** The hover-weight sibling of click-to-reveal: `ProofTreeView.onHoverTactic(pos | null)` reports raw enter/leave, `widget.tsx` debounces it (`HOVER_DWELL_MS`, so sweeping the pointer across the tree sends nothing) and relays `highlight`/`clear` actions through the companion, which paints a `TextEditorDecorationType` (`editor.wordHighlightBackground`) on every visible editor for the uri. **The painted range is narrowed at BOTH ends of the relay, and it needs both.** The widget sends the server's tight span from `tacticEdits` rather than the node's own `position` — a Paperproof range includes trailing trivia, running to the NEXT tactic's first token, so painting it raw bled past the tactic onto the following line's indent — and the tight span additionally drops a trailing comment, which nothing downstream can see. The companion then clamps geometrically in `tightenForHighlight`: to the END of the start line, then back over trailing whitespace. That second layer is what stops a structured tactic lighting up its whole block (`have … := by` spans 13 lines in euclid for a node whose box shows one), and it is the only thing standing for a tactic missing from `tacticEdits`. Verified against the real sources: every euclid tactic paints exactly one line of exactly its own text, and on `commented.lean` the clamp alone would keep `-- split on the parity of m` while the tight range stops at `ih`. **`reveal` and `popout` are narrowed the same way**, by the same `tightenRange`: when a lens is open `showInLens` SELECTS the range, so a raw span selected past the tactic and a structured one selected more than the lens is tall. What must not move is the range's START — the cursor is left there deliberately (cursor-at-start + half-open is the 0-of-86 configuration measured above), and tightening only ever pulls the END back. Verified end-to-end over all 86 tactics by feeding each raw range through the real `tightenRange` and the tightened start back into `tacticNodeAt`: start moved 0 times, 0 selections span multiple lines, 0 collapse to empty, and 0 resolve to the wrong tactic — so the tree↔lens loop still closes. In the main buffer reveal was already conservative: it collapses to a bare caret at the start. Deliberately NOT reveal: reveal moves the cursor and steals focus, which would make hovering unusable. These two actions are the only chatty traffic on the relay, so the companion's log skips them.

**Deleting a tactic or a subtree, and undo/redo from the tree (widget only).** Every other write path here is ADDITIVE, so the moment an attempt went wrong you had to leave the tree and go back to the buffer. Two gestures, split by node type because each is the obvious reading for that node: `⊘` on a TACTIC removes it and any block it OWNS (a `have`'s side proof, a split's branches) but never its linear continuation; `⊘` on a GOAL clears everything below it, which mid-block returns the goal to the frontier where the existing `+`/`sorry`/`calc` chips take over. Ownership is `spawnedGoals` if non-empty, else `goalsAfter` **only if `goalsAfter.length > 1`** — the first half is `NodeFlags.targets`' spawned-first rule, the second is `addSpecFor`'s split gate, and both are needed: a lone `goalsAfter` is a continuation, which a delete must leave standing.

**The unit a delete acts on is a `TacticSlot`, not a step, and that is forced by measurement.** A Paperproof step range is not the tactic as written, in both directions: `intro p hpm` is ONE step covering `intro p ` alone (the label is a merged display string) and `rcases … <;> exact h` is a step covering just the `rcases`, so deleting either tight range strands text; conversely `induction … with` has a step range TRUNCATED at its first case marker while its syntax covers every branch. `surfaceTacticRange` cannot bridge this — it requires the container to start STRICTLY BEFORE the step, and both containers start at the same column — and **it must not be loosened**: its 86/86 alignment behaviour is load-bearing for token colouring, and delete wants the LARGEST qualifying node where colouring wants the SMALLEST. So `tacticSlots` (ProofTreeComments.lean) descends SYNTAX in the shape of the existing `calcBlocks` walk, finds every `tacticSeq1Indented`/`tacticSeqBracketed` and emits its DIRECT CHILDREN — a direct child *is* one tactic as the author wrote it, with no head-token heuristics. Deliberately NOT built from `collectTacticRanges`, which is a flat kind-less list in which a `tacticSeq` carries its own info node at the same offset as its first child, so any largest-container rule swallows the whole block for the first tactic of every sequence. Each slot carries `index`/`count` (the emptiness test), `blockStart` (the sibling key), and three LEXICAL facts the client cannot know because the widget never holds the document text: `lineStart` (whole-line removal is safe), `tailIsTrivia`/`tailStop` (the tail is whitespace and comments), and `prevSameLine` (a sibling shares this line). The whole set ships rather than one entry per step, because the client joins by CONTAINMENT — lifting a deep anchor to its ancestor in another block is then a containment search needing no parent pointers.

`deleteEdit.ts` is pure (the `calcEdit.ts` precedent, so a probe drives production code): the extent is `slot(node) ∪ slot(subtreeLastStep(g))` over the owned goals, lifted into ONE block, then **whole-line delete** when `lineStart && tailIsTrivia`, **exact-range** otherwise (`· intro h`, `{ rfl }`, where whole lines would eat the marker), **declined** on `prevSameLine` (`intro n; simp` — the one destructive gesture here should refuse rather than guess), and **`sorry`** when the extent takes every child of its block. The stub needs no indent computation: the extent starts at the block's FIRST tactic, so its column already is the block's indent, and the `·`/`| case =>` marker is never inside the extent (a bullet is the PARENT slot, a case arm is interior to the `induction`) so it survives — which it must, since dropping `| zero =>` is an "alternative not covered" error. **A comment on its own line above the extent goes with it**, since `attributeComments` already gave it to the node being deleted, but with two floors, and the second one was found by the corpus sweep rather than by reasoning: never reach the previous sibling's last line (a trailing comment there belongs to that tactic), and for a block's FIRST child never reach above `blockStart` — measured on `proofs/calc.lean`, `· -- Chain 1: …` puts the bullet marker and the comment on ONE line and that comment attributes to the `have` below it, so extending would have deleted the `·` and left its branch bodiless.

The affordance is `⊘` in the existing `NodeActionBar`, last so it is furthest from where the pointer arrives, and **one click only ARMS it**: the extent lights up in the buffer, every node inside it dims, and the bar is replaced by a `delete N lines` / `replace N with sorry` chip plus `×`. The confirm chip carries no glyph of its own — the `⊘` said "you may delete here", and once armed that is settled, so what is left to read is the COUNT. Only the second click writes. That is what lets a destructive control live in a hover bar at all — an accidental click costs nothing — and it is the picker-row idiom already here, so it stays inside the SVG with no portal and no focus to manage. `arming` holds RANGES, so it is dismissed everywhere `picking` is (the `×`, a background click, Escape's document listener, both reset branches) **plus on `docRev`**, which is the real staleness protection: it closes the human-latency window between arming and confirming, the only large one. The confirm row is rendered AFTER the nodes loop, like the editor overlay and for the same reason — it hangs below the box where nothing reserves space (`chipH` is budgeted only where an add/link chip lives), so inside the node's own `<g>` every later sibling would paint over it. The preview rides a NEW relay action (`preview`), not the hover one: the companion clamps `highlight` to the end of the START line, which is right for "the tactic you are pointing at" and exactly wrong for an extent that is routinely many lines. Suppressed on combined (⇉) and elided markers and on the synthetic broken-`calc` node — all map to several source ranges or to text the repair chip owns, the same reason editing is off there. The gesture is DELIBERATELY not offered where `deleteExtent` declines, so the button never appears promising something it will not do.

**Undo/redo had to come with it.** Every edit the widget makes leaves focus in the WEBVIEW, where ⌘Z reaches nothing at all — so before this the only way to undo a tree edit was to click into the editor first. `undo`/`redo` are focus-dependent VS Code commands with no document-targeted API, so `runEditorCommand` (extension.js) resolves the editor for the uri (lens via `findLensColumn`, else the visible editor), focuses it, then `executeCommand`. Focus moving to the editor is unavoidable and also the better behaviour: you land where the change happened, and every subsequent ⌘Z is native, which keeps repeats off this one-shot relay entirely. Reachable as `↶`/`↷` at the top of the rail, divided off because they change the FILE where everything else changes only how it is drawn, and as a document keydown skipped inside a textarea so the in-place editor keeps the browser's own undo. Both new actions are explicit branches BEFORE the `else` in the companion's dispatch — an unknown action there falls through to `popout`.

**`documentChanges` was checked and rejected rather than assumed.** `ec.api.applyEdit` types as a full LSP `WorkspaceEdit`, so a versioned `TextDocumentEdit` typechecks — but vscode-lean4 runs `p2c.asWorkspaceEdit` then `vscode.workspace.applyEdit` directly, and the version guard (`{applied:false}` on mismatch) lives only in vscode-languageclient's SERVER-INITIATED handler, which this path never reaches. The version is silently dropped, and its `if (1 !== entries().length) return` additionally makes a non-conforming edit a silent no-op. So the delete stays on `changes` like every other write here (one undo entry, the editor's own pipeline), and safety comes from disarm-on-`docRev` plus the fact that slots ride `proofTreeCache`, already keyed on `(uri, DocumentMeta.version, command start)` — a payload can never mix a fresh tree with stale ranges.

**Measured.** Tier 0, over a core-only corpus shaped to hit every tactic form (`IO.processCommands`, the documented recipe): 44 slots / 38 steps, **0 slot slices that fail to re-parse as one tactic, 0 sibling overlaps, 0 steps with no slot**, with `induction n with | zero … | succ …` resolving to ONE slot spanning all four lines (26:2 → 29:25) where the step stops at 27:2, and both steps of `constructor <;> exact hp` resolving to the same whole slot. Tier 1/2, applying the REAL `deleteEdit` output to that corpus and re-elaborating in-process: 72 edits applied, 4 declined, **0 structural failures, 0 step growth, 0 surviving tactic mutated**. Tier 3, over `proofs/*.lean` with Mathlib: **306 mutants, 0 structural failures** — 140 elaborate with no errors at all, 110 leave only `unsolved goals`/`sorry`, and 56 have SEMANTIC fallout, which is inherent and not a defect (deleting `intro n` must break the `hn` under it; that class is what the gesture means). The classifier is worth restating because it is the whole discipline here: **benign** (unsolved goals / sorry) is the deletion working, **semantic** (type mismatch, unknown identifier) is the necessary consequence of removing a step, and only **structural** (a parse failure, or a `with` block that lost a case) is a bug — and the test for it must be narrow, since "expected" also appears inside "but is expected to have type". Plus a pure sweep over all 524 specs of the corpus: 0 extents CROSS a slot boundary (nesting either way is fine — an ancestor properly contains the extent and shares its start; only half-in-half-out means the edit cuts a tactic in two), 0 whole-line edits on a slot that is not line-initial, and 0 comment extensions crossing a node boundary. That crossing sweep is the one worth rerunning if this is touched: it is what caught the bullet-eating comment bug, and a naive version of it reports hundreds of false positives from ancestors and from trailing-trivia tails. Verified in the preview with stubbed hooks (then reverted): arm paints the exact extent (`ring` → 32:50–32:54, byte-checked against the source), the chip reads `replace 1 with sorry` for a lone tactic in a `by` block and `delete 1 line` for a term-`have`, Escape and the `×` both disarm and clear the preview, confirm fires ONCE with the right spec, and the rail button and ⌘Z both reach `onUndo`. The standalone app passes no hooks, so it draws no `⊘` and no `↶`/`↷` — verified.

**Known edges, accepted.** A tactic nested inside a combinator (`try simp`, `repeat constructor`) resolves to the INNER slot, so deleting it yields `try sorry` rather than removing the whole `try simp`; the file still parses, which is the invariant that matters, and no corpus proof contains one. All four nodes of a 4-rule `rw` share one slot and therefore one delete, consistent with their already sharing one edit and one lens. The armed dimming keys on a node's own `position` falling inside the extent, so a goal PRODUCED by the deleted tactic dims too — correct in the sense that the goal as drawn will not survive, though the goal itself may. Deleting an individual `calc` link is out of scope: a chain's links restate each other's endpoints, so removing one has consistency implications the `?_` machinery should own.

Note `deleteSlots` rides the CLI wire too (`Ppharness.lean`), like the calc seams and for the same stated reason — it is plain data, and it is what lets a probe run the real client-side extent maths offline. `web/public/sample.ndjson` therefore grows by ~40KB; the standalone app reads the field but draws nothing from it.

**Named cases get a badge.** A goal produced into a named branch (`induction … with | zero | succ`, `by_cases` → `pos`/`neg`, `rcases` → `inl`/`inr`) carries `TreeNode.caseLabel`, drawn as a small hue-free tag at the very top of the node's band — above the comment strip, mirroring source order (the case marker precedes any comment inside it) and aligned with it, so an annotated branch reads as one left-aligned column. Two things make it usable rather than noise: Lean's tag arrives with the MACRO-HYGIENE suffix attached (`pos._@.282783777._hygCtx._hyg.77`), so everything from `._@.` on is dropped and `[anonymous]`/`_` get no badge at all; and a case tag PROPAGATES to every descendant goal, so the badge is emitted only where a case is ENTERED (`thisCase !== parentCase`, threaded down the DFS) — unconditionally it stamped `neg` on all nine goals of one factorization.lean branch. Lean's tag is also the full case PATH, so a badge shows only what its goal ADDS to the parent's (`refine_1.calc.step` under a box already badged `refine_1` reads `calc.step`; `neg.refine_1.inl` reads `inl`). Where there is no parent badge to strip against the full path stands, which is right — nothing above is carrying the prefix. Geometry mirrors the comment strip exactly (`caseSize` → `caseH`/`caseW`, joined into the band and the width in both layout modes).

**Source comments render in the tree.** Comments are parser trivia — never in the `InfoTree` — so both data paths re-lex the *raw source* of just the proof's command through the shared `lean/ProofTreeComments.lean` (its own `lean_lib`; handles `--`, nested `/- -/`, strings, char literals) and ship `comments: [{text, start, stop}]` on the wire (CLI: extra field in `resultToJson`, range from a `commandRange` fold over the InfoTree; widget: `snap.stx.getRange?`, and the field rides the stable-proof signature). The range is extended to its final line's end because a syntax range's stop excludes trailing trivia — exactly where a last-line trailing comment lives. The theorem's docstring falls inside the command range **deliberately**. Attribution is JS-side and source-agnostic (`attributeComments` in proofToTree.ts), built around one quirk: **Paperproof step ranges include trailing trivia**, so range-containment IS the trailing-comment test (`simp -- c` puts the comment inside `simp`'s range). Rules in order: contained in a step → if the comment starts on that step's OWN first line it is its trailing comment and stays; otherwise it sits on its own line inside the inflated range and belongs to the next step starting at-or-before the container's end. That bound must be INCLUSIVE — trivia inflation makes the next step start exactly AT the container's stop, so the strict test this used to run never fired and every leading comment fell onto the PRECEDING tactic (`-- Step 2: apply it to N! + 1` was drawn above the previous branch's last `exact`, and the cursor accent jumped there with it); entirely before the first tactic (incl. the docstring) → the ROOT goal ("the plan" slot); else next step by start; else the previous step. The same trivia quirk means tactic labels can carry their trailing comments verbatim — `cleanLabel` scrubs every comment's exact text out of them. Rendering: an italic, muted, box-less strip at the very TOP of the node's band (comment → box, mirroring source order): `commentSize` in layout.ts wraps it via the shared wrapper *measured italic* (italics are wider) at `COMMENT_FONT_PX`, with NO hanging indent and looser leading (see the reflow paragraph's `indentMode`), `commentBlockH` joins the band and `commentW` the effective width in both layout modes. In compact mode a parented node's strip hangs INDENTED off the incoming connector (`COMMENT_INDENT`, git-graph style): the straight trunk lane runs continuously past the comment down to the node's box, so the strip annotates the lane instead of interrupting it — root comments (no incoming lane) stay flush-left, and wide mode keeps centered strips. `proofs/commented.lean` exercises every rule.

**Alectryon-style display flags.** A comment whose first word is a flag — `-- .fold`, `-- .none why this is dull` — is a DIRECTIVE, not prose: the proof source itself says how the tree should draw the part it introduces. This is Alectryon's vocabulary (already reachable from Lean via LeanInk) translated to a tree, and it rides the comment pipeline entirely: `parseFlags` (proofToTree.ts) runs on the already-attributed comment, so a flag lands on exactly the node whose strip the comment would have been, and the whole feature is source-agnostic — the CLI corpus (`proofs/flags.lean`) demonstrates it in the standalone app with no widget involved. Flags are recognised only at the START of a comment and only on its first line, and scanning stops at the first word that isn't one, so `-- see .fold above` and `-- .5 of the cases` stay prose (`ParsedFlags.any` is what distinguishes a directive from a comment that merely begins with a period). A well-formed but unknown flag is CONSUMED rather than echoed: Alectryon's vocabulary is bigger than the part that means anything here (`.in`, `.messages`, `.g#1`), and leaking those into a strip would be noise. **The four that do mean something split into two groups, and they resolve to different nodes — that asymmetry is forced, not sloppy.** `.fold` / `.none` govern the OUTPUT of the tactic they precede, which is Alectryon's own framing: `.fold` seeds the collapsed set (a starting view — unfolding by hand still works, and ⊞ expand-all opens it), `.none` joins the `hide` set the gallery already threads into `computeLayout`, so the subtree is gone with no fold glyph and ⊞ does NOT bring it back. Both act on `NodeFlags.targets` — the tactic's **spawned** goals when it has any, else the goals it produced — and never on the tactic node itself. Two reasons, and each is load-bearing. Collapsing the TACTIC would hide the goals with it, leaving nothing on screen to say what was folded away; targeting the goals draws each box with a fold glyph, which is much closer to Alectryon's "output shown but folded". And spawned-first is what keeps a flag on a `have … := by` from swallowing the rest of the proof: such a step has two children, the side proof it opened and the continuation of the main line, and "hide this have's proof" plainly means the former — measured on `proofs/odd_sums.lean`, `.fold` on its `gap` step folds the side goal while `have parity` and everything after it stay drawn, and `.none` on the inner `have hodd` elides the algebra while its own `exact` continuation survives. A real case split has no spawned goals, so there the targets are simply all the branches. But `.no-hyps` / `.h#name` (repeatable) narrow the context of the goal the tactic CONSUMES, because the output reading does not survive the translation: a tree draws a goal ABOVE its tactic rather than after it, and a closing tactic like `omega` has no output at all — so `-- .no-hyps` written above the `omega` in a bullet branch, which is exactly where an author would write it, would silently do nothing. Hypothesis flags INTERSECT with the rail's breadth rather than overriding it (filtered after the mode, so a named hyp the current mode wouldn't show stays hidden and ∀ reveals it), and they are consumed in `contextFor`, so they never reach a `TreeNode` — only `fold`/`elide`/`note` do (`NodeFlags`). Prose after the flags is kept: normally it becomes the node's comment strip as usual, but on a `.none` it moves INTO the elision marker instead of being drawn twice. That marker (`ElidedMarker`, a dashed hue-free chip) REPLACES the flagged tactic's box outright — the box, label and fold glyph are suppressed and the chip is drawn in their place (vertically centred in the box's slot, `isElided` in ProofTreeView) — so the whole elided step reads as one dashed note in the trunk rather than a live green box trailing a secondary strip (which looked like a stray child node). The node stays in layout, so the connectors in and out of it are unchanged and the continuation below still attaches. It is the "elided features replaced with associated comments" half, and exists because silently dropping a subtree reads as a proof that simply STOPS; it is deliberately inert, so `.fold`'s toggle and `.none`'s finality stay visibly different things. A flags-only comment draws no strip and therefore claims no `commentRanges` entry — that map means "the node whose strip is SHOWING this" and the widget's cursor accent trusts it, so an invisible comment must not appear in it (the accent falls through to plain containment there). Verified in the standalone app over `proofs/flags.lean`: `.no-hyps` gives its goal 0 context lines and `.h#hn` exactly 1, `.fold` starts collapsed and opens on click, and `.none`'s subtree survives both a hand unfold and ⊞ expand-all while its marker stays put. Related: the view distinguishes a NEW PROOF from an EDITED one, and conflating them is what made structural editing painful. **`proofKey` is the DECLARATION NAME** (`ProofTreeData.proofId`, from `declName?` in ProofTreeWidget.lean; `rootIds` is the CLI fallback), and only a change there resets fold/zoom/sequence/focus and re-centres. It used to be the root goal's mvarId, on the measured basis that adding or deleting a tactic keeps it — **and that is the single mistake this file should warn hardest about, because it recurred FOUR separate times.** A node id here is an mvarId, i.e. an ELABORATION-ORDER artifact: it is stable only while an edit doesn't change how many metavariables are allocated before it. A `calc` insertion introduces a `?_` and so changes exactly that. Measured on the scratch file, adding one link to `calc_workout` changed that theorem's OWN root id and renumbered **34 of 34** ids in the theorem below it — so the proof being edited "became a different proof", the view reset, and the author was scrolled back to the top of the very proof they were working in (measured in the preview: scroll 1030 → 720, where 720 is exactly the re-centre target; with a stable identity the same edit holds at 1267, moving only by how far the anchored node moved). **The general rule: view identity and view state must key on SOURCE facts — a declaration name, a source position — never on anything elaboration mints.** mvarIds are fine for matching nodes WITHIN one payload (that is all they are for); the moment one is used to decide "is this the same thing I was just looking at", it will be wrong under some edit nobody has tried yet. The same reasoning already fixed the cursor-tracking effect (keyed on `hlKey`, the cursor, never on the resolved node id) and is why `shapeKey` only prunes. `shapeKey` (all step goal ids) still changes on any structural edit, but now only PRUNES: collapsed ids, a focus root or a sequence endpoint are dropped when they no longer refer to a live node, and scroll/zoom stay put. Previously the reset keyed on `shapeKey`, so adding a tactic from a (+) chip — or deleting one in the buffer — threw away fold state and scrolled back to the root, i.e. away from exactly where you were working. Verified with real re-harvested proofs: add/delete/mid-insert all classify as PRUNE, a different theorem as FULL RESET, and the prune set equals the node set exactly (0 live nodes dropped) so a fold set survives an edit intact. Keeping the STATE, though, is not the same as keeping the VIEW: an arriving proof rebuilds the engine and moves boxes while scroll stays at the same NUMBER, so the tree slid under the viewport with nothing holding it. **Every relayout is now anchored, not just the gestures that ask for one.** `anchorOn(id)` (folds, and now a commit / `sorry` chip, which pin the node being edited) still wins — **but only if that node is still there after the relayout**, which for an edit is exactly what it may not be, since re-elaboration renumbers every goal downstream of it. A named anchor that no longer resolves now FALLS THROUGH to the viewport-centre rule instead of silently doing nothing, which was the worst of the three options: the layout moved, the scroll didn't, and the tree slid under the viewport. Where nothing named an anchor — an edit landing, the buffer re-elaborating, a context-breadth or font change — the node nearest the viewport's vertical centre stands in, since that is what you were looking at. **How a node is matched to ITSELF across the relayout is `layoutKeys` (`web/src/layoutKey.ts`, its own pure module so a probe can run the REAL matcher over two harvested proofs), and it keys on the node's SOURCE POSITION, never on its id — this is the fourth instance of the rule above, and the sharpest, because the mechanism that exists to hold the view still was itself keyed on mvarIds and so was defeated by exactly the edits it was written for.** Both `lastLayoutRef` and `anchorRef` carry the key; a node with no position at all (root goals, whose span is the theorem statement rather than any tactic's — one per proof) falls back to the id. That is what fixes SCROLL-ON-COMMENT-TOGGLE, the symptom that exposed it: a `--` toggle shifts columns on ONE line and no line numbers at all, so position survives it exactly, while commenting a single tactic near the top of a proof renumbers nearly everything below. Measured on `proofs/odd_sums.lean` (harvest, comment out one line, re-harvest): commenting `intro m` matched **8 of 69** nodes by id against 69 of 69 by position, and commenting a leaf `ring` 17 of 79 against 79 of 79 — in both cases every id that survived sat at or ABOVE the edit, so the anchor pinned an unmoved node above the viewport, computed a zero shift, and let the content in view slide. In the preview, with a control run against the id-keyed lookup: **1224–2006px of drift (up to ~3 viewport heights) before, 0px after**, in both directions, with scroll moving by exactly ∓626 — commenting and uncommenting are exact inverses. Note position is never WORSE than the id: an insertion renumbers ids below it and shifts lines below it, so both schemes miss below the edit and both hit above it. **When the node you were ON is the one the edit DELETED — which is what commenting a tactic out does — there is nothing to hold still, and the viewport-centre rule has to guess from whatever else survived.** It guesses badly, because "survived" means the source position survived, and a position can outlive its place in the tree: measured on the scratch file, commenting out `_ ≤ _ := by linarith` (the last well-formed link of a chain, so the block stops parsing and takes two sibling branches with it) leaves the `ring` on the line above matching by position while moving from y 955 to y 377 and re-indenting, so anchoring on it lurches the view. So `cursorChainRef` records the cursor's node and its ancestors as `layoutKeys` keys for the layout last drawn (its own effect, declared AFTER the anchor effect so a relayout still sees the previous layout's chain, while a cursor move alone updates it in place), and a vanished cursor node falls back to the nearest surviving ANCESTOR — here the `calc` head one line up, literally the tactic above the one commented out — which is then also scrolled INTO VIEW rather than merely held put, since the subtree under it just disappeared. Gated on that node having been ON SCREEN in the layout being replaced: if you were reading elsewhere while an edit landed somewhere else, what you are looking at is what should stay put. **Horizontal is followed only in WIDE mode**, and the asymmetry is in the two layouts' coordinates rather than in taste: wide is a centred Sugiyama tree whose every x carries a global offset that moves with the tree's overall width, so following the anchor's dx is what CANCELS it, whereas compact pins the root's left edge at x = 0 and indents from there, so an x is absolute and moves only when that node's own indent does — following it then scrolls sideways for a reason the reader cannot see and pulls the left-aligned trunk off screen. The cursor-tracking effect's own compact nudge had the matching bug from the other direction: it fired when a box SPILLED past the right edge and could then only scroll RIGHT, so a box wider than the remaining width triggered it even with its left edge perfectly visible and the view walked rightward once per cursor move, never back — the rightward creep felt while toggling comments, since each toggle moves the cursor. It now tests the box's LEFT EDGE against the comfortable band and brings it to `COMPACT_LEFT` from EITHER side: a box whose start you can already see is left alone however far its tail runs. Verified in the preview with a faithful fixture (the swapped proofs carry a stable `proofId`, or the standalone app's `rootIds` proofKey makes every swap a full reset and re-centres, masking the anchor entirely — a harness trap worth remembering): commenting line 181 of `calc_workout` drifts the trunk 0px horizontally, drops `linarith`, and moves `calc (a + b) ^ 2` from the viewport's top edge into comfortable view, at 1600px and 466px widths alike. Two things this deliberately does not reach: nodes can legitimately SHARE a position (a tactic's `goalsAfter` all carry their producer's range), so a running ordinal over the DFS-preorder node list disambiguates; and `collapsed` is still id-keyed all the way into `computeLayout`, so `shapeKey`'s prune drops fold state below an edit — the remaining piece of view state on the wrong side of this rule. Pinning the EDITED node is the stronger case and why the commit path sets one explicitly: a tactic can only affect the proof below it and the compact layout walks a single y-cursor in DFS order, so everything above the edit is then literally unmoved. The subtlety is measuring the delta from the right base — `el.scrollTop` at effect time is already the browser's CLAMPED value when the new layout is shorter, so `lastScrollRef` holds the scroll that was showing the previous layout, fed from two sources because neither covers it alone: a `scroll` listener (the user, and the wheel handler) plus a no-dep `useLayoutEffect` declared after every scroll-writing effect (programmatic scrolls) — scroll events ride the rendering steps, which a hidden webview never runs. Reading the scroll during render would be the tidier single source and is what eslint's `react-hooks/refs` forbids. Measured in the standalone app by swapping in a mutated proof (same ids, one tactic grown by N lines): every visible node holds at 0px and scroll moves by exactly the growth — +32 on a 2-line grow mid-tree, −320 on a 20-line shrink taken from the very bottom of the scroll range, i.e. through the clamp. Related, and the other half of the reported jumpiness: the cursor-tracking effect is keyed on the CURSOR (`hlKey`), never on the resolved node id. Ids are mvarIds, so a re-elaboration mints new ones for everything downstream of an edit — an id-keyed guard read that as "the cursor moved to a new node" on every re-parse and smooth-scrolled the view away while the cursor had not moved at all. The preview harness CAN exercise all of this, but only after a `computer{screenshot}`: the pane lays out no height until then (`clientHeight` 0, which also short-circuits the centering effect's own `viewport.w === 0` guard), and because the tab is hidden it dispatches no scroll events of its own — a programmatic `scrollTop` write needs a synthetic `new Event("scroll")` after it, or the anchor measures from a stale base and every reading is off by the difference.

**Outline-only** rides the same mechanism from the other end: it stamps `data-ptw-fill="none"` on the same root and a last-in-the-sheet block (same specificity, so source order is what makes it win) swaps the three fill variables to `transparent`, leaving the borders to carry goal-vs-tactic. No render site changes and no relayout — it is purely paint. Transparent rather than the page colour because the layout's bands are overlap-free by construction; verified by sampling points inside every node box in BOTH layout modes and checking no connector path is hit (0 of 171). It is a **SETTING, not a rail button** (`proofTree.outlineOnly`, widget-only): it is a standing preference about how boxes look rather than a gesture you reach for while reading a proof, and the rail is for the latter. It therefore arrives as a `ProofTreeView` prop over the same companion→file→server channel as the token colours (see below) — the only channel a webview has for a VS Code setting — which costs the standalone app the toggle entirely, since there is no companion there to set it. **Colour follows the editor's theme (`web/src/theme.ts`).** Every drawable colour — node fills and strokes, label/context text, comment strips, connectors, the accent, and the syntax-token palette — is a CSS custom property on `[data-ptw-theme]`, which `ProofTreeView` stamps on its own root; render sites carry `var(--ptw-…)` strings, so a theme switch is repainted by the BROWSER with no React render on the paint path (the chrome already worked this way with `--vscode-editorWidget-*`; this extends it to the tree itself). Scoped on `data-ptw-theme` rather than widget.tsx's `data-ptw-root` because the standalone app has no such wrapper, and a second copy of that marker would disturb the section-order sheet's `:has(> …)` selectors. **The light/dark split is deliberately ONE decision.** Node fills used to be fixed light pastels, which is precisely why the token palette had to be fixed light too — theme-following tokens would have gone light-on-light; fixing only one half swaps that for the mirror bug (a dark box under light-palette tokens), so both hang off the same stamp and cannot disagree. That stamp is derived from the background's LUMINANCE (`resolveThemeKind`, Rec. 601 luma < 0.5), not from VS Code's `vscode-dark` body class: luminance is the question that actually matters ("will light ink read on this?") and it answers correctly for custom themes, high-contrast themes, and hosts that aren't a webview at all. It reads `--vscode-editor-background`, then the body's computed background, then the root's — skipping a fully transparent one, which is not hypothetical: the standalone app's body is `rgba(0,0,0,0)` and only the fall-through gets it right. Refreshed by the SAME MutationObserver that already watched the root's `style` for font changes (plus the body's `class`/`data-vscode-theme-kind`, which a light↔dark switch can hit first). **Everything is anchored to the theme's own background and foreground**, which is what makes it work for a theme nobody here has seen: `--ptw-bg`/`--ptw-fg` are the editor's, and every other value is a `color-mix` of a hue INTO one of them. Hue is used sparingly and only where it carries meaning (goal vs tactic vs keyword). The RECIPES are written once in the base block and the dark block overrides only their INPUTS (`--ptw-surface`, the hues, the bg/fg fallbacks) — custom properties substitute lazily at use time, so one recipe picks up whichever inputs are in scope. Nodes sit on `--ptw-surface`, a shade LIGHTER than the page (in a dark theme, the background lifted 10% toward the foreground), so a box still reads as a raised card; on Catppuccin Mocha that derives to `#2F3042` against the theme's own `surface0` of `#313244`, which is the check that the derivation is right rather than tuned. Syntax tokens are the raw Light+/Dark+ hue pulled 72% toward `--ptw-fg`, so a soft theme gets soft tokens: the FIRST attempt used those palettes verbatim at full saturation and read as neon on Catppuccin, because a vendor palette is calibrated for its own background and foreground, not someone else's. Context lines carry no hue at all — plain foreground, unused ones dimmed to 62% (not lower: they are real content, and on an already-soft theme the dim compounds with the theme's own softness). Contrast was measured across Mocha/Dark+/Gruvbox/Nord/Light+/Solarized-Light: label-on-fill 6.3–14.2 and dimmed-hyp-on-fill 3.4–4.1 everywhere except Solarized Light, whose own foreground is only 3.7 against our fill — that ceiling is the theme's, not ours, and matching it is the point.

**Eliding nodes on demand — two cuts, one collapse mechanism (`web/src/elide.ts`).** Both hide a set of nodes by collapsing it to a single dashed `⋯ N tactics` marker the tree flows through, applied as a **pure `TreeNode[]` → `TreeNode[]` transform run BEFORE the engine** (`applyElisions`), not a `computeLayout` mask — a mask can only hide SUBTREES (the fixpoint sweep takes everything below with it), whereas an interior cut must KEEP what hangs below. An `ElideCut` is one of two kinds: **path** (the rail's **⇥**, the REVERSE of linearize) — a picked ancestor→descendant path (`pathIds`), the goal-structural cut; or **band** (the rail's **⇳**) — every node whose VERTICAL position falls between two picks in the compact outline (`{kind:"band", ids}`), the purely GEOMETRIC cut. `applyElisions` resolves each cut to an id-set, replaces it with one marker emitted in the set's TOPMOST slot (min index in `nodes`, so DFS-preorder position is preserved), gives the marker the remapped UNION of every set member's parents (a path yields `from`'s parents; a band may yield several → a **multi-parent marker**, which the trunk layout tolerates by design — placed once, one connector pushed per parent, per the DAG guard), and RE-PARENTS every edge that pointed into the set onto the marker so nothing below is orphaned. It reuses every downstream feature for free — layout, folding, srcRank/ORD ordering, the render path — because the collapsed nodes simply aren't in the tree the engine sees; the marker is a real node (`TreeNode.elidedCut`), a dashed unfilled chip in muted comment ink with the elided tactic labels in its `<title>`, and clicking it removes the cut (matched by the marker's `id` = `cutId(cut)`; un-elide is one click, in any mode — the `elidedCut` check runs first in `onNodeClick`). Cuts live in `elideCuts` state (an engine dep, like `brief`); path cuts key on ORIGINAL ids validated over `baseNodes` (the pre-elision tree), reject overlap, and re-derive across edits. **The band is computed at pick time from the live post-layout `.y`** (`commitBand`): `[lo,hi]` of the two picks' band centres, every placed node with `lo ≤ y ≤ hi` (INCLUSIVE — the two picks are cut too), frozen as base ids like a fold set; a marker caught in the band is ABSORBED (its nodes rejoin the new band, its own cut dropped) so cuts stay disjoint with no merge logic. The band only makes sense where `y` is a total vertical order — **compact STACKED mode** — so the ⇳ button is disabled in wide (y = depth, many share it) and side-by-side (columns share y) mode; already-committed band cuts still render in any mode. The three picking modes (sequence, path-elide, band-elide) are mutually exclusive. `pruneCuts` drops cuts that no longer resolve (endpoints/lineage vanished, or an empty band) on the shape-change hook. Verified over the whole corpus (0 dangling parents, marker drawn, above/below preserved; a cross-branch band on euclid → a 2-parent marker drawing 2 connectors, one sample → a 3-parent marker) and end-to-end in the preview (band cut collapses and the chip restores it; the ⇳ button greys out in wide/side-by-side). **Combining tactic nodes (the rail's ⇉) is the SIBLING of this, and rides the same collapse** — a third `ElideCut` kind whose synthetic node renders the set's joined tactic labels (a stacked `intro n` / `induction … with` / `intro hn` / `by_cases hp`) instead of `⋯`. It is SYNTACTIC, not semantic: the labels are concatenated verbatim, nothing is merged at the tactic level (`intro a` + `intro b` stays two lines, not `intro a b`) — the semantic version is a much harder problem and deliberately out of scope. `combineRuns` (elide.ts) finds every maximal LINEAR run — a chain tactic → goal → tactic → … where every step is single-parent/single-child, so there is no branching to lose — and its id set is the tactics PLUS the pass-through goals between them, deliberately EXCLUDING the boundary goals: the goal the first tactic consumes and the one the last produces stay drawn, so a combined node still reads as "from this goal, these steps, to that goal". Only runs of ≥2 tactics combine. Because a linear run has exactly one entry, a combine marker always has exactly ONE parent (measured: `maxParents=1` over the whole corpus), unlike a band cut. Unlike the ⇥/⇳ cuts it is AUTOMATIC — an engine-tier toggle (in the engine memo + `viewKey`, `anchorRoot` on flip, like reflow/brief), not a stored cut — so its marker is not click-to-restore; it folds like the ordinary tactic node it now is (`isCombined` splits the render: a combined node keeps the normal green tactic box and fold glyph, only an ELIDE marker gets the dashed `⋯` chip and the click-to-remove). Combine cuts are computed over the nodes the manual cuts don't claim, so the two stay disjoint. Measured over `proofs/`: 276 → 148 nodes (−46%) and total height −41% — euclid 42→14 (−67%, height −62%), odd_sums 80→38 (−52%), factorization 76→38 (−50%), and a proof with no linear runs is byte-identical; 0 dangling parents, every combined label exactly its tactics joined, and every original tactic still accounted for (none lost). Composes with reflow / side-by-side / brief / gallery. **A combined node keeps FULL per-token fidelity**, which is the part that needed real work: it maps to several source ranges, so the one-tactic render path can't colour it. `TreeNode.elidedCut.parts` therefore carries each constituent tactic's `label`, `position` and brief-`elision`, and `WrappedLine.seg` (the explicit-newline segment a wrapped line came out of, stamped in `wrapText`) maps every DRAWN line back to the part it belongs to. `renderCombinedLines` (ProofTreeView) renders each part against its OWN tactic and concatenates, so colour and hover popups survive the merge exactly as the separate nodes had them; a part's label can itself be multi-line, so parts own segment RANGES, not single indices. It is all-or-nothing per node (any part failing to align drops the whole box to plain text) so a combined box is never half-coloured. The cursor→tree accent survives too: `cursorTargets` offers EVERY part's range under the combined node's id, so the cursor anywhere in the run lights the one node now standing for it. Measured over `proofs/`: 32 combined nodes / 96 parts — 0 parts without a position, the per-part segment ranges exactly partition every node's lines (0 double-claimed, 0 uncovered), each part's lines reconstruct its label, and 96/96 constituent starts resolve to their combined node (0 wrong). What is still deliberately off on a merged node is **editing and click-to-reveal**, which are genuinely ambiguous over which constituent tactic; toggle ⇉ off to edit. Un-combined tactics are untouched either way. Toggling ⇉ does NOT re-centre (it is kept out of `viewKey`, and the handler sets no `anchorRoot`) — merging a run while you are deep in a proof must not scroll you back to the top; the `[nodes]` anchor pins the surviving node nearest the viewport centre instead, measured holding at 0px drift. **That anchor had a latent bug this exposed**: it compared a node's raw content `y` against `scrollTop + clientHeight/2`, but a node's screen position is `(MARGIN.top + PAD_Y + y) * zoom - scrollTop` and `PAD_Y` is a WHOLE viewport — so the "nearest the centre" pick was off by about a screenful and it held a node well above the viewport. The shift itself was always right (a difference cancels the constant), which is why it looked merely imprecise rather than broken.

**Gallery (the rail's ❮❯)** is the opposite trade to side-by-side: instead of spending width to show every branch at once, it shows ONE of a branching tactic's subtrees at a time, cycled by a `‹ n/m ›` pager. A wide case split then reads at the width of a linear proof. Implementation is deliberately thin — `computeLayout` grew a `hide` set that SEEDS the same fixpoint sweep the fold rule already runs, so hiding a branch's root takes its whole subtree with it and no reachability pass is needed; the view computes that set from `engine.childrenOf` (source-ordered, so "next" in the gallery is "next in the buffer") and a `pick` map keyed by the splitting node, read modulo the child count so a stale entry left by an edit can never point at nothing. Nested splits compose: page into a branch and its own splits grow their own pagers. Paging deliberately does NOT re-center the view — `shownChild` is kept OUT of `viewKey` for exactly this reason, so clicking `‹`/`›` holds the current scroll/pan; the relayout it triggers is steadied by the shared `[nodes]` anchor (in compact layout the trunk above the split is unmoved, so the anchored node's position is unchanged and scroll stays put). The pager hangs in the gap a branching tactic leaves above its children — `TRUNK_GAP_BRANCH` (24px) bounds it, and a tactic with one VISIBLE child still gets that gap (the tight `TRUNK_GAP_STEP` is a goal→tactic rule), so hiding the siblings can't squeeze it out; it is always visible rather than hover-revealed, being the only way to reach the hidden branches. **The gallery FOLLOWS the editor cursor**, and getting that right needed a second resolution path: `cursorNodeId` is matched against `cursorTargets`, which is built from the VISIBLE nodes — correct for the accent (it lights a drawn box) but fatal here, since the branch to page to is by definition the one not drawn, so `cursorNodeId` is null exactly when the follow has work to do. Hence `engine.allNodes()` and a separate `galleryTarget`; the root→cursor path then names, at each split it crosses, which child is on the way there. Once the follow pages to it, the node is visible and the accent resolves normally. It is adjusted during render (the `prevShape`/`prevHlKey` pattern) and guarded on the cursor landing on a DIFFERENT node, so it never fights a branch you paged to by hand. Measured on factorization: 76 boxes drawn → 18, height 7534 → 2723 (−64%); with ◫ columns also on, 4475×4334 → 2946×2723 (−34% width, −37% height). Suppressed in sequence mode, where `only` drives visibility instead.

**Side-by-side branches (the rail's ◫, compact mode)** turn a branching tactic's subtrees into COLUMNS sharing one vertical span — leftmost continues the trunk lane, later ones fork right in source order with their case badges on top — instead of stacking down the page. It is a `computeLayout` parameter (placement only, no engine rebuild; part of `viewKey`), implemented by threading `trunkLayout`'s y instead of using a global cursor, so a column can restart at its sibling's top; columns are CONTOUR-PACKED, not bounding-box packed: each is placed provisionally past everything, its occupied ink is collected as horizontal spans over y-ranges, and the whole column slides left until its ragged left profile sits `BRANCH_COL_GAP` from the previous columns' right profile at the nearest approach — so a tall column's one wide box no longer holds every neighbour at arm's length over its whole height. Two parts of that are load-bearing. The spans include CONNECTOR ink, not just node rects (`linkSpans`, which MIRRORS the renderer's routing math — change one, change both): a branch elbow's horizontal and the lane down to a distant child live outside every box, and packing against rects alone would slide a column onto them. And the split's own parent links are fed to the contour only AFTER packing, since their over-the-top horizontals span the very gaps being closed. Shifting after placement is safe because links hold `PlacedNode` references — moving `node.x` moves their geometry — but it forces `width` to be computed after all placement, not tracked during it (a running max would remember pre-shift positions). Verified: 0 pairwise box overlaps over all 174 nodes AND 0 link-through-foreign-box hits over all 167 links; packing widths vs bounding-box: euclid −19%, factorization −37%, branch-free proofs unchanged. All columns start at the SAME y, and the renderer relies on that: column links are TAGGED (`PlacedLink.col`) and routed over the columns' tops (down the parent's lane, across in the gap band, down the child's own lane) — the stacked `│└` elbow would cut through earlier columns' boxes, and the tag is deliberate rather than inferring from x-distance. Trade measured on euclid: 2968×557 stacked → 1598×1554 columns. Branch-free proofs lay out identically. `lean/ProofTreeScratch.lean`'s `three_column_demo` is shaped to show it off (a `refine` spawning three columns of unequal height, one splitting again); pairs with ¶ reflow, which is what makes the columns narrow enough to fit. **Reflow (the rail's ¶) trades height for width so branches sit side by side.** It re-wraps labels AND comment strips at `REFLOW_W` (44 cols vs the normal 100) and is threaded as a `createLayoutEngine` option, so unlike outline-only it is GEOMETRY: the engine rebuilds and `viewKey` includes it. **There are TWO budgets, cycled by the one button** (`REFLOW_MODES`, off → wide → narrow → off, the same three-state shape as `HYP_MODES` and for the same reasons: two booleans would let you ask for both budgets at once, and a second rail button would spend permanent space on an occasional mode). `wide` is exactly `2 × REFLOW_W`, a single derived constant so the two settings cannot drift apart, and everything else about the mode — the seam tiers, the eager break, the nested bracket indent, wrapped hyps — is shared. It exists because narrow reflow is a big trade and not always the one you want: measured over `proofs/`, **narrow takes total layout width −33.7% and the widest box −40.8% for +12.6% height and 17 wrapped context lines (17 lost type tooltips), while wide takes −17.1% / −19.2% for +2.0% height and 2 wrapped hyps** — about half the width saving for a sixth of the height cost and an eighth of the tooltip loss. So wide is the setting for bringing the widest boxes under control, narrow the one for getting three branches across the viewport. Two things make it readable rather than merely narrow. **Seams** are four tiers, and the ordering is the whole design: 3 = clause (comma/semicolon, connective `→ ↔ ∧ ∨ ⊢`, binder `∀ ∃ Σ λ fun`, tactic keyword `using with at by from generalizing :=`), 2 = GROUP (the previous word closes a bracket, or the next one opens one), 1 = relation (`= ≤ ∣ …`), 0 = none. Groups sit BELOW clauses deliberately — `(2 ≤ n → …)` should split at a nearby `∧`, not at the paren wrapping it, the same reasoning that already put relations last. On top of that a seam is DEMOTED one tier when it sits at bracket depth > 0, because breaking there splits something that reads as a unit: that is what makes `obtain ⟨m, hmdvd, hm2, hmlt⟩ := …` break at the top-level `:=` and keep the anonymous constructor whole, instead of at one of its nested commas. Two rules keep a break from reading badly regardless of tier: a token made entirely of operator glyphs (`OP_CHARS` — `*`, `=`, `∧`, `:=`, `⊢`) may never END a line, since the whole model is "break BEFORE the connective so the continuation STARTS with it" and a dangling `*` is that rule inverted (it bit via the GROUP tier, which scores the token AFTER it: `⊢ m + 1 = 2 * (k + 1)` broke as `⊢ m + 1 = 2 *` / `(k + 1)`); and no seam is taken until the line it closes clears a fill floor. **Reflow breaks EAGERLY** — at the earliest seam past that floor, even when the remainder would have fit. Filling the line to the budget is the wrong objective in this mode: a box is sized by its widest line, so a 38-column label that fits the 44-column budget still makes a 38-column box, and side-by-side columns pay for every one of those columns. Only "latest that fits" becomes "earliest that's worth it"; the tier order is untouched. It applies only to a line that is actually LONG (`EAGER_MIN_SEG`, 65% of the budget, measured against the text REMAINING for the line — which also stops a wrapped tail being split again once it has become short). Breaking a short label buys nothing: `refine ⟨?_, ?_, ?_⟩` sitting under a four-line goal box is already narrower than everything around it, so the split saves no width anywhere and reads as noise. That gate is close to free — it removed 32 of 87 breaks at ZERO cost to the widest box per proof (identical) and 1.1% of total layout width, while cutting height 4.4% and widows from 6 to 2. The two floors are deliberately different numbers (`SEAM_MIN_FILL` 0.4 vs `EAGER_MIN_FILL` 0.3) because they protect against different things — filling vs slivers — and sharing one was measurably worse: in `⊢ ∃ k, n = 2 * k ∨ n = 2 * k + 1` the `∨` seam sits at 36% and the `=` at 45%, so a shared 0.4 floor rejected the CLAUSE seam and took the relation one, for a worse break AND a wider box (max line 20 cols vs 16). Eager applies to labels and comment strips but NOT to hyp lines: measured, eager hyps bought a further 2% of total layout width and wrapped 18 more context lines to do it, i.e. 18 more lost type tooltips — the wrong side of that trade. Measured over `proofs/` in reflow mode: of 55 breaks, 46 land on a clause, 8 on a group boundary (the group tier is load-bearing, not decorative), 1 on a relation and **0 fall back to a greedy break**; 0 lines end on a dangling opener or a dangling operator, 0 begin with an orphaned closer, 2 leave a widow. Total layout width across the corpus drops 8.8% and the widest box per proof 6.6%, for 8% more height. Non-reflow wrapping is byte-identical (same width, height and line count over all 7 proofs) — the eager rule is gated on the mode and the operator rule never fires at a 100-column budget. **Indentation is per line, not a flat hang**: `WrappedLine.indent` replaced the old `cont ? CONT_INDENT : 0` rule everywhere (measurer AND render, which must agree), and the wrapper takes an `indentMode` — `flat` (every continuation hangs by `CONT_INDENT`), `nested` (reflow: `CONT_INDENT + bracketDepth × NEST_INDENT`, accumulated from `depthDelta` over the text already consumed and capped at 40% of the budget so a deep tail can't squeeze the line to nothing), and `none`. Comment strips take `none` in BOTH modes, because a strip is PROSE rather than a structured expression: neither hang means anything there, and indenting wrapped lines while the comment's own explicit-newline lines stay flush made the block ragged and hard to read. What separates comment lines instead is leading — `COMMENT_LINE_H` is 18 at an 11px font (1.6×, against `LINE_H`'s 1.2× for code). **`none` also switches the wrapper into PROSE mode** — greedy word-fill with the whole seam machinery (`seamRank`, the eager break) turned OFF: those tiers are tuned for Lean expressions ("break before the connective"), and on a sentence they break at a `+`/`=` and mid-formula, which is exactly what a reflowed docstring looked like — `the classical identity 1 + 3` / `+ ⋯ + (2m−1) = m²` with a dangling backtick. So `indentMode === "none"` is the one signal that means "this is a comment", carrying both no-indent and no-seams. The prose that reaches the wrapper is also cleaned first, in `stripComment` (proofToTree.ts): markdown delimiters that only read as noise in a one-block italic strip are removed (`**bold**` → bold, a leading `#`, and inline `` `code` `` → its text with the inner spaces turned NON-BREAKING so a formula stays one unbreakable token here — single-`*` is left alone, since `2 * k` is multiplication); and soft-wrapped source lines are re-joined, a single newline becoming a space and only a blank line a paragraph break, so a docstring reflows to the tree's own budget instead of inheriting the `.lean` file's physical line breaks. **The load-bearing discovery was that labels were never the binding constraint**: context lines are deliberately unwrapped (a mid-line break destroys the exact `name : type` string `renderTaggedHyps` matches on), and measuring showed 44 of the 84 boxes with a context are width-bound by their widest hyp — so wrapping only labels moved total width by 9.8% and the widest box not at all. Reflow therefore wraps hyps too, and pays the cost precisely where it falls: a WRAPPED hyp line stops matching by text and loses its type tooltip, while unwrapped ones keep theirs (measured: 9 of 292 context lines wrap). With that, the widest single box halves (681→340px) at a 4.4% height cost, and `lineOffsets` still reconstructs all 174 nodes — so goal tooltips and tactic token colouring are unaffected, which is the invariant to re-check if this is ever retuned.

**Controls are a floating icon rail, not a top bar.** All view controls live in a vertical icon-button column at top-right (`ControlRail` in ProofTreeView.tsx: ↶↷ undo/redo — widget only, and divided off because they change the FILE where everything below changes only how it is drawn — then ⊞⊟ expand/collapse, ⇅ accordion, ⋔ wide layered tree, ◫ side-by-side branches, ¶ reflow (off / wide / narrow, cycled), ⋯ brief (collapse in-tactic boilerplate), Δ/∀/▸ context breadth, ⇝ sequence, ◎ exit focus when focused, +−⛶ zoom/fit) — deliberately NO top bar, so the eye falls straight from the infoview's expected-types block onto the tree; words live in tooltips, toggles get pressed styling — and the LAYOUT button is the wide tree (⋔, pressed when wide), not the compact one: compact is the default and the reading mode, so the rail offers the departure from it rather than asking you to hold a toggle pressed to stay home. The state stays `compact`; only which way the button reads is inverted; rail/action-bar chrome is styled on the editor's own widget palette (`--vscode-editorWidget-background/-border`, `--vscode-icon-foreground`, `--vscode-toolbar-hoverBackground`) with light fallbacks for the standalone app, and corners are VS Code-tight (rail 3px, tactic boxes 4px vs goals 6px — a pill-round tactic read as a label, not an editable box). `headerExtra` (the standalone app's proof picker) and the sequence-hint pill float at top-left. The whole scroll container is `user-select: none` — the tree is a diagram driven by click/double-click/drag, and a stray selection fights all three (that is how the ⇧ gesture broke); the in-place editor's textarea opts back in with `user-select: text`, and the infoview's hover popups are portalled to `document.body` so they're unaffected. Because floaters overlay the content, a short (26px) **headroom veil** (a `pointer-events: none` gradient strip from the editor background to transparent) fades scrolled content out under them instead of letting it collide — kept deliberately shallow so nodes stay crisp as high as possible (the veil is absolute/zero-layout, so its height is pure fade distance, not reserved space). Wheel handling: zoom is `exp(-deltaY * 0.008)` (browser-page feel); plain scrolling has a **vertical gesture lock** — a wheel gesture that starts vertical stays vertical (manual `scrollTop` with `preventDefault`; a ≥180ms idle gap starts a new gesture), while horizontal scrolling is unrestricted — because the compact layout is read by vertical scrolling and trackpad drift would walk it sideways.
