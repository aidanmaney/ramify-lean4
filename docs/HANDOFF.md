```fish
cd <your clone>
git fetch origin claude/jolly-thompson-buna1f
```

## 2. In flight when the session ended: the WASM live tier (task: "level up" the playground)

Goal (owner): the baked playground loads instantly; an opt-in, DESKTOP-ONLY
download of real Lean in a Web Worker "levels it up" so un-baked tactics really
elaborate, behind the existing seam `answer(goalKey, tactic)` in
`web/src/playgroundAnswer.ts` (`makeAnswer([bakedEngine(t), wasmEngine])`).
**Phones are out of scope** (owner: "I don't care about running it on phones").

**It works** (measured in the cloud container; raw logs in `docs/wasm-measurements/`):

- Lean v4.32.2 (tag `f3b06c7`) builds to WebAssembly with emsdk **3.1.44** —
  Lean's own Emscripten path (`CMAKE_TOOLCHAIN_FILE=…/Emscripten.cmake`,
  `LEAN_INSTALL_SUFFIX=-linux_wasm32`, a 32-bit native stage0: `STAGE0_*` flags
  `-m32 -msse2 -mfpmath=sse`, `STAGE0_MMAP=OFF`; excerpt in
  `scripts/wasm/recipe/cmake-cache-excerpt.txt`). stage1 built in ~22 min.
- A custom entry point, `scripts/wasm/LiveEngine.lean` + `live_shim.c`
  (exports `ramify_init` / `ramify_answer`), linked by
  `scripts/wasm/recipe/link-live.sh` (needs a generated symbol table:
  `gen-symtab.py` → `symtab.o`; V8 caps a module at 100k exports, so no
  `MAIN_MODULE`/`EXPORT_ALL`). Unresolved `dl_iterate_phdr` / `lean_uv_tcp_*`
  were harmless.
- Sizes (`docs/wasm-measurements/sizes.txt`): `live.stripped.wasm` 66.9 MB raw
  / 12.1 MB gz / **6.7 MB br**; core oleans without private data
  (`init-noprivate.tar`) 87.5 MB / 33.1 MB gz / **22.8 MB br** → **≈ 30 MB br
  (≈ 45 MB gz — GitHub Pages serves gzip, not brotli)**.
- Chromium Web Worker (`scripts/wasm/worker-live.js`, `browser-live.mjs`):
  fetch ~0.9 s + runtime/unpack ~1.1 s + `import Init` ~0.75 s ≈ **2.7 s cold**;
  first tactic ~0.8 s; typical tactics **5–150 ms**; `omega`/induction-heavy
  200–470 ms. Native is ~2–5× faster. Answers have the baker's shape
  (`goals`, `uses`, `error`).
- Memory: WASM heap ~375 MB, but the Chrome tab's RSS climbed to **~1.4 GB**
  (`chrome-rss.txt`) — probably the olean tar held beside its unpacked MEMFS
  copy plus the debug/unstripped module; trimming is the next investigation.

**Verdict: GO WITH CAVEATS** — the full write-up is `docs/wasm-spike.md`
(commit `965e0bc`); read it before touching this. Summary:

- Lean's Emscripten target still exists but is unmaintained; the recipe is its
  commented-out CI job. It needed **12 patches** — committed as
  `scripts/wasm/recipe/lean4-v4.32.2-wasm.patch` (three are real 32-bit bugs:
  static name hashes truncated to 32 bits, a 1 GB default thread stack, eight
  C++ externs whose calling convention disagrees with the new compiler and trap
  the olean loader in wasm). The stock link exports 231k symbols (> V8's 100k),
  hence the static link + a generated 20k-symbol `Init` table for `dlsym`.
  Build: ~12 min stage0, ~32 min stage1, 12–22 min per optimised link.
- 42/42 requests answered identically by wasm, native and the baked table
  (AndSwap's goal keys match exactly). Per tactic: node median 12 ms / p90 122 /
  max 467; browser median 18 ms / p90 151 / max 0.8 s; a whole browser session
  6.1 s end to end on localhost.
- Download: `live.wasm` 6.7 MB br + `Init` without `.olean.private` 22.8 MB br
  ≈ **30 MB br / ≈ 45 MB gz**.
- Memory: tab peak ~1.41 GB → 1.14 GB with MEMFS `canOwn` (no second copy of the
  archive). The wasm heap holds every olean (no `mmap` in wasm). A small Lean
  patch to skip `.olean.private` (187 of the 275 MB) would save ~370 MB RSS
  (costs a ~40 min rebuild).
- Caveats: threads need COOP/COEP headers → GitHub Pages needs a
  `coi-serviceworker` shim; one `.ir` file fails to read, which blocks
  `import Lean` in the engine (needed for tagged prints of new goals); we would
  own the patch set and the build.
- Effort to ship the opt-in desktop tier: **~1.5–2 weeks**. Next steps: the
  `.olean.private` skip, fix the `.ir` read, a `wasmEngine` in `makeAnswer`
  behind an opt-in "Unlock live Lean" button (desktop only, Cache Storage via a
  service worker that also supplies COOP/COEP), hosting decision (gzip on Pages
  vs pre-compressed brotli elsewhere).

## 3. Open items and known rough edges

- **Playground**: phone header wraps to two rows (tree gets ~half the screen);
  `rcases h with hp | hq` aliasing per alternative; v2 ideas — share-link
  replay, click a goal to target it, show/copy the proof's source (already
  built, not shown), one hover table site-wide, trim boring errors (¾ of steps
  are errors, ~half the bytes).
- **Band**: not yet looked at under a theme with a saturated status bar (Dark+'s
  blue); Ramify hides the infoview's own Restart File button while mounted
  (CSS rule removed on unmount) — if vscode-lean4 renames `.restart-file-button`
  its button reappears over the band (harmless, ugly).
- **Lint popup**: in code-server a REAL mouse hover on the hint dots didn't open
  it (a dispatched mouseover did); works in the harness. Uninvestigated.
- **Keys** ⌘. / F8 / ⌘K chords: verified in the harness; check VS Code doesn't
  swallow them before the webview (fallbacks: ⇧F10, the strip's arrows).
- **Settings writes**: two writes within the watcher's read window can lose the
  first (same race as the hover-bar pin).
- Strategic choices taken on the judge's recommendation (owner may revisit):
  keep coloured goal/tactic boxes + amber cursor; no push channel from the
  extension into the widget yet; strip values rather than a single gear menu.

## 4. Working conventions the owner has asked for

- Prefer VS Code's own idioms (codicons, theme tokens, menus, status bar).
- Check EVERY surface after a change (menus, band, chips, header, panels, both
  appearances, light and dark), not just the one you touched — `probe icons`
  catches icon reuse and stray glyphs; screenshots catch the rest.
- Commit messages end with the Co-Authored-By / Claude-Session lines used
  throughout this branch's history; stage files explicitly.
- Deploying the site: `cd web && npm run publish:site` (needs Playwright for
  thumbnails; NODE_PATH to an install works), then copy `site/` onto the
  `gh-pages` branch (docs/viewer.md "Deploying").
